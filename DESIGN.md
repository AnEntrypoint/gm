# gm-new design directions

This note turns the evidence in `research/deep-research.md` into design directions. Each direction is marked as confirmed by the evidence, or as a hypothesis gm-new must test on its own workload before it becomes a design rule.

## Decided

- Scope: a fresh worker that replaces gm's loop, not a fork of gm. Reason: one worker, one log and one loop is the simplest design the evidence supports.
- Language: Node.js 22 or later, ES modules (see "Node floor 22 (2026-11-03)" at the end of this file). Dependencies: one pinned runtime dependency, acorn 8.18.0. No native code and no submodules. Any further dependency needs a measured gain in turns or accuracy, and a measured memory cost per worker, recorded here first. Decided 2026-11-02 as the joint decision of the owner and the orchestrator, which replaced the zero-dependency rule; see "Dependency rule, joint decision" below. The orchestrator rejected the agent's earlier change, which had added thorns and node:sqlite and raised Node to 22.5, and that change is reverted by the commit that records this rule. Reason: acorn is small and has no native code, and it gives exact call sites, which cuts the turns spent verifying callers and impact.
- Shape: gm-new is an MCP server (stdio, JSON-RPC written by hand with Node built-ins, no network listener) plus a skill at `skills/gm/SKILL.md`. The Claude Code session is the model. The CLI is a thin wrapper for scripted witnesses. Reason: owner decision, relayed by the gm agent (2026-11-01). It supersedes the earlier single-CLI shape, because the host model is already the worker.
- Self-iteration: gm-new runs on itself. The project .mcp.json starts tools/supervise.mjs with --runs runs/self and task tasks/self.md. Each server start gets its own run directory under runs/self. A run resumes only with an explicit --resume <run-id>. finish closes only that run, and a later session starts a new one. The skill and the self-task say the same. The step budget is 100000, which is correct for a shared project run. The gm agent decided this on the user's instruction (2026-11-01). The user approves the server once, in /mcp, the first time Claude Code opens the project, and nothing in gm-new can grant that. ccbridge sessions do not read project .mcp.json. gm-new writes nothing into any host's global config. The project .mcp.json is the only registration, and it lives in the repo.
- Hot reload: tools/relay.mjs holds the host connection and runs tools/supervise.mjs, which runs the worker as a child (see the relay bullet below). A change under src/ or skills/ holds new host requests, waits for calls in flight, pauses the worker with SIGTERM, starts a new one on the same run, and resumes the run from its log. A call still running is never interrupted or answered with an error: the restart waits until its result is logged. Background jobs stop at a restart, and each stop is logged. A broken source is reported, and the next good change recovers. It registers nothing in any config. Reason: the user asked for hot reload while the worker runs.
- Hot reload, decided and witnessed (gm agent, 2026-11-01): the project .mcp.json runs the host-facing relay, which runs the supervisor and the worker, so a running session reloads on a source change.
- Relay, so the supervisor can be replaced without a reconnect (user request, 2026-11-01): `tools/relay.mjs` is the only file the host runs, and it holds the host's stdio and never changes in normal work. It runs `tools/supervise.mjs` as a child. A change to `tools/supervise.mjs` swaps the supervisor: the relay refuses a file with a syntax error and keeps the running supervisor, otherwise it holds new host lines, waits for every request it sent to be answered, stops the supervisor with SIGTERM, and starts a new one on the same run. The supervisor pauses the worker on SIGTERM, so the run stays open, and the new supervisor restarts the worker with the reason `changed: supervise.mjs`. A supervisor that dies is replaced by the relay after a backoff (1 s, doubling to 30 s), and each call it had taken is answered with the failure text. The host sees one `notifications/tools/list_changed` notice per swap, and no disconnect. Reconnect needed: once, to move the project's `.mcp.json` from `tools/supervise.mjs` to `tools/relay.mjs`. After that, only a change to `tools/relay.mjs` or `.mcp.json` needs one. Reason: the user asked for no further reconnects while the worker is developed.
- Crash rules, decided with the relay (2026-11-01): a crash that the supervisor can catch (an uncaught exception or rejection) pauses the worker before it exits, so the run stays open. A SIGKILL of the supervisor cannot be caught by it, so the worker catches it instead: the worker runs with `--supervised yes`, and the end of its stdin pauses the run, and the next start resumes it. Before this fix a SIGKILL closed the run; the crash witness `crash-1793563150633` below shows that old behaviour and is superseded.
- Supervisor exit pauses, never closes (gm agent defect report, 2026-11-01): the old supervisor's SIGTERM ended the worker's stdin, which closed run `2026-11-01-19-50-16-6b638b` at seq 233 (inFlight 0, last result seq 231, commit 5d90f25, already pushed). Now every exit of `tools/supervise.mjs` (SIGTERM, SIGINT, the end of its stdin) pauses the worker with SIGTERM and waits for it to exit before the supervisor exits, and the worker pauses on the end of its stdin when it runs supervised. Witness, scripted (`/tmp/gm-scratch/gm-new/pause-fix/run-1793563965152/run`, driver `drive.mjs` beside it): three supervisor lives on one run. Life 1 ended with SIGTERM (paused at seq 5, reason SIGTERM from the supervisor), life 2 with SIGKILL (paused at seq 10, reason the supervisor ended stdin), life 3 with the end of stdin (paused at seq 15). Each life ended with a paused event and no end event, and each next life resumed the same run (restart at seq 6 and 11). The run has no end event at the end. A pause kills the worker's shell and job groups first, then waits for the calls to settle, so a pause orphans no shell. Before the change, a SIGKILL after the 5 s pause left a `sleep` running, found after the catchable-crash test.
- Relay witnesses (scripted, copies of the tree under `/tmp/gm-scratch/gm-new/hmr2`, drivers `drive.mjs`, `drive-throw.mjs`, `drive-crash.mjs`): `run-1793563317775` (a 3 s `run_shell` in flight at the swap was answered ok before the swap; two `restart` events with reason `changed: supervise.mjs`, one `notifications/tools/list_changed` notice per swap; a syntax-broken edit was refused with the old supervisor still answering; the restored file swapped again; the relay pid and stdio stayed up and the relay exited 0 after stdin ended). `throw-1793563286672` (an injected throw while a `run_shell` ran: the call settled with signal SIGTERM, the run has `paused` then `restart` with reason `retry after a failed start`, one run, and no orphan `sleep`). `crash-1793563150633` (SIGKILL of the supervisor: the call got the failure text, the retry started, and the run closed as the known limit above). Each server start gets its own run, and finish closes only its run. Witness: two sessions in a row, runs 2026-11-01-18-14-03-4867a3 (closed when its stdin ended) and 2026-11-01-18-14-03-8d72d4 (finished). The second session took its first step, unaffected by the first run's finish.
- Replacement principle: gm-new changes anything that can be changed or improved. No design choice is kept because gm made it. Each inherited choice is re-decided on evidence, and gm-derived plumbing is removed rather than adapted. Reason: the user's instruction (2026-11-01), that gm-new exists to change everything, not to bear the weight of gm's decisions.
- Independence from gm: gm-new does not use gm. Its code, skill, MCP server, runner, tests and builds use no gm MCP tool, no gm skill, no gm runner and no gm state. gm is the comparison target for arm B only, and the arm B configuration in the removed live runner is comparison tooling. Reason: gm-new replaces gm, so it must not depend on it (the user's instruction, 2026-11-01). Earlier builder briefs that named the gm MCP for code search are superseded.
- Model: gm-new makes no API calls. In MCP mode the host session is the model. The CLI has one model, `scripted`, which is offline and deterministic. Reason: a project decision (2026-11-01), taken on the user's instruction that gm-new is an MCP tool and does not interact with any API. No API key is needed, because interactive Claude Code runs on OAuth. Anything that would call an API is reported to the gm agent to do, not done here.
- Anthropic adapter: removed. gm-new holds no API key and sends no Messages API request, so the earlier decisions (the default model, the key from `ANTHROPIC_API_KEY`, the fetch adapter) are superseded. Reason: a project decision (2026-11-01), taken on the user's instruction that gm-new is an MCP tool. Spend belongs to the host session on the Claude Code login, not to gm-new.
- Context: no summarisation. `next_context` returns the rules, the task, the witness requirement, the events new since the last step in full, the seen events as compact records within two horizons (H1 = 14 and H2 = 12 events), and `prefixSha`; `query_log` reaches every event. Decided 2026-11-02 as the owner's request, approved by gm; see "Feed compaction". Reason: the log stays complete, so no lossy summary can drop a fact, and each event is transferred in full once.
- Governance: `rules.md` in the run directory is re-read at every step, placed first in the prompt and never compacted. Reason: rules that a summary drops are violated (finding 3).
- Tools (MCP): `next_context`, `read_file`, `write_file`, `list_dir`, `run_shell` (60 s default timeout), `job_start` (detached shell job), `job_status` (state, exit code and output tail, with a bounded `waitMs` poll), `query_log`, `finish` (needs a witness). The server writes every event to the log, and the host model calls `next_context` each step. The server answers concurrent requests: it reads stdin without blocking and replies by JSON-RPC id, so the host's parallel tool calls run in parallel and the server measures them. Reason: owner decision (2026-11-01). Each tool is one plannable step (finding 4), and background jobs let shell work overlap other actions (item 2).
- Kernel and phase plan (gm agent, 2026-11-02, decided by the gm agent, recorded here). The kernel comes from the gm agent's inventory of gm's 193 verbs: filesystem (read_file, write_file, edit_file, list_dir, stat_file), exec (run_shell and the job verbs; no language stem, since this Node project runs node through run_shell), git (the 11 verbs through the host git binary, with explicit paths for commit and add), ci_status (through gh api), and row tracking (prd_* and unknown_*). Dropped, plumbing only: the spool, leases, the FSM as data, the wasm sideload and sibling registry, install and skill serving, the hourly self-update, Dream-RSI, config sync over git, writer locks, and the witness ledger. Rows are files in `work/rows/<id>.yml`, and a row resolves with a witness of a seq in this run's log plus a commit that exists in the repository. Zero dependencies stays. The embedder and the vector store are dropped. The gh CLI stays as an external tool, because git push authentication and CI need it; it is not a gm component. Search is phase 2: BM25 over tracked files with no embedder, plus literal, regex and whole-word modes. callers and impact parse with acorn 8.18.0, decided by the joint decision of 2026-11-02 (see Dependency rule, joint decision). Phase 3 runs the project's tests and checks through run_shell, each with a witness, and no test files are written. Phase 4 (fetch, then browser over CDP) is optional. The gate for done: gm-new edits a small real change to itself through its own tools, in a live Claude session through airc, the commit goes through its own git verbs, and CI passes. Only after the gate do the gm dependencies come out, each removal in its own commit. The CLI prompt lists the original verbs only; the kernel verbs run in both modes, and the MCP tool list describes them to the model.
- Search (phase 2, gm agent 2026-11-02): `search` ranks the lines of git-tracked text files by BM25 (k1 1.2, b 0.75), and an identifier also matches its camelCase or snake_case parts. `grep` finds text by literal (default), regex, or word (a whole identifier), with optional ignoreCase and limit. Both are read-only and need no path, so they run beside writes; a result can show a file as it was just before a concurrent write. Files are read only if they are tracked, not symlinks, inside the workspace, text (no NUL in the first 8000 bytes), and at most 1 MB; each file is re-read only when its mtime or size changes. Known limits: a regex runs without a timeout, so a pattern with catastrophic backtracking blocks the server (patterns are capped at 200 characters); BM25 can rank a call site above the definition of a symbol that both lines contain; a workspace that is not a git repository is refused. callers and impact parse with acorn 8.18.0 (joint decision, 2026-11-02). Reason: the gm agent's phase plan (2026-11-02), phase 2.

It no longer re-reads the status file every 100 ms. Witness, run 2026-11-01-19-05-04-223331: job `evjob` (`sleep 2`), then one `job_status` call with waitMs 10000. The job ended at seq 35 and the reply came at seq 36, 0.347 ms later, in one call. The scripted measurement before the change had a 9.5 ms gap with 100 ms polling, and six calls for the same job.

## playwriter on each install (2026-11-03)

Question: is playwriter set up on every gm install the way it is on this machine? No. Three things differ.

- Each gm-new checkout runs the shipped default: `npx -y -p github:AnEntrypoint/pw#v0.1.0 playwriter-project` with telemetry off and no sandbox flag, from `defaults/mcp.json`. Setup registers only gm with the host (`setup.sh` prints add-mcp commands for gm alone), so the worker is the only thing that starts playwriter.
- This machine adds a layer through the `--mcp-config` file of its gm registration (`/config/.claude.json` points it at `/config/.gm-new/mcp.json`). That layer runs `/workspace/pw/bin/playwriter-project` with `PLAYWRITER_NO_SANDBOX=1`. The code matches the pinned tag: `git diff --stat v0.1.0 HEAD` in `/workspace/pw` lists only `docs/index.html`.
- The predecessor gm (`/workspace/gm`) installs no playwriter. Its `install.sh` and `bin/gm-install.js` do not name it, and only `.gitignore` names `.playwriter/`.

Decision: the shipped default does not set `PLAYWRITER_NO_SANDBOX`. It turns off Chromium's sandbox on every platform, and pw documents it only for Linux containers. README.md shows the layer that sets it. The owner may reverse this.

Witnesses (run 2026-11-03-19-43-51-791ac8): actionSeq 6 and 8 (defaults/mcp.json; `/workspace/pw` HEAD caab629 equals origin main), actionSeq 15 (pw sandbox handling at README:17 and bin/playwriter-project:156-170), actionSeq 23 (tag v0.1.0 handles the flag; package.json identical to HEAD), actionSeq 35 (setup.sh registers gm only), actionSeq 41 (the --mcp-config layer; no `.gm-new/` directory in the workspace).

## Dependency closure, blind witness (2026-11-03)

Question: does one-hop dependency closure help natural-language search? The earlier witness (15 descriptions written by the author, research/dep-recall/natural.cjs) let the described function's own hit anchor the closure, so its callees were credited by construction. This witness uses descriptions the author did not write, and reports the closure both ways.

- Units: all 35 top-level functions of gm-new src/ that call a function in another file, and 60 units sampled evenly from the 283 such functions in gm-mcp/src/ (the predecessor's MCP server). A name defined twice is excluded, as in research/dep-recall/units.cjs.
- Descriptions: three child writers (general-purpose agents) each read a share of 95 snippets. A snippet is the first 50 lines of one function, with the function's name replaced by FN. Each writer wrote one description per snippet from the code alone. Checked in run 2026-11-03-20-14-53-70d7da, actionSeq 203: 0 missing, 0 non-ASCII, 0 names leaking. The writers could not read skill://gm/SKILL.md (no ReadMcpResourceTool in their sessions), so the gm rule for subagents was not met for them; their output is text only. The descriptions and the unit map are in research/dep-recall/blind/.
- Measure (research/dep-recall/blind-measure.cjs, actionSeq 101). Mean recall of the callee-defining files, at the file budget that the closure itself reaches:

| corpus | plain at budget | closure, unit excluded from anchors | closure, unit allowed as anchor |
| --- | --- | --- | --- |
| all 95 | 0.235 | 0.398 | 0.476 |
| gm-new (35) | 0.384 | 0.508 | 0.631 |
| gm-mcp (60) | 0.147 | 0.333 | 0.386 |

- Production (research/dep-recall/production-check.cjs, run through gm.run_shell, actionSeq 246): the shipped search with closure true over the same 95 descriptions gives plain at budget 0.236 and closure 0.471, with 2.07 files added on average (gm-new 0.388 against 0.617; gm-mcp 0.147 against 0.386). Its closure rows read `path:line closure text`, at most 20, one for each JavaScript file that defines a function called from a top-10 hit and is not itself a top-10 file. src/closure.mjs parses the tracked JavaScript with acorn, the one runtime dependency, and caches the definitions by file digest. ## MCP features against gm-new, after the 2026-07-28 research (2026-11-03)

Research: deep-research workflow wf_226cee04-a18 (MCP protocol features): 20 sources, 25 claims verified, 20 confirmed, 5 refuted. The refuted claims are not used. Caveats from the run: the 2026-07-28 revision was current on 2026-11-03, and the release-candidate dates conflict across sources.

What gm-new declares and does (src/connect.mjs CAPABILITIES; src/mcp.mjs):

- tools, prompts and resources each declare listChanged: true. No subscribe, tasks, logging or completions capability.
- It negotiates 2025-11-25 and accepts 2025-06-18. Any other asked version gets 2025-11-25 back (src/mcp.mjs, the initialize reply).
- It serves server instructions (src/connect.mjs), the prompts gm and gm-continue, the skill:// resources, and an empty resources/templates/list.
- It sends notifications/progress for long calls and handles notifications/cancelled.
