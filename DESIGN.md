# gm-new design directions

This note turns the evidence in `research/deep-research.md` into design directions. Each direction is marked as confirmed by the evidence, or as a hypothesis gm-new must test on its own workload before it becomes a design rule.

## Decided

- Scope: a fresh worker that replaces gm's loop, not a fork of gm. Reason: one worker, one log and one loop is the simplest design the evidence supports.
- Language: Node.js 20+ ES modules, standard library only, zero dependencies. Reason: runs unchanged on macOS, Windows and Linux, on x64 and arm, with no build step.
- Shape: gm-new is an MCP server (stdio, JSON-RPC written by hand with Node built-ins, no network listener) plus a skill at `skills/gm-new/SKILL.md`. The Claude Code session is the model. The CLI is a thin wrapper for scripted witnesses. Reason: owner decision, relayed by the gm agent (2026-11-01). It supersedes the earlier single-CLI shape, because the host model is already the worker.
- Self-iteration: gm-new runs on itself. The project .mcp.json starts tools/supervise.mjs with --runs runs/self and task tasks/self.md. Each server start gets its own run directory under runs/self. A run resumes only with an explicit --resume <run-id>. finish closes only that run, and a later session starts a new one. The skill and the self-task say the same. The step budget is 100000, which is correct for a shared project run. The gm agent decided this on the user's instruction (2026-11-01). The user approves the server once, in /mcp, the first time Claude Code opens the project, and nothing in gm-new can grant that. ccbridge sessions do not read project .mcp.json. gm-new writes nothing into any host's global config. The project .mcp.json is the only registration, and it lives in the repo.
- Hot reload: tools/relay.mjs holds the host connection and runs tools/supervise.mjs, which runs the worker as a child (see the relay bullet below). A change under src/ or skills/ holds new host requests, waits for calls in flight, pauses the worker with SIGTERM, starts a new one on the same run, and resumes the run from its log. A call still running is never interrupted or answered with an error: the restart waits until its result is logged. Background jobs stop at a restart, and each stop is logged. A broken source is reported, and the next good change recovers. It registers nothing in any config. Reason: the user asked for hot reload while the worker runs.
- Hot reload, decided and witnessed (gm agent, 2026-11-01): the project .mcp.json runs the host-facing relay, which runs the supervisor and the worker, so a running session reloads on a source change.
- Relay, so the supervisor can be replaced without a reconnect (user request, 2026-11-01): `tools/relay.mjs` is the only file the host runs, and it holds the host's stdio and never changes in normal work. It runs `tools/supervise.mjs` as a child. A change to `tools/supervise.mjs` swaps the supervisor: the relay refuses a file with a syntax error and keeps the running supervisor, otherwise it holds new host lines, waits for every request it sent to be answered, stops the supervisor with SIGTERM, and starts a new one on the same run. The supervisor pauses the worker on SIGTERM, so the run stays open, and the new supervisor restarts the worker with the reason `changed: supervise.mjs`. A supervisor that dies is replaced by the relay after a backoff (1 s, doubling to 30 s), and each call it had taken is answered with the failure text. The host sees one `notifications/tools/list_changed` notice per swap, and no disconnect. Reconnect needed: once, to move the project's `.mcp.json` from `tools/supervise.mjs` to `tools/relay.mjs`. After that, only a change to `tools/relay.mjs` or `.mcp.json` needs one. Reason: the user asked for no further reconnects while the worker is developed.
- Crash rules, decided with the relay (2026-11-01): a crash that the supervisor can catch (an uncaught exception or rejection) pauses the worker before it exits, so the run stays open. A SIGKILL of the supervisor cannot be caught by it, so the worker catches it instead: the worker runs with `--supervised yes`, and the end of its stdin pauses the run, and the next start resumes it. Before this fix a SIGKILL closed the run; the crash witness `crash-1793563150633` below shows that old behaviour and is superseded.
- Supervisor exit pauses, never closes (gm agent defect report, 2026-11-01): the old supervisor's SIGTERM ended the worker's stdin, which closed run `2026-11-01-19-50-16-6b638b` at seq 233 (inFlight 0, last result seq 231, commit 5d90f25, already pushed). Now every exit of `tools/supervise.mjs` (SIGTERM, SIGINT, the end of its stdin) pauses the worker with SIGTERM and waits for it to exit before the supervisor exits, and the worker pauses on the end of its stdin when it runs supervised. Witness, scripted (`/tmp/gm-scratch/gm-new/pause-fix/run-1793563965152/run`, driver `drive.mjs` beside it): three supervisor lives on one run. Life 1 ended with SIGTERM (paused at seq 5, reason SIGTERM from the supervisor), life 2 with SIGKILL (paused at seq 10, reason the supervisor ended stdin), life 3 with the end of stdin (paused at seq 15). Each life ended with a paused event and no end event, and each next life resumed the same run (restart at seq 6 and 11). The run has no end event at the end. A pause kills the worker's shell and job groups first, then waits for the calls to settle, so a pause orphans no shell. Before the change, a SIGKILL after the 5 s pause left a `sleep` running, found after the catchable-crash test.
- Relay witnesses (scripted, copies of the tree under `/tmp/gm-scratch/gm-new/hmr2`, drivers `drive.mjs`, `drive-throw.mjs`, `drive-crash.mjs`): `run-1793563317775` (a 3 s `run_shell` in flight at the swap was answered ok before the swap; two `restart` events with reason `changed: supervise.mjs`, one `notifications/tools/list_changed` notice per swap; a syntax-broken edit was refused with the old supervisor still answering; the restored file swapped again; the relay pid and stdio stayed up and the relay exited 0 after stdin ended). `throw-1793563286672` (an injected throw while a `run_shell` ran: the call settled with signal SIGTERM, the run has `paused` then `restart` with reason `retry after a failed start`, one run, and no orphan `sleep`). `crash-1793563150633` (SIGKILL of the supervisor: the call got the failure text, the retry started, and the run closed as the known limit above). Each server start gets its own run, and finish closes only its run. The second session took its first step, unaffected by the first run's finish.
- Replacement principle: gm-new changes anything that can be changed or improved. No design choice is kept because gm made it. Each inherited choice is re-decided on evidence, and gm-derived plumbing is removed rather than adapted. Reason: the user's instruction (2026-11-01), that gm-new exists to change everything, not to bear the weight of gm's decisions.
- Independence from gm: gm-new does not use gm. Its code, skill, MCP server, runner, tests and builds use no gm MCP tool, no gm skill, no gm runner and no gm state. gm is the comparison target for arm B only, and the arm B configuration in the removed live runner is comparison tooling. Reason: gm-new replaces gm, so it must not depend on it (the user's instruction, 2026-11-01). Earlier builder briefs that named the gm MCP for code search are superseded.
- Model: gm-new makes no API calls. In MCP mode the host session is the model. The CLI has one model, `scripted`, which is offline and deterministic. Reason: a project decision (2026-11-01), taken on the user's instruction that gm-new is an MCP tool and does not interact with any API. No API key is needed, because interactive Claude Code runs on OAuth. Anything that would call an API is reported to the gm agent to do, not done here.
- Anthropic adapter: removed. gm-new holds no API key and sends no Messages API request, so the earlier decisions (the default model, the key from `ANTHROPIC_API_KEY`, the fetch adapter) are superseded. Reason: a project decision (2026-11-01), taken on the user's instruction that gm-new is an MCP tool. Spend belongs to the host session on the Claude Code login, not to gm-new.
- Context: no summarisation. `next_context` returns the rules, the task, the witness requirement, the last 20 events and `prefixSha`; `query_log` reaches older events. Reason: the log stays complete, so no lossy summary can drop a fact.
- Governance: `rules.md` in the run directory is re-read at every step, placed first in the prompt and never compacted. Reason: rules that a summary drops are violated (finding 3).
- Tools (MCP): `next_context`, `read_file`, `write_file`, `list_dir`, `run_shell` (60 s default timeout), `job_start` (detached shell job), `job_status` (state, exit code and output tail, with a bounded `waitMs` poll), `query_log`, `finish` (needs a witness). The server writes every event to the log, and the host model calls `next_context` each step. The server answers concurrent requests: it reads stdin without blocking and replies by JSON-RPC id, so the host's parallel tool calls run in parallel and the server measures them. Reason: owner decision (2026-11-01). Each tool is one plannable step (finding 4), and background jobs let shell work overlap other actions (item 2).
- Kernel and phase plan (gm agent, 2026-11-02, decided by the gm agent, recorded here). The kernel comes from the gm agent's inventory of gm's 193 verbs: filesystem (read_file, write_file, edit_file, list_dir, stat_file), exec (run_shell and the job verbs; no language stem, since this Node project runs node through run_shell), git (the 11 verbs through the host git binary, with explicit paths for commit and add), ci_status (through gh api), and row tracking (prd_* and unknown_*). Dropped, plumbing only: the spool, leases, the FSM as data, the wasm sideload and sibling registry, install and skill serving, the hourly self-update, Dream-RSI, config sync over git, writer locks, and the witness ledger. Rows are files in `work/rows/<id>.yml`, and a row resolves with a witness of a seq in this run's log plus a commit that exists in the repository. Zero dependencies stays. The embedder and the vector store are dropped. The gh CLI stays as an external tool, because git push authentication and CI need it; it is not a gm component. Search is phase 2: BM25 over tracked files with no embedder, plus literal, regex and whole-word modes. callers and impact need a parser, which is a dependency decision for the user; until it is made, they are not available. Phase 3 runs the project's tests and checks through run_shell, each with a witness, and no test files are written. Phase 4 (fetch, then browser over CDP) is optional. The gate for done: gm-new edits a small real change to itself through its own tools, in a live Claude session through airc, the commit goes through its own git verbs, and CI passes. Only after the gate do the gm dependencies come out, each removal in its own commit. The CLI prompt lists the original verbs only; the kernel verbs run in both modes, and the MCP tool list describes them to the model.
- Search (phase 2, gm agent 2026-11-02): `search` ranks the lines of git-tracked text files by BM25 (k1 1.2, b 0.75), and an identifier also matches its camelCase or snake_case parts. `grep` finds text by literal (default), regex, or word (a whole identifier), with optional ignoreCase and limit. Both are read-only and need no path, so they run beside writes; a result can show a file as it was just before a concurrent write. Files are read only if they are tracked, not symlinks, inside the workspace, text (no NUL in the first 8000 bytes), and at most 1 MB; each file is re-read only when its mtime or size changes. Known limits: a regex runs without a timeout, so a pattern with catastrophic backtracking blocks the server (patterns are capped at 200 characters); BM25 can rank a call site above the definition of a symbol that both lines contain; a workspace that is not a git repository is refused. callers and impact are not available until the user decides the parser dependency. Reason: the gm agent's phase plan (2026-11-02), phase 2.

- Wait for a job (brief change 4, gm agent 2026-11-01): a 3-second job, measured two ways in scripted drivers (`/tmp/gmnc/poll/drive.mjs`, run `/tmp/gmnc/poll/runs/poll`). Bounded polling, one job_status call with waitMs 500 repeated until the job leaves running: 6 calls, and the final reply came 9.5 ms after the job ended. One long wait, one job_status call with waitMs 30000: 1 call, and the reply came 0.2 ms after the job ended. The extra latency of polling is 9.3 ms, under the 100 ms threshold, so the default is the one long wait, which uses fewer calls. A job that runs past 30000 ms needs a second call.
- Tool list hash (brief change 7, gm agent 2026-11-01): each start logs a `tools` event with the sha256 of the served tool list. A resumed run whose last `tools` hash differs logs `tools-changed` with `old` and `new`. A changed description invalidates the host's prompt cache (documented), so tool descriptions stay stable unless a change is needed. The worker does not see the host's cache usage, so the usage fields stay in the host transcript, as recorded earlier, and the log does not claim a saving.
- Retry after a failed restart (gm agent decision, 2026-11-01): a failed restart retries by itself, starting at 1 s and doubling to a 30 s cap, and it needs no source change. A call that arrives while the restart is failed is answered at once with the failure text, and a held call is answered the same way. - Restart and pause (brief changes 1 and 2, gm agent 2026-11-01): a restart waits for every call in flight to have its result logged. The 30-second error is gone, and no call is answered with a restart error, so the host does not repeat a call that is still running. The supervisor pauses the worker with SIGTERM. The worker writes a `paused` event, stops its jobs, and exits, and the supervisor sends SIGKILL after 5 seconds. Closing stdin is not part of the pause, because it would end the run as closed, and a closed run stays closed. A repeated tools/call request id is answered from the first reply and logged as a `duplicate`, never run again. Reason: the gm agent's research brief, with Claude Code's default tool timeout of about 28 hours.
- Output pages (brief change 3, gm agent 2026-11-01): `read_file` returns one page of at most 20000 characters, from `offset` (default 0) with `limit` (default 20000). Its result carries `total` (characters in the file), `offset` and `next`, the offset of the next page, or null at the end. `grep` takes `offset` over matches and stops a page at 20000 characters of output. Its footer reads "showing A to B; next offset N". `job_status` with `offset` returns one page of the job output, with `next`. Without `offset` it keeps the 2000-character tail. Offsets count JavaScript characters (UTF-16 units). Reason: the gm agent's brief, so one result cannot flood a context window.
- Callers and impact (item 3, gm agent 2026-11-01, zero dependencies): `callers` lists the call sites of an identifier in tracked .js, .mjs, .cjs and .ts files, by regex over each line. A call is the name followed by an open parenthesis and not a property access. A member call is `.name(`. A definition line (function, class, const/let/var, or a method shorthand) is excluded and marks its file as defining the name. A call in a file that imports a defining file is marked linked. `impact` lists the defining files, the files that call the name, and the importers of those, out to depth levels (default 2, max 5). Import edges come from a regex over `from`, `import(`, `require(` and `import` specifiers, resolved inside the repo only. Every answer says approximate. Known limits, stated in each answer: dynamic calls, re-exports and shadowed names are not resolved, and a line that starts with a comment marker is skipped. A string that contains `name(` is still counted. Reason: the gm agent's decision for zero dependencies (2026-11-01). Item 5 of the brief measures this regex against an acorn oracle.
- Fetch (item 2, gm agent 2026-11-01): `fetch` is an HTTP GET of one http or https URL through Node's built-in fetch, with no body, no cookies and no credentials. Redirects are followed by hand and capped (`maxRedirects`, default 5, up to 10). The timeout covers the headers and the body (`timeoutMs`, default 15000, up to 60000). The body is read up to `maxBytes` (default 2000000, up to 20000000), and `truncated` says when the cap cut it. HTML is reduced to text, and script, style, noscript and comments are dropped before the tags are removed. The result carries status, bytes, finalUrl, redirects and truncated, and a non-2xx status is reported as data, not as an error. Known limit: nothing blocks localhost or private-network addresses, so a fetch can reach services on the worker's host or LAN. The text is untrusted input, and the model must treat it as data. Reason: the gm agent's item 2 (2026-11-01).
- Commit gate (owner decision, relayed by the gm agent, 2026-11-01): there is no CI, and the quality checks run inside the git_commit verb on every commit. Four checks run before the commit, and a failed check refuses it. `syntax` parses every tracked module with node --check. `ascii` finds non-ASCII text in every tracked text file. `docs` requires every repo path that DESIGN.md, AGENTS.md or README.md names in backticks to exist in the index, and every KEEP path to exist on disk. A path counts as a repo path when its first segment is a top-level name in the index. Runtime directories, placeholders, URLs, method names and absolute paths are not checked. `smoke` runs the CLI on a scripted task, which must finish, and a negative control with one step, which must stop at max_steps. Each check reports its result and time in the git_commit result event. No test files and no test directory exist. Reason: the owner's no-test rule, applied to the commit path.
- Gaps, recorded not hidden (gm agent decision, 2026-11-01, from arXiv 2609.02749, Sec. 3.2: "any gap that survives the checks is recorded ... rather than hidden"): every `git_commit` result and its `commit` event carry `notCovered`, a fixed list of what the gate does not check: the semantic correctness of the change, behaviour the smoke run does not exercise, doc content beyond path existence, and CI (none configured). A refused commit carries it too. `finish` takes an optional `gaps` array, logged in the `end` event with the witness, which is still required. A bad `gaps` value is refused and the run stays open. Witness: finish, scripted (`/tmp/gm-scratch/gm-new/gaps/run-1793563683727/run`): a `gaps` array with a number in it was refused with a `refusal` event, the run stayed open, and the next finish logged `gaps` with its two strings in the end event. - Long-horizon rules (gm agent decisions, 2026-11-01, from the DeepSeek superagent prototype's documents 003-execution.md, 007-architecture.md and 000-philosophy.md in dsh-superagent-prototype). Grade: documented design from a research prototype, not measured, and untested on our workload. (1) Recovery note: a run that resumes after a restart carries a recovery note in the next next_context. It names the last seq and each action that started and has no end event, with its tool and arguments, and it asks the model to verify outside effects (git log, git status, the remote, the row files) before repeating a push, a commit, a fetch that posted, or a row resolve. (2) Persisted request ids: each action records its request id, and at startup the worker rebuilds the duplicate map from the log, so a repeated id is answered from the log and never run again. An action with no end event was interrupted, and its repeat gets an error that asks for the outside effects to be checked. (3) Background job lifetime: a job is killed after 30 minutes by default (flag `--job-lifetime-ms`). The kill is logged as its own `job-killed` event with the output tail, and the next next_context names it. (4) Log growth: the log stays complete, and nothing is deleted. The measured growth and query cost are in Measured.
- Background jobs keep state in `runs/<id>/jobs/<job>.json` (written by rename) and output in `<job>.out`. A job still running at run end is killed and awaited, and its end is logged as a `job` event. Reason: status is readable by any process, and no child outlives the run.
- Path confinement covers the file tools only: `read_file`, `write_file` and `list_dir`. Paths stay inside the workspace, a `..` segment is refused, and a symlink that leaves the workspace is refused, including a dangling one (checked with `lstat` in `nearestExisting`). Refusals are logged as `refusal` events and not thrown. `run_shell` is not confined, and doctor says so. Known limit: a shell command can create a hard link to a file outside the workspace, and the path checks do not see it. A path check does not close this, because a shell can do anything the user can. Reason: an escape attempt through the file tools shows up in the log, and path checks cannot confine a shell (gm agent, 2026-11-01).
- Loop: plan, act, observe, repeat. Each reply is one JSON action or an array of actions; actions that touch no common path run together in one wave with `Promise.all`, and a shell command, `query_log`, `finish` or unknown tool runs alone. Every reply, action and result is appended to the log with monotonic times. Stops on `finish` or at `maxSteps` (default 50). An unparseable reply counts as one step. Reason: work item 1 needs multi-action replies, and the wave rule keeps the log replayable.
- Wave planning uses real paths, not lexical ones. An existing path uses `realpath`; a new file uses the `realpath` of its parent plus its basename. Existing files are grouped by dev and ino, so hard links serialise. Writes that share a group go in one serial wave. Reason: a symlink alias or hard link to a file written in the same reply would race under `Promise.all` (found by the item 5 witness).
- Storage: `runs/<run-id>/` holds `log.jsonl` (append-only), `rules.md` and `task.json`, and `runs/` is git-ignored. Reason: runtime state is never tracked.

Reason: no child outlives the run, and a grandchild that outlives its foreground call breaks that rule. Owner decision via the gm agent (2026-11-01). A shell call runs alone. Reads of distinct paths may run together. Reason: both arms are measured by the same code, from the transcript timestamps, not from our own clocks. Owner decision via the gm agent (2026-11-01).

## Simplicity rule

Start with one worker, one log and one loop. Add a component only when a measured run shows the current design failing. This follows the Anthropic harness guidance (low confidence, dated) and the single-agent baseline result (medium confidence).

## Directions

1. **Complete log, queried by code (hypothesis).** Every observation, action and outcome is appended to one log. Recall runs code over the log, not a summary. Evidence: finding 1 (medium). Unknown: log growth and retrieval cost. Test: the same long task run with a log-query worker and a compacting worker, with cost measured.

2. **Validated compaction, only when the log is too big to query (hypothesis).** If compaction is needed, check each summary against the next k steps before using it. Evidence: finding 2 (medium, self-reported, one replication dispute). Test: summary accepted or rejected by a judge on gm's own traces, compared against no validation.

3. **Governance rules outside the compactor (hypothesis, risk confirmed, fix untested).** Rules that must hold for the whole run are kept in a file that every step re-reads, so they cannot be summarised away. Evidence: finding 3 supports the risk (medium, observational). The Constraint Pinning remedy was refuted 0-3, so this direction is not evidence-backed. Test: a rule set of gm's kind, violation rate with and without re-injection.

4. **Context operations as worker actions (hypothesis).** Compaction and log queries are actions the worker plans, like file edits and commands. Evidence: finding 4 (medium). The 57.6% result is one run against same-family baselines, below frontier models, so it is not evidence that the design is best.

5. **Summariser trained with the worker (out of scope for now).** Finding 5 (medium) needs training infrastructure gm-new does not have. Keep it as a later option, not a day-one design.

6. **Measure one worker before fanning out (confirmed in direction, threshold unusable).** Finding 6 (medium) supports measuring a single-worker baseline before adding parallel workers. The saturation threshold (finding 7, low) must not be used as a constant (94% and 45% are unverified).

7. **Subagent isolation (open).** The claim that isolated subagents help was refuted 1-2. Parallel subagents stay in gm-new only where a measured run shows they beat one worker on the same task.
8. **Proactive mode (future, not built).** The agent watches a repo with no task. Source: the DeepSeek prototype README (github.com/deepseek-ai/dsh-superagent-prototype), checked against the primary sources in research run wf_261fe87f-4c6. It describes a proactive coding agent for one repository, and the article's designs for it are unimplemented. gm-new is task-driven, so this is a future direction with no evidence here.
9. **Verification-gated admission (future, not built).** If gm-new learns from its runs, an item is admitted only after a check, and the gaps the check did not cover are recorded, not hidden. Source: arXiv 2609.02749 (Repo-To-Skill, AREX-Skill), Sec. 3.2: "No skill is admitted on the strength of its sources alone," and "any gap that survives the checks is recorded ... rather than hidden." The gains there are self-reported, from one preprint with no replication. The paper excludes construction from both runtime conditions for MLE-bench and PaperBench; it does not say whether construction is counted for FrontierCS or PassNet.
10. **Matched-budget falsifier (future, not built).** Once a learned artifact exists, compare it with and without the artifact, with the same model, the same budget and the same tasks, at least 3 trials per task. Count the construction cost inside the budget. The source paper (arXiv 2609.02749) excludes construction from both runtime conditions for MLE-bench and PaperBench, and does not say whether construction is counted for FrontierCS or PassNet. On FrontierCS, token use rises about 82% (2.46M to 4.47M per task) and tool calls rise from 64.7 to 105.0 (figures as read by the gm agent, 2026-11-01), so a falsifier must count that run cost as well. Trigger: this falsifier is built only when gm-new writes a reusable artifact from its runs. Until then it is not built.
11. **Raw-replay arm (future).** When there is something to replay, add an arm that replays the raw log instead of a distilled skill. SkillEvolBench (arXiv 2605.24117) finds raw replay often beats distilled skills. The full log already keeps the raw trajectory (direction 1). Skill distillation is not built: the log is the raw trajectory, and the falsifier in direction 10 is triggered only when gm-new writes a reusable artifact from its runs. SkillEvolBench is cited from the gm agent's reading (2026-11-01).

## Concurrency evidence (digest, research/concurrency.md)

- Parallel tool calls in one turn cut wall-clock 40.6% and cost 35.9% in one self-reported study (medium, arxiv 2602.07359). Use: work item 1, measured in item 7.
- Overlapping tool execution with generation can cut latency (medium, arxiv 2603.18897, serving-system paper). Speculation can hurt under high load: unsupported, because the brief found no support for that claim. Use: default off until measured.
- Fine-grained tool streaming may return invalid JSON tool input. Use: not enabled. The parser already handles unparseable replies.
- Prompt caching: order is tools, system, messages; put the breakpoint at the end of the stable prefix, before the event window. Measured 41 to 80% cost cut and 13 to 31% faster first token (medium, arxiv 2601.06007). Use: rule 5, item 4.
- Rate limits: honour retry-after first, then backoff (high, Anthropic docs). Cached input tokens do not count toward input-tokens-per-minute for most models (high). Use: rule 6, item 3.
- Primary-sourced by the brief (gm agent, 2026-11-01): the minimum cacheable prefix for claude-haiku-5-5 is 512 tokens, cache writes cost 1.25x and 2x (one for each cache TTL), and cache reads cost 0.1x. Still unverified: the back-pressure measurement. No saving is claimed from these until a live usage run measures it.

## Wiki (gm agent decision, 2026-11-01)

- Item 1, raw source archive: built. `fetch` saves the full body, up to 1 MB, as ASCII text in `sources/<id>.txt`. The id is the first 12 hex digits of the sha256 of the stored bytes. Every non-ASCII UTF-16 code unit is written as a `\uXXXX` escape, so the repo's ASCII rule holds and the text can be recovered. The one lossy step is invalid UTF-8, which becomes U+FFFD. A file is written once (`wx`), so a fetch of an existing id leaves it unchanged. The reply carries `source` and `sourceNew`, and each fetch adds one line to `sources/index.jsonl`.
