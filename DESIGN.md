## Hot reload language (2026-11-04)

Owner direction, 2026-11-04: choose the ideal language for hot reload. QuickJS is not mandatory, and every option is a candidate. Decision: hot code is ES2023 JavaScript run by QuickJS-NG, in one fresh context per leaf call. This supersedes decisions 4 and 7 of "Rewrite on deoxidene" for the leaves: the leaves are JavaScript modules in native/leaves/, not native plugins in native/plugins/.

Candidates, judged on reload cost, crash isolation, toolchain needed at edit time, portability to the six targets, and one language with run_code bodies:

| Option | Reload cost | Verdict |
| --- | --- | --- |
| Native C++ plugin, rebuilt on change and loaded with dlopen (deoxidene tier 0, spike in docs/spikes/hmr) | A compile per edit, then a load. A loaded DLL cannot be overwritten on Windows, so each load needs a copied file. A crash in a plugin takes the worker down. | Rejected for leaves. Every machine that edits gm-new would need a C++ toolchain at edit time. Core code stays native and restarts through the relay instead of reloading. |
| QuickJS-NG, leaves as JavaScript modules, fresh context per call (chosen) | No compile step. A changed file is read and its bytecode cached by mtime; the next call uses it. Deoxidene measured about 0.1 ms per runtime and context. | Chosen. One language for leaves and run_code bodies, C source with no dependency, builds with any C compiler on the six targets, and an exception stays inside its call. |
| Lua 5.4 or LuaJIT | As QuickJS | Rejected: run_code bodies are JavaScript, so Lua would be a second language for the leaves. |
| Hermes | As QuickJS | Rejected: a much larger source tree and build for the same job. |
| WebAssembly modules (wasm3 or WAMR as the interpreter) | A compile to wasm per edit | Rejected: needs a compiler at edit time, as native does, plus an extra runtime. |
| Node.js as the host (gm-new today) | An ESM loader hook, cheap | Rejected for the rewrite: it keeps the Node runtime the rewrite removes. It stays the live runtime until cutover. |
| Embedded Python | Interpreter reload | Rejected: a heavy runtime and a third language. |

Rules that follow from the choice:
- A leaf is native/leaves/<name>.mjs. It exports verbs, an array of objects with name, description, inputSchema and call(args). A leaf keeps no state at module level, because each call runs in a fresh context.
- A leaf reaches the host only through host.<name>(args), where the name is a native verb (read_file, write_file, list_dir, stat_file, edit_file, search, grep, and the others) or one of the extra primitives (run, shell, logAppend). It uses no Node or engine-specific API, so the same file also runs under node in its tests.
- Reload: a call recompiles a leaf when its mtime or size changes. A file that does not compile keeps its last good bytecode, and the error goes to the caller and the log, as the Node loader keeps old code on a refused reload.
- The core (MCP server, run log, job table, verb table, primitives) is C++. A change to it restarts the worker through the relay, as today.
- Witness: an edit to a leaf takes effect on the next call with no restart. The latency is measured and recorded here.

## Rewrite on deoxidene (2026-11-04)

Owner direction, 2026-11-04 (`/mcp__gm__gm`): rewrite gm-new starting from `../deoxidene` as the boilerplate, keep gm-new's hot reload, and the orchestrating session decides the rest. Decided by the orchestrator under that delegation:

1. Language and build: C++23 with deoxidene's CMake presets, library headers (`include/deoxidene/`), vendored `third_party/tl/` and CTest setup. Preset names are the ones in `CMakePresets.json` (x64 and arm64 on Linux, Windows and macOS). Built and tested here with GCC 15.2, CMake 4.2, Ninja.
2. Node stays the live runtime until the native build reaches parity and is witnessed. `src/` and `tools/` are not edited during the port: a half-made edit there is live to every running worker (see AGENTS.md, "shared checkout is live"). Cutover is one commit that points `.mcp.json` at the native binary, and it needs a reconnect.
3. `run_code` bodies run in QuickJS-NG (deoxidene tier 1, measured in the QuickJS spike of deoxidene (its docs/spikes/quickjs)). The `gm.*` verbs are bound as native functions, so bodies stay JavaScript and existing prompts and skills keep working.
4. Hot reload: superseded by "Hot reload language (2026-11-04)".
5. `fetch` runs the system `curl` (present on macOS, Linux and Windows 10 and later), so there is no TLS library. No new library was added.
6. `callers` and `impact` (code-ast) need a JavaScript parser. acorn is pure JavaScript, so it is vendored as a file and run inside QuickJS-NG; no native parser is written.
7. Layout: `native/components/<name>` holds the core (json, log, host, quickjs, mcp, verbs, relay), and `native/plugins/<name>` holds the leaf plugins. `native/CMakeLists.txt` adds every directory that has a `CMakeLists.txt`, so a directory is added only once it configures and builds.
8. Comments: the new code has none. A reason that cannot be read from the code goes to AGENTS.md after it is checked (INVARIANT 6).
9. Commits are attributed to lanmower with no trailers and pushed to origin main at each witnessed milestone. Nothing is pushed that breaks the running gm-new.

Milestones: M0 the scaffold configures and its boilerplate tests pass. M1 json and the run log pass their tests. M2 the native binary serves the three-tool surface over stdio from a fresh run. M3 each verb group matches the JavaScript on the same inputs. M4 a plugin edit is live in the running process, shown by a new generation. M5 cutover.

## Decided

- Scope: a fresh worker that replaces gm's loop, not a fork of gm. Reason: one worker, one log and one loop is the simplest design the evidence supports.
- Language: Node.js 22 or later, ES modules (see "Node floor 22 (2026-11-03)" at the end of this file). Dependencies: one pinned runtime dependency, acorn 8.18.0. No native code and no submodules. Any further dependency needs a measured gain in turns or accuracy, and a measured memory cost per worker, recorded here first. Decided 2026-11-02 as the joint decision of the owner and the orchestrator, which replaced the zero-dependency rule; see "Dependency rule, joint decision" below. The orchestrator rejected the agent's earlier change, which had added thorns and node:sqlite and raised Node to 22.5, and that change is reverted by the commit that records this rule. Reason: acorn is small and has no native code, and it gives exact call sites, which cuts the turns spent verifying callers and impact.
- Shape: gm-new is an MCP server (stdio, JSON-RPC written by hand with Node built-ins, no network listener) plus a skill at `skills/gm/SKILL.md`. The Claude Code session is the model. The CLI is a thin wrapper for scripted witnesses. Reason: owner decision, relayed by the gm agent (2026-11-01). It supersedes the earlier single-CLI shape, because the host model is already the worker.
- Self-iteration: gm-new runs on itself. The project .mcp.json starts tools/supervise.mjs with --runs runs/self and task tasks/self.md. Each server start gets its own run directory under runs/self. A run resumes only with an explicit --resume <run-id>. finish closes only that run, and a later session starts a new one. The skill and the self-task say the same. The step budget is 100000, which is correct for a shared project run. The gm agent decided this on the user's instruction (2026-11-01). The user approves the server once, in /mcp, the first time Claude Code opens the project, and nothing in gm-new can grant that. ccbridge sessions do not read project .mcp.json. gm-new writes nothing into any host's global config. The project .mcp.json is the only registration, and it lives in the repo.
- Hot reload: tools/relay.mjs holds the host connection and runs tools/supervise.mjs, which runs the worker as a child (see the relay bullet below). A change under src/ or skills/ holds new host requests, waits for calls in flight, pauses the worker with SIGTERM, starts a new one on the same run, and resumes the run from its log. A call still running is never interrupted or answered with an error: the restart waits until its result is logged. Background jobs stop at a restart, and each stop is logged. A broken source is reported, and the next good change recovers. It registers nothing in any config. Reason: the user asked for hot reload while the worker runs.
- Hot reload, decided and witnessed (gm agent, 2026-11-01): the project .mcp.json runs the host-facing relay, which runs the supervisor and the worker, so a running session reloads on a source change.
- Relay, so the supervisor can be replaced without a reconnect (user request, 2026-11-01): `tools/relay.mjs` is the only file the host runs, and it holds the host's stdio and never changes in normal work. It runs `tools/supervise.mjs` as a child. A change to `tools/supervise.mjs` swaps the supervisor: the relay refuses a file with a syntax error and keeps the running supervisor, otherwise it holds new host lines, waits for every request it sent to be answered, stops the supervisor with SIGTERM, and starts a new one on the same run. The supervisor pauses the worker on SIGTERM, so the run stays open, and the new supervisor restarts the worker with the reason `changed: supervise.mjs`. A supervisor that dies is replaced by the relay after a backoff (1 s, doubling to 30 s), and each call it had taken is answered with the failure text. The host sees one `notifications/tools/list_changed` notice per swap, and no disconnect. Reconnect needed: once, to move the project's `.mcp.json` from `tools/supervise.mjs` to `tools/relay.mjs`. After that, only a change to `tools/relay.mjs` or `.mcp.json` needs one. Reason: the user asked for no further reconnects while the worker is developed.
- Crash rules, decided with the relay (2026-11-01): a crash that the supervisor can catch (an uncaught exception or rejection) pauses the worker before it exits, so the run stays open. A SIGKILL of the supervisor cannot be caught by it, so the worker catches it instead: the worker runs with `--supervised yes`, and the end of its stdin pauses the run, and the next start resumes it. Before this fix a SIGKILL closed the run; the crash witness `crash-1793563150633` below shows that old behaviour and is superseded.
- Supervisor exit pauses, never closes (gm agent defect report, 2026-11-01): the old supervisor's SIGTERM ended the worker's stdin, which closed run `2026-11-01-19-50-16-6b638b` at seq 233 (inFlight 0, last result seq 231, commit 5d90f25, already pushed). Now every exit of `tools/supervise.mjs` (SIGTERM, SIGINT, the end of its stdin) pauses the worker with SIGTERM and waits for it to exit before the supervisor exits, and the worker pauses on the end of its stdin when it runs supervised. Witness, scripted (`/tmp/gm-scratch/gm-new/pause-fix/run-1793563965152/run`, driver `drive.mjs` beside it): three supervisor lives on one run. Life 1 ended with SIGTERM (paused at seq 5, reason SIGTERM from the supervisor), life 2 with SIGKILL (paused at seq 10, reason the supervisor ended stdin), life 3 with the end of stdin (paused at seq 15). Each life ended with a paused event and no end event, and each next life resumed the same run (restart at seq 6 and 11). The run has no end event at the end. A pause kills the worker's shell and job groups first, then waits for the calls to settle, so a pause orphans no shell. Before the change, a SIGKILL after the 5 s pause left a `sleep` running, found after the catchable-crash test.

The second session took its first step, unaffected by the first run's finish.
- Replacement principle: gm-new changes anything that can be changed or improved. No design choice is kept because gm made it. Each inherited choice is re-decided on evidence, and gm-derived plumbing is removed rather than adapted. Reason: the user's instruction (2026-11-01), that gm-new exists to change everything, not to bear the weight of gm's decisions.
- Independence from gm: gm-new does not use gm. Its code, skill, MCP server, runner, tests and builds use no gm MCP tool, no gm skill, no gm runner and no gm state. gm is the comparison target for arm B only, and the arm B configuration in the removed live runner is comparison tooling. Reason: gm-new replaces gm, so it must not depend on it (the user's instruction, 2026-11-01). Earlier builder briefs that named the gm MCP for code search are superseded.
- Model: gm-new makes no API calls. In MCP mode the host session is the model. The CLI has one model, `scripted`, which is offline and deterministic. Reason: a project decision (2026-11-01), taken on the user's instruction that gm-new is an MCP tool and does not interact with any API. No API key is needed, because interactive Claude Code runs on OAuth. Anything that would call an API is reported to the gm agent to do, not done here.
- Anthropic adapter: removed. gm-new holds no API key and sends no Messages API request, so the earlier decisions (the default model, the key from `ANTHROPIC_API_KEY`, the fetch adapter) are superseded. Reason: a project decision (2026-11-01), taken on the user's instruction that gm-new is an MCP tool. Spend belongs to the host session on the Claude Code login, not to gm-new.
- Context: no summarisation. `next_context` returns the rules, the task, the witness requirement, the events new since the last step in full, the seen events as compact records within two horizons (H1 = 14 and H2 = 12 events), and `prefixSha`; `query_log` reaches every event. Decided 2026-11-02 as the owner's request, approved by gm; see "Feed compaction". Reason: the log stays complete, so no lossy summary can drop a fact, and each event is transferred in full once.
- Governance: `rules.md` in the run directory is re-read at every step, placed first in the prompt and never compacted. Reason: rules that a summary drops are violated (finding 3).
- Tools (MCP): `next_context`, `read_file`, `write_file`, `list_dir`, `run_shell` (60 s default timeout), `job_start` (detached shell job), `job_status` (state, exit code and output tail, with a bounded `waitMs` poll), `query_log`, `finish` (needs a witness). The server writes every event to the log, and the host model calls `next_context` each step. The server answers concurrent requests: it reads stdin without blocking and replies by JSON-RPC id, so the host's parallel tool calls run in parallel and the server measures them. Reason: owner decision (2026-11-01). Each tool is one plannable step (finding 4), and background jobs let shell work overlap other actions (item 2).
- Kernel and phase plan (gm agent, 2026-11-02, decided by the gm agent, recorded here). The kernel comes from the gm agent's inventory of gm's 193 verbs: filesystem (read_file, write_file, edit_file, list_dir, stat_file), exec (run_shell and the job verbs; no language stem, since this Node project runs node through run_shell), git (the 11 verbs through the host git binary, with explicit paths for commit and add), ci_status (through gh api), and row tracking (prd_* and unknown_*). Dropped, plumbing only: the spool, leases, the FSM as data, the wasm sideload and sibling registry, install and skill serving, the hourly self-update, Dream-RSI, config sync over git, writer locks, and the witness ledger. Rows are files in `work/rows/<id>.yml`, and a row resolves with a witness of a seq in this run's log plus a commit that exists in the repository. Zero dependencies stays. The embedder and the vector store are dropped. The gh CLI stays as an external tool, because git push authentication and CI need it; it is not a gm component. Search is phase 2: BM25 over tracked files with no embedder, plus literal, regex and whole-word modes. callers and impact parse with acorn 8.18.0, decided by the joint decision of 2026-11-02 (see Dependency rule, joint decision). Phase 3 runs the project's tests and checks through run_shell, each with a witness, and no test files are written. Phase 4 (fetch, then browser over CDP) is optional. The gate for done: gm-new edits a small real change to itself through its own tools, in a live Claude session through airc, the commit goes through its own git verbs, and CI passes. ## Stopped background fetch: native-ahead row (2026-11-04)

The "log event kinds" row differed by one code-call, from the "run_code background" scenario, not from the lint scenario. The body runs `gm.read_file` and then `gm.fetch` to a server that never answers, and `finish` with stopBackground kills it. Native's fetch runs curl, which the body owns (`OwnerScope` in native/components/mcp/server.cpp and `proc::kill_owned` in `stop_locked`), so the stop kills curl, the fetch returns "curl exited 137", and its code-call is logged after the job-killed event. Node's fetch is in-process with only an `AbortSignal.timeout` (src/fetch.mjs), and `killBody` (src/exec.mjs) kills shells only, so the stop never reaches it and no code-call is logged before end. Node's run_shell in the same body is killed and logged in both trees.

Decision: native-ahead, recorded in native/tests/parity/run.mjs (`NATIVE_AHEAD`, the code-call count and the first-divergence index). Native's behaviour is the deliberate one: a stopped body leaves no network request running and its code-call carries the real outcome. Node leaves the request running until its 60 s timeout, and its code-call would then land after the run has ended. Node is not changed here (it is the reference). If the owner wants Node to match, the Node change is to abort fetch on a body stop, and the row is then removed.

## Auto-update (2026-11-05)

- Release contract: the manifest at the `latest` release of AnEntrypoint/gm, one archive per target, checked against its sha256 and size before anything is replaced. `gmnew update` runs one check and prints one JSON line. The build version is the CMake cache value GMNEW_VERSION (default `dev`), shown by `gmnew --version`. serverInfo.version keeps the MCP package version already set, so it is not changed. A dev build never updates by itself. `GMNEW_AUTO_UPDATE=0` turns the background check off; `GMNEW_UPDATE_URL` replaces the manifest URL (tests use file://).
- Swap: the archive unpacks into `.gmnew-staging` inside the install directory, and the replaced items move to `.gmnew-previous`. Every step is a rename that is recorded and undone in reverse when a later step fails, so a failed swap leaves the installed build as it was. On POSIX the executable and the leaves, skills and defaults directories are renamed in place. On Windows the running gmnew.exe is renamed to gmnew.exe.old, and gmnew.exe.old is deleted at the next start.
- Relay: a background thread checks at start and then every 6 hours, and never blocks a request. A staged build restarts the worker through the existing binary-change restart. On POSIX the relay then re-executes itself with the same argv and stdio once no request is in flight. The host connection survives the exec because the file descriptors are inherited. The initialize params travel as `--handshake`, and the run directory as `--run-dir`. Stdin is read with poll and read, and the exec waits for an empty input buffer, so no bytes are lost at the exec point.
- Windows trade-off: the relay process keeps the build it started with until the host restarts it, because a running image cannot be replaced over its live stdio connection. The worker runs the new gmnew.exe from its next start, and the leaves, skills and defaults directories are read by that worker too. The relay binary therefore changes only on a host restart, which is the rarely-changing relay the release contract asks for.
- Failure is silent and safe. No network, a bad sha256, a size mismatch or a failed unpack leaves the installed build untouched and writes one line to the relay log (stderr, which the host captures). It does not write to the run log, because the worker is that log's only writer and a second writer would break its sequence numbers.
- Install layout: a leaves, skills or defaults directory next to the executable takes precedence over the source tree. A dev build in build/ has none, so it keeps using the source tree.
