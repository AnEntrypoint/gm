# gm-new design directions

This note turns the evidence in `research/deep-research.md` into design directions. Each direction is marked as confirmed by the evidence, or as a hypothesis gm-new must test on its own workload before it becomes a design rule.

## Decided

- Scope: a fresh worker that replaces gm's loop, not a fork of gm. Reason: one worker, one log and one loop is the simplest design the evidence supports.
- Language: Node.js 20+ ES modules. Dependencies: one pinned runtime dependency, acorn 8.18.0. No native code and no submodules. Any further dependency needs a measured gain in turns or accuracy, and a measured memory cost per worker, recorded here first. Decided 2026-11-02 as the joint decision of the owner and the orchestrator, which replaced the zero-dependency rule; see "Dependency rule, joint decision" below. The orchestrator rejected the agent's earlier change, which had added thorns and node:sqlite and raised Node to 22.5, and that change is reverted by the commit that records this rule. Reason: acorn is small and has no native code, and it gives exact call sites, which cuts the turns spent verifying callers and impact.
- Shape: gm-new is an MCP server (stdio, JSON-RPC written by hand with Node built-ins, no network listener) plus a skill at `skills/gm/SKILL.md`. The Claude Code session is the model. The CLI is a thin wrapper for scripted witnesses. Reason: owner decision, relayed by the gm agent (2026-11-01). It supersedes the earlier single-CLI shape, because the host model is already the worker.
- Self-iteration: gm-new runs on itself. The project .mcp.json starts tools/supervise.mjs with --runs runs/self and task tasks/self.md. Each server start gets its own run directory under runs/self. A run resumes only with an explicit --resume <run-id>. finish closes only that run, and a later session starts a new one. The skill and the self-task say the same. The step budget is 100000, which is correct for a shared project run. The gm agent decided this on the user's instruction (2026-11-01). The user approves the server once, in /mcp, the first time Claude Code opens the project, and nothing in gm-new can grant that. ccbridge sessions do not read project .mcp.json. gm-new writes nothing into any host's global config. The project .mcp.json is the only registration, and it lives in the repo.
- Hot reload: tools/relay.mjs holds the host connection and runs tools/supervise.mjs, which runs the worker as a child (see the relay bullet below). A change under src/ or skills/ holds new host requests, waits for calls in flight, pauses the worker with SIGTERM, starts a new one on the same run, and resumes the run from its log. A call still running is never interrupted or answered with an error: the restart waits until its result is logged. Background jobs stop at a restart, and each stop is logged. A broken source is reported, and the next good change recovers. It registers nothing in any config. Reason: the user asked for hot reload while the worker runs.
- Hot reload, decided and witnessed (gm agent, 2026-11-01): the project .mcp.json runs the host-facing relay, which runs the supervisor and the worker, so a running session reloads on a source change.
- Relay, so the supervisor can be replaced without a reconnect (user request, 2026-11-01): `tools/relay.mjs` is the only file the host runs, and it holds the host's stdio and never changes in normal work. It runs `tools/supervise.mjs` as a child. A change to `tools/supervise.mjs` swaps the supervisor: the relay refuses a file with a syntax error and keeps the running supervisor, otherwise it holds new host lines, waits for every request it sent to be answered, stops the supervisor with SIGTERM, and starts a new one on the same run. The supervisor pauses the worker on SIGTERM, so the run stays open, and the new supervisor restarts the worker with the reason `changed: supervise.mjs`. A supervisor that dies is replaced by the relay after a backoff (1 s, doubling to 30 s), and each call it had taken is answered with the failure text. The host sees one `notifications/tools/list_changed` notice per swap, and no disconnect. Reconnect needed: once, to move the project's `.mcp.json` from `tools/supervise.mjs` to `tools/relay.mjs`. After that, only a change to `tools/relay.mjs` or `.mcp.json` needs one. Reason: the user asked for no further reconnects while the worker is developed.
- Crash rules, decided with the relay (2026-11-01): a crash that the supervisor can catch (an uncaught exception or rejection) pauses the worker before it exits, so the run stays open. A SIGKILL of the supervisor cannot be caught by it, so the worker catches it instead: the worker runs with `--supervised yes`, and the end of its stdin pauses the run, and the next start resumes it. Before this fix a SIGKILL closed the run; the crash witness `crash-1793563150633` below shows that old behaviour and is superseded.
- Supervisor exit pauses, never closes (gm agent defect report, 2026-11-01): the old supervisor's SIGTERM ended the worker's stdin, which closed run `2026-11-01-19-50-16-6b638b` at seq 233 (inFlight 0, last result seq 231, commit 5d90f25, already pushed). Now every exit of `tools/supervise.mjs` (SIGTERM, SIGINT, the end of its stdin) pauses the worker with SIGTERM and waits for it to exit before the supervisor exits, and the worker pauses on the end of its stdin when it runs supervised. Witness, scripted (`/tmp/gm-scratch/gm-new/pause-fix/run-1793563965152/run`, driver `drive.mjs` beside it): three supervisor lives on one run. Life 1 ended with SIGTERM (paused at seq 5, reason SIGTERM from the supervisor), life 2 with SIGKILL (paused at seq 10, reason the supervisor ended stdin), life 3 with the end of stdin (paused at seq 15). Each life ended with a paused event and no end event, and each next life resumed the same run (restart at seq 6 and 11). The run has no end event at the end. A pause kills the worker's shell and job groups first, then waits for the calls to settle, so a pause orphans no shell. Before the change, a SIGKILL after the 5 s pause left a `sleep` running, found after the catchable-crash test.
- Relay witnesses (scripted, copies of the tree under `/tmp/gm-scratch/gm-new/hmr2`, drivers `drive.mjs`, `drive-throw.mjs`, `drive-crash.mjs`): `run-1793563317775` (a 3 s `run_shell` in flight at the swap was answered ok before the swap; two `restart` events with reason `changed: supervise.mjs`, one `notifications/tools/list_changed` notice per swap; a syntax-broken edit was refused with the old supervisor still answering; the restored file swapped again; the relay pid and stdio stayed up and the relay exited 0 after stdin ended). `throw-1793563286672` (an injected throw while a `run_shell` ran: the call settled with signal SIGTERM, the run has `paused` then `restart` with reason `retry after a failed start`, one run, and no orphan `sleep`). `crash-1793563150633` (SIGKILL of the supervisor: the call got the failure text, the retry started, and the run closed as the known limit above). Each server start gets its own run, and finish closes only its run. Witness: two sessions in a row, runs 2026-11-01-18-14-03-4867a3 (closed when its stdin ended) and 2026-11-01-18-14-03-8d72d4 (finished). The second session took its first step, unaffected by the first run's finish.
- Replacement principle: gm-new changes anything that can be changed or improved. No design choice is kept because gm made it. Each inherited choice is re-decided on evidence, and gm-derived plumbing is removed rather than adapted. Reason: the user's instruction (2026-11-01), that gm-new exists to change everything, not to bear the weight of gm's decisions.
- Independence from gm: gm-new does not use gm. Its code, skill, MCP server, runner, tests and builds use no gm MCP tool, no gm skill, no gm runner and no gm state. gm is the comparison target for arm B only, and the arm B configuration in the removed live runner is comparison tooling. Reason: gm-new replaces gm, so it must not depend on it (the user's instruction, 2026-11-01). Earlier builder briefs that named the gm MCP for code search are superseded.
- Model: gm-new makes no API calls. In MCP mode the host session is the model. The CLI has one model, `scripted`, which is offline and deterministic. Reason: a project decision (2026-11-01), taken on the user's instruction that gm-new is an MCP tool and does not interact with any API. No API key is needed, because interactive Claude Code runs on OAuth. Anything that would call an API is reported to the gm agent to do, not done here.
- Anthropic adapter: removed. gm-new holds no API key and sends no Messages API request, so the earlier decisions (the default model, the key from `ANTHROPIC_API_KEY`, the fetch adapter) are superseded. Reason: a project decision (2026-11-01), taken on the user's instruction that gm-new is an MCP tool. Spend belongs to the host session on the Claude Code login, not to gm-new.
- Context: no summarisation. `next_context` returns the rules, the task, the witness requirement, the events new since the last step in full, the seen events as compact records within two horizons (H1 = 14 and H2 = 12 events), and `prefixSha`; `query_log` reaches every event. Decided 2026-11-02 as the owner's request, approved by gm; see "Feed compaction". Reason: the log stays complete, so no lossy summary can drop a fact, and each event is transferred in full once.
- Governance: `rules.md` in the run directory is re-read at every step, placed first in the prompt and never compacted. Reason: rules that a summary drops are violated (finding 3).
- Tools (MCP): `next_context`, `read_file`, `write_file`, `list_dir`, `run_shell` (60 s default timeout), `job_start` (detached shell job), `job_status` (state, exit code and output tail, with a bounded `waitMs` poll), `query_log`, `finish` (needs a witness). The server writes every event to the log, and the host model calls `next_context` each step. The server answers concurrent requests: it reads stdin without blocking and replies by JSON-RPC id, so the host's parallel tool calls run in parallel and the server measures them. Reason: owner decision (2026-11-01). Each tool is one plannable step (finding 4), and background jobs let shell work overlap other actions (item 2).
- Kernel and phase plan (gm agent, 2026-11-02, decided by the gm agent, recorded here). The kernel comes from the gm agent's inventory of gm's 193 verbs: filesystem (read_file, write_file, edit_file, list_dir, stat_file), exec (run_shell and the job verbs; no language stem, since this Node project runs node through run_shell), git (the 11 verbs through the host git binary, with explicit paths for commit and add), ci_status (through gh api), and row tracking (prd_* and unknown_*). Dropped, plumbing only: the spool, leases, the FSM as data, the wasm sideload and sibling registry, install and skill serving, the hourly self-update, Dream-RSI, config sync over git, writer locks, and the witness ledger. Rows are files in `work/rows/<id>.yml`, and a row resolves with a witness of a seq in this run's log plus a commit that exists in the repository. Zero dependencies stays. The embedder and the vector store are dropped. The gh CLI stays as an external tool, because git push authentication and CI need it; it is not a gm component. Search is phase 2: BM25 over tracked files with no embedder, plus literal, regex and whole-word modes. callers and impact parse with acorn 8.18.0, decided by the joint decision of 2026-11-02 (see Dependency rule, joint decision). Phase 3 runs the project's tests and checks through run_shell, each with a witness, and no test files are written. Phase 4 (fetch, then browser over CDP) is optional. The gate for done: gm-new edits a small real change to itself through its own tools, in a live Claude session through airc, the commit goes through its own git verbs, and CI passes. Only after the gate do the gm dependencies come out, each removal in its own commit. The CLI prompt lists the original verbs only; the kernel verbs run in both modes, and the MCP tool list describes them to the model.
- Search (phase 2, gm agent 2026-11-02): `search` ranks the lines of git-tracked text files by BM25 (k1 1.2, b 0.75), and an identifier also matches its camelCase or snake_case parts. `grep` finds text by literal (default), regex, or word (a whole identifier), with optional ignoreCase and limit. Both are read-only and need no path, so they run beside writes; a result can show a file as it was just before a concurrent write. Files are read only if they are tracked, not symlinks, inside the workspace, text (no NUL in the first 8000 bytes), and at most 1 MB; each file is re-read only when its mtime or size changes. Known limits: a regex runs without a timeout, so a pattern with catastrophic backtracking blocks the server (patterns are capped at 200 characters); BM25 can rank a call site above the definition of a symbol that both lines contain; a workspace that is not a git repository is refused. callers and impact parse with acorn 8.18.0 (joint decision, 2026-11-02). Reason: the gm agent's phase plan (2026-11-02), phase 2.

- Wait for a job (brief change 4, gm agent 2026-11-01): a 3-second job, measured two ways in scripted drivers (`/tmp/gmnc/poll/drive.mjs`, run `/tmp/gmnc/poll/runs/poll`). Bounded polling, one job_status call with waitMs 500 repeated until the job leaves running: 6 calls, and the final reply came 9.5 ms after the job ended. One long wait, one job_status call with waitMs 30000: 1 call, and the reply came 0.2 ms after the job ended. The extra latency of polling is 9.3 ms, under the 100 ms threshold, so the default is the one long wait, which uses fewer calls. A job that runs past 30000 ms needs a second call.
- Tool list hash (brief change 7, gm agent 2026-11-01): each start logs a `tools` event with the sha256 of the served tool list. A resumed run whose last `tools` hash differs logs `tools-changed` with `old` and `new`. A changed description invalidates the host's prompt cache (documented), so tool descriptions stay stable unless a change is needed. The worker does not see the host's cache usage, so the usage fields stay in the host transcript, as recorded earlier, and the log does not claim a saving.
- Retry after a failed restart (gm agent decision, 2026-11-01): a failed restart retries by itself, starting at 1 s and doubling to a 30 s cap, and it needs no source change. A call that arrives while the restart is failed is answered at once with the failure text, and a held call is answered the same way. Witness, a scripted test with a fresh run directory `/tmp/gm-scratch/gm-new/supervisor-retry/run-1793559709334`: the flag was set and one source change broke the restart. A call during the failure was answered with the failure text in 1 ms. The retries ran at 1000, 2000, 4000 and 8000 ms with no source change. The flag was then cleared, which is not a source change, and the restart recovered after 5033 ms, with 10 error replies on the way. The live server runs the old supervisor until the owner reconnects it, so this scripted test is the witness.
- Restart and pause (brief changes 1 and 2, gm agent 2026-11-01): a restart waits for every call in flight to have its result logged. The 30-second error is gone, and no call is answered with a restart error, so the host does not repeat a call that is still running. The supervisor pauses the worker with SIGTERM. The worker writes a `paused` event, stops its jobs, and exits, and the supervisor sends SIGKILL after 5 seconds. Closing stdin is not part of the pause, because it would end the run as closed, and a closed run stays closed. A repeated tools/call request id is answered from the first reply and logged as a `duplicate`, never run again. Reason: the gm agent's research brief, with Claude Code's default tool timeout of about 28 hours.
- Output pages (brief change 3, gm agent 2026-11-01): `read_file` returns one page of at most 20000 characters, from `offset` (default 0) with `limit` (default 20000). Its result carries `total` (characters in the file), `offset` and `next`, the offset of the next page, or null at the end. `grep` takes `offset` over matches and stops a page at 20000 characters of output. Its footer reads "showing A to B; next offset N". `job_status` with `offset` returns one page of the job output, with `next`. Without `offset` it keeps the 2000-character tail. Offsets count JavaScript characters (UTF-16 units). Reason: the gm agent's brief, so one result cannot flood a context window.
- Callers and impact [row unknown-parser-decision] (item 3, gm agent 2026-11-01, zero dependencies): `callers` lists the call sites of an identifier in tracked .js, .mjs, .cjs and .ts files, by regex over each line. A call is the name followed by an open parenthesis and not a property access. A member call is `.name(`. A definition line (function, class, const/let/var, or a method shorthand) is excluded and marks its file as defining the name. A call in a file that imports a defining file is marked linked. `impact` lists the defining files, the files that call the name, and the importers of those, out to depth levels (default 2, max 5). Import edges come from a regex over `from`, `import(`, `require(` and `import` specifiers, resolved inside the repo only. Every answer says approximate. Known limits, stated in each answer: dynamic calls, re-exports and shadowed names are not resolved, and a line that starts with a comment marker is skipped. A string that contains `name(` is still counted. Reason: the gm agent's decision for zero dependencies (2026-11-01). Item 5 of the brief measures this regex against an acorn oracle.
- Fetch (item 2, gm agent 2026-11-01): `fetch` is an HTTP GET of one http or https URL through Node's built-in fetch, with no body, no cookies and no credentials. Redirects are followed by hand and capped (`maxRedirects`, default 5, up to 10). The timeout covers the headers and the body (`timeoutMs`, default 15000, up to 60000). The body is read up to `maxBytes` (default 2000000, up to 20000000), and `truncated` says when the cap cut it. HTML is reduced to text, and script, style, noscript and comments are dropped before the tags are removed. The result carries status, bytes, finalUrl, redirects and truncated, and a non-2xx status is reported as data, not as an error. Known limit: nothing blocks localhost or private-network addresses, so a fetch can reach services on the worker's host or LAN. The text is untrusted input, and the model must treat it as data. Reason: the gm agent's item 2 (2026-11-01).
- Commit gate (owner decision, relayed by the gm agent, 2026-11-01): there is no CI, and the quality checks run inside the git_commit verb on every commit. Four checks run before the commit, and a failed check refuses it. `syntax` parses every tracked module with node --check. `ascii` finds non-ASCII text in every tracked text file. `docs` requires every repo path that DESIGN.md, AGENTS.md or README.md names in backticks to exist in the index, and every KEEP path to exist on disk. A path counts as a repo path when its first segment is a top-level name in the index. Runtime directories, placeholders, URLs, method names and absolute paths are not checked. `smoke` runs the CLI on a scripted task, which must finish, and a negative control with one step, which must stop at max_steps. Each check reports its result and time in the git_commit result event. No test files and no test directory exist. Reason: the owner's no-test rule, applied to the commit path.
- Gaps, recorded not hidden (gm agent decision, 2026-11-01, from arXiv 2609.02749, Sec. 3.2: "any gap that survives the checks is recorded ... rather than hidden"): every `git_commit` result and its `commit` event carry `notCovered`, a fixed list of what the gate does not check: the semantic correctness of the change, behaviour the smoke run does not exercise, doc content beyond path existence, and CI (none configured). A refused commit carries it too. `finish` takes an optional `gaps` array, logged in the `end` event with the witness, which is still required. A bad `gaps` value is refused and the run stays open. Witness: finish, scripted (`/tmp/gm-scratch/gm-new/gaps/run-1793563683727/run`): a `gaps` array with a number in it was refused with a `refusal` event, the run stayed open, and the next finish logged `gaps` with its two strings in the end event. The commit witness is the commit that adds this line: its `git_commit` result carries `notCovered`, and its `commit` event is in the live run log. The tool list hash changes, as expected.
- Long-horizon rules (gm agent decisions, 2026-11-01, from the DeepSeek superagent prototype's documents 003-execution.md, 007-architecture.md and 000-philosophy.md in dsh-superagent-prototype). Grade: documented design from a research prototype, not measured, and untested on our workload. (1) Recovery note: a run that resumes after a restart carries a recovery note in the next next_context. It names the last seq and each action that started and has no end event, with its tool and arguments, and it asks the model to verify outside effects (git log, git status, the remote, the row files) before repeating a push, a commit, a fetch that posted, or a row resolve. (2) Persisted request ids: each action records its request id, and at startup the worker rebuilds the duplicate map from the log, so a repeated id is answered from the log and never run again. An action with no end event was interrupted, and its repeat gets an error that asks for the outside effects to be checked. (3) Background job lifetime: a job is killed after 30 minutes by default (flag `--job-lifetime-ms`). The kill is logged as its own `job-killed` event with the output tail, and the next next_context names it. (4) Log growth: the log stays complete, and nothing is deleted. The measured growth and query cost are in Measured.
- Background jobs keep state in `runs/<id>/jobs/<job>.json` (written by rename) and output in `<job>.out`. A job still running at run end is killed and awaited, and its end is logged as a `job` event. Reason: status is readable by any process, and no child outlives the run.
- Path confinement covers the file tools only: `read_file`, `write_file` and `list_dir`. Paths stay inside the workspace, a `..` segment is refused, and a symlink that leaves the workspace is refused, including a dangling one (checked with `lstat` in `nearestExisting`). Refusals are logged as `refusal` events and not thrown. `run_shell` is not confined, and doctor says so. Known limit: a shell command can create a hard link to a file outside the workspace, and the path checks do not see it. A path check does not close this, because a shell can do anything the user can. Reason: an escape attempt through the file tools shows up in the log, and path checks cannot confine a shell (gm agent, 2026-11-01).
- Loop: plan, act, observe, repeat. Each reply is one JSON action or an array of actions; actions that touch no common path run together in one wave with `Promise.all`, and a shell command, `query_log`, `finish` or unknown tool runs alone. Every reply, action and result is appended to the log with monotonic times. Stops on `finish` or at `maxSteps` (default 50). An unparseable reply counts as one step. Reason: work item 1 needs multi-action replies, and the wave rule keeps the log replayable.
- Wave planning uses real paths, not lexical ones. An existing path uses `realpath`; a new file uses the `realpath` of its parent plus its basename. Existing files are grouped by dev and ino, so hard links serialise. Writes that share a group go in one serial wave. Reason: a symlink alias or hard link to a file written in the same reply would race under `Promise.all` (found by the item 5 witness).
- Storage: `runs/<run-id>/` holds `log.jsonl` (append-only), `rules.md` and `task.json`, and `runs/` is git-ignored. Reason: runtime state is never tracked.
- Remote: `AnEntrypoint/gm-new`, branch `main`, pushed by the single writer after each committed item. Reason: the standing owner instruction says to push AnEntrypoint work, and the owner asked for this repository (2026-11-01). The repository stays private; making it public is the owner's decision.

- Orphans: a background job and a foreground shell command run in their own process group (detached spawn). A job kill, a foreground timeout and the run end kill the group: `kill(-pid)` on POSIX, `taskkill /T /F` on Windows. An interrupt (SIGINT or SIGTERM) on the CLI kills every group at once with SIGKILL, then exits, so no new call starts while the process goes down.

Reason: a host should not lose a step's context for the length of a shell. Owner decision via the gm agent (2026-11-01). Witness: `/tmp/gmnc/keep/run`. The next_context reply (seq 4) comes before the 3 s run_shell result (seq 5), at 206 ms against 3129 ms.

Background work goes through `job_start`, or in the CLI `run_shell` with `background` true and a job name. The rule is in the run_shell tool description. Reason: no child outlives the run, and a grandchild that outlives its foreground call breaks that rule. Owner decision via the gm agent (2026-11-01). Witness: run `2026-11-01-12-02-53-e4e69d`, where `sleep 47 &` was gone when the call returned.

- MCP queue: MCP mode queues calls by real path, with the same realpath and dev:ino grouping as wave planning. Two calls that touch one file, with at least one write, run in order. A shell call runs alone. Reads of distinct paths may run together. Reason: a host burst can write one file twice, which is silent data loss, and option (b), accepting the race, would leave that case known. Owner decision (2026-11-01).

- Steps: each `next_context` call is one step. The run summary reports `contextCalls` with the same value. The harness uses wall time and idleMs as its primary measures, and step count as a secondary one. Reason: one explicit definition of a step, and the primary measures are the ones concurrency changes. Owner decision (2026-11-01).

Both modes render the tool list with `renderTools` and hash the same way, since the API caches tools with their schemas ahead of the system text, so the schemas are part of the stable prefix. Wall time runs from the prompt record to the first end_turn. Tool time is the union of tool_use to tool_result intervals. Reason: both arms are measured by the same code, from the transcript timestamps, not from our own clocks. Owner decision via the gm agent (2026-11-01).

## Simplicity rule

Start with one worker, one log and one loop. Add a component only when a measured run shows the current design failing. This follows the Anthropic harness guidance (low confidence, dated) and the single-agent baseline result (medium confidence).

## Directions

1. **Complete log, queried by code (hypothesis).** Every observation, action and outcome is appended to one log. Recall runs code over the log, not a summary. Evidence: finding 1 (medium). Unknown: log growth and retrieval cost. Test: the same long task run with a log-query worker and a compacting worker, with cost measured.

2. **Validated compaction, only when the log is too big to query (hypothesis).** If compaction is needed, check each summary against the next k steps before using it. Evidence: finding 2 (medium, self-reported, one replication dispute). Test: summary accepted or rejected by a judge on gm's own traces, compared against no validation.

3. **Governance rules outside the compactor (hypothesis, risk confirmed, fix untested).** Rules that must hold for the whole run are kept in a file that every step re-reads, so they cannot be summarised away. Evidence: finding 3 supports the risk (medium, observational). The Constraint Pinning remedy was refuted 0-3, so this direction is not evidence-backed. Test: a rule set of gm's kind, violation rate with and without re-injection.

4. **Context operations as worker actions (hypothesis).** Compaction and log queries are actions the worker plans, like file edits and commands. Evidence: finding 4 (medium). The 57.6% result is one run against same-family baselines, below frontier models, so it is not evidence that the design is best.

5. **Summariser trained with the worker (out of scope for now).** Finding 5 (medium) needs training infrastructure gm-new does not have. Keep it as a later option, not a day-one design.

6. **Measure one worker before fanning out (confirmed in direction, threshold unusable).** Finding 6 (medium) supports measuring a single-worker baseline before adding parallel workers. The saturation threshold (finding 7, low) must not be used as a constant (94% and 45% are unverified).

7. **Subagent isolation (open).** [row unknown-subagent-isolation] The claim that isolated subagents help was refuted 1-2. Parallel subagents stay in gm-new only where a measured run shows they beat one worker on the same task.
8. **Proactive mode (future, not built).** [row unknown-future-directions] The agent watches a repo with no task. Source: the DeepSeek prototype README (github.com/deepseek-ai/dsh-superagent-prototype), checked against the primary sources in research run wf_261fe87f-4c6. It describes a proactive coding agent for one repository, and the article's designs for it are unimplemented. gm-new is task-driven, so this is a future direction with no evidence here.
9. **Verification-gated admission (future, not built).** [row unknown-future-directions] If gm-new learns from its runs, an item is admitted only after a check, and the gaps the check did not cover are recorded, not hidden. Source: arXiv 2609.02749 (Repo-To-Skill, AREX-Skill), Sec. 3.2: "No skill is admitted on the strength of its sources alone," and "any gap that survives the checks is recorded ... rather than hidden." The gains there are self-reported, from one preprint with no replication. The paper excludes construction from both runtime conditions for MLE-bench and PaperBench; it does not say whether construction is counted for FrontierCS or PassNet.
10. **Matched-budget falsifier (future, not built).** [row unknown-future-directions] Once a learned artifact exists, compare it with and without the artifact, with the same model, the same budget and the same tasks, at least 3 trials per task. Count the construction cost inside the budget. The source paper (arXiv 2609.02749) excludes construction from both runtime conditions for MLE-bench and PaperBench, and does not say whether construction is counted for FrontierCS or PassNet. On FrontierCS, token use rises about 82% (2.46M to 4.47M per task) and tool calls rise from 64.7 to 105.0 (figures as read by the gm agent, 2026-11-01), so a falsifier must count that run cost as well. Trigger: this falsifier is built only when gm-new writes a reusable artifact from its runs. Until then it is not built.
11. **Raw-replay arm (future).** [row unknown-future-directions] When there is something to replay, add an arm that replays the raw log instead of a distilled skill. SkillEvolBench (arXiv 2605.24117) finds raw replay often beats distilled skills. The full log already keeps the raw trajectory (direction 1). Skill distillation is not built: the log is the raw trajectory, and the falsifier in direction 10 is triggered only when gm-new writes a reusable artifact from its runs. SkillEvolBench is cited from the gm agent's reading (2026-11-01).

## Concurrency evidence (digest, research/concurrency.md)

- Parallel tool calls in one turn cut wall-clock 40.6% and cost 35.9% in one self-reported study (medium, arxiv 2602.07359). Use: work item 1, measured in item 7.
- Overlapping tool execution with generation can cut latency (medium, arxiv 2603.18897, serving-system paper). Speculation can hurt under high load: unsupported, because the brief found no support for that claim. Use: default off until measured.
- Fine-grained tool streaming may return invalid JSON tool input. Use: not enabled. The parser already handles unparseable replies.
- Prompt caching: order is tools, system, messages; put the breakpoint at the end of the stable prefix, before the event window. Measured 41 to 80% cost cut and 13 to 31% faster first token (medium, arxiv 2601.06007). Use: rule 5, item 4.
- Rate limits: honour retry-after first, then backoff (high, Anthropic docs). Cached input tokens do not count toward input-tokens-per-minute for most models (high). Use: rule 6, item 3.
- Primary-sourced by the brief (gm agent, 2026-11-01): the minimum cacheable prefix for claude-haiku-5-5 is 512 tokens, cache writes cost 1.25x and 2x (one for each cache TTL), and cache reads cost 0.1x. Still unverified: the back-pressure measurement. No saving is claimed from these until a live usage run measures it.

## Feed compaction (Decided change, 2026-11-02)

The owner asked for the most compact feed the agent can use. Each event should be transferred in full once, when the agent first sees it, and after that only in compact form, within two horizons. gm approved it as a Decided change, with these constraints, which hold: the log stays complete and query_log reaches all of it; replacement records are fixed templates, not summaries, so no model writes them and nothing is trained; the rules are re-read at every step and stay first in the prompt; the witness requirement is unchanged; a replacement record keeps seq, kind, tool, path, bytes changed, exit status, error text, refusal reasons and witness text; output compaction never drops an exit code, an error line, or the first and last lines of a result, and each compacted output records its full size and the seq of the full output; the horizon lengths come from measurement; the compactors are deterministic.

The rule, as built (src/compact.mjs). next_context returns the events after the last feed in full, at most 20 of them. It returns the events already seen as compact records: H1 = 14 events back, then H2 = 12 further back. Older events are not in the feed, and a count `older` says how many. The last feed is read from the log: it is the total on the last next_context result. Each module owns its strategy next to its tool, as a COMPACT export: tools.mjs, search.mjs, fetch.mjs, git.mjs, code-ast.mjs, rows.mjs, wiki-tools.mjs, review-tools.mjs and runcode.mjs. The lifecycle events are in mcp.mjs. The clock fields of a full event (t, mono, inFlight, startMono, durMs) are raw log data, not compactor output; a compact record has none of them.

Two changes the constraints required. (1) A verb called inside run_code was logged as a code-call with its name, ok and durMs only, so its output and exit code were not in the log. query_log could not reach them, and a failed shell call lost its exit code. A code-call now logs its arguments, exit code, signal, output and error. The log grows by those fields. (2) A failed call keeps its output whole up to 60 lines, since a failure's lines are not all marked by an error keyword, and its error lines are marked either way. A failed call with more than 60 lines records the count of the rest, and query_log reaches all of them. This is a gap against the strict constraint: lines beyond 60 of a failing call are not in its record.

## Stuck check and the open-jobs snapshot (agent decision under the owner's delegation, 2026-11-02)

The owner asked that the agent get all progress from every source when it queries, and also the notices about what is still happening, so that it can later tell when something has stuck. Decisions, made by the agent under the owner's delegation:

- A running job is stuck when it has made no progress for stuckMs, default 180000, the same as the run_code budget. Progress is: output written by a shell job (the mtime of its output file); a verb call a body has in flight, or has finished (the body's newest code-call in the log); or the job's start.
- A verb call in flight counts as progress until it returns, so a call that never returns is not flagged. Its own timeout is what bounds it.
- A queued body is waiting for a slot, not stuck. Its clock starts when its thread starts.
- The monitor checks every monitorMs, default 15000. It logs job-stuck once when a job becomes stuck, and job-unstuck once when it progresses again. A job that settles while stuck is not reported unstuck; its end notice is the report.

## Background budget for run_code (2026-11-02)

gm asked that a body never hold the agent for more than a few minutes, and never leave work the agent cannot see. The decisions, one line each with its reason:

- The foreground budget is 180 s by default and timeoutMs is at most 300000: a body must not hold the agent for more than a few minutes (gm).

## Update safety (2026-11-02)

The owner asked for the update check to deploy main into running workers within the hour, and gm asked for two conditions before the hourly update is judged safe. This section supersedes the pull-then-undo rule in the section above: a commit is now checked before the checkout moves to it.

- A commit is checked in a clone of the checkout at that commit. The clone shares the checkout's objects and creates no branch in the checkout. The gate runs there, and the checkout is fast-forwarded only when the gate passes. A commit the gate rejects never reaches the checkout.

When the worker does not start on the new code, the checkout is reset to the commit before the pull, the worker starts on the old code, and the rollback is logged. The wait for the rollback takes only a report that the worker is running, because the supervisor keeps retrying the broken code until the reset, and a failure report from those retries is not the outcome of the rollback.

## Idle trace (2026-11-02, gm request)

The idle wake-ups are V8's memory reducer, a background garbage collector that runs main-thread tasks while the process is idle. Evidence, in scratch under `audit/`:
- A bare Node process that only waits makes no wake-up in 45 seconds (`bare-wait.sh`: 0 switches for a timer, a stdin pipe, and an interval).
- A standalone worker makes 5 wake-ups in 45 seconds by default, and 0 with `--no-memory-reducer` (`worker-idle.sh plain`, `worker-idle.sh no-memory-reducer`).

- The whole stack, traced per thread (`idle-threads.mjs`, runs `trace-now` and `trace-flag`): before, 8 switches a minute on the main thread for each of the relay, the core and the worker. After the worker flag (commit `0d9dd42`), the worker shows 0. The relay shows 0 in this run and 8 in the first, which varies run to run. The core shows 8, because the relay starts it without the flag.
- Rejected: `--no-memory-reducer`. The runtime does not accept the flag through `NODE_OPTIONS`, and `v8.setFlagsFromString` in a preload has no effect (5 switches with it), so the only way to set it is on each process's command line. The flag was added to the worker's start in commit `0d9dd42` and removed again. - The memory measurement above does not contradict that reason. A 30-second idle is too short to show the reducer returning memory, so the measurement shows no saving only within that window.

- Timers in the stack, from the preload trace: the relay's only timer is its shutdown timeout. The core has its shutdown and startup timers and the update check, which is an hourly interval with a first check at 30 seconds (updates off in these traces). The worker has none while idle, since its stuck check now runs only while a job is open.

## Single-worker limit: query_log paging (2026-11-02, owner request, reviewed by the orchestrator)

The owner asked for the single-worker limit to be fixed as far as possible, for subagents and single workers alike. The measured limit was query_log. Each call parsed the whole log and filtered it before it cut the page, so paging a log of N events cost about N squared over the page size. A reply could also go out over its cap: an event larger than the cap was not cut, so runQuery cut the output mid-string and the reply was not valid JSON. The real log had no such event (its largest is 603 characters), but a log that holds earlier query results does, since each result is up to 20000 characters, and paging that log hit both problems.

What changed (src/log.mjs, src/tools.mjs, src/mcp.mjs):
- `take(after, limit, match)` reads the file from the byte offset of the first event after `after`, and stops at `limit` matches. query_log asks for 51 events, so pageOf makes the same page and the same `next` as before: one event past the page says whether more remain.
- pageOf never returns a reply over 20000 characters. An event that does not fit a reply of its own is cut to its head until it fits, so the reply is valid JSON.
- A query_log reply is logged with its first 1000 characters and `outputChars`, its full length, at the top level, inside run_code, and in the scripted run (src/loop.mjs). The events a query reads are logged in full. gm accepted this on that condition (2026-11-02). Reason: a reply is a copy of events already in the log. Logged in full, each query added up to 20 KB, and a reader that pages to the end reads its own copies: each page returns one copy and each query adds two events, so `next` never clears. The reply the agent receives is unchanged. This changes what the log stores for query replies, so it is the part gm should review.
- query_log rejects an `after` that is not a number. Before, any value was compared as it was.

## Subagent handoff (2026-11-02, owner request, reviewed by the orchestrator)

The owner asked for subagent isolation to be fixed as far as possible, once the single worker's limit showed (the section above). The mechanics are built. Whether isolation helps a long-horizon outcome is not measured, and it stays open.

- A child session is a new run with its own run directory, log, feed and context. Isolation is by construction: the child's `next_context` shows only its task and its own events, and its log is separate from the parent's.
- The handle is the child's run id. `next_context` now returns it as `run` (src/mcp.mjs, the reply of `context`). Before, the id was only on stderr, so a child could not name its log to the parent.
- The parent reads the child's result through the CLI, `node src/cli.mjs query --run <id> --js "..."`, and keeps only the witness. The skill section "Handing work to a child session" (skills/gm/SKILL.md) tells a session to do this.
- The workspace is shared. Children and parent can write the same file, and nothing enforces a separate workspace. Collisions are repaired after the fact (see "Collisions: repair after the fact", at the end of this file), and the skill states that policy at every hand-off.

## Reminder carries the open PRD window (2026-11-02, owner request)
