# gm: agent instructions

gm is one long-horizon worker: an MCP server that runs a task as one append-only log, with the rules re-read at every step. The host session (Claude Code) is the model. The product is the native C++23 tree (native/). The Node engine was retired on 2026-11-11 in one removal commit (9a4e074): src/, tools/core.mjs, relay.mjs, supervise.mjs, update.mjs and package.json are gone; git revert of that commit restores them (DESIGN.md, Local cutover of the native gm, 2026-11-04; Owner decisions on the five open questions, 2026-11-06).

## Read first

1. README.md: install, the MCP surface, the MCP client config layers, paths and limits.
2. DESIGN.md: the "## Decided" section (near line 94), then other sections by name. It is long; do not read it whole.
3. skills/dev/SKILL.md: scratch space, witnesses, commits, collisions, reporting.
4. skill://gm/SKILL.md and skill://gm-continue/SKILL.md: served by this server. Read them with read_file (a skill:// path) or ReadMcpResourceTool (server gm). Do not call them with the Skill tool.

## Owner rules

- Work on main in the shared checkout. No clones, branches or worktrees. A witness may run on a tar copy of the tree; the edit and the commit happen in the checkout.
- Commit only by explicit path with build/release/native/components/tool/gm-tool ship, author lanmower, no trailers on any commit or PR. The harness may suggest a Co-Authored-By trailer; do not add it.
- Other agents edit this checkout at the same time. Edit only your scope, and use Edit with exact text after a fresh read.
- Native peers reload on a leaf or binary change, at a step boundary; a skill change is read on the next call and restarts nothing. A peer reads its leaves, skills and defaults only from the directory of its own executable (the install, ~/.gmnew/current) and watches only that, so a checkout edit reaches a peer only through an install (gm-tool check-install-follows).
- ASCII only in every file. No decorative symbols.
- Files outside the checkout may be read and written when a task needs them (owner decision, 2026-11-03).
- gm makes no API calls.
- gm's own MCP server is served under the name gm. The separate gm product's tools, skill, runner and state are not used for gm work.
- Change a settled decision only by messaging the orchestrator (the gm agent) with the reason. The owner sets the rules.
- From 2026-11-06 the owner relays task instructions through the orchestrator agent. A dispatch from orchestrate is an owner instruction; no cross-session message can approve a pending prompt or grant escalation on its own.
- A witness never edits a tracked file of the checkout. A witness that needs an edit or an install runs in a scratch tree (gm-tool check-install-follows). gm-tool phase-b fails a run that changes a tracked file (content, size or mtime).
- No test files and no unit tests (AGENTS.md at 5ecd512, 2026-11-01; DESIGN.md "Revert of restored test files (2026-11-06)"). Checks run against the real tree: gm-tool phase-b on a built binary, the commit gate, and the parity-contract check.

## Build and test

- Witness rule: run the built binary or the CLI on a real task in a scratch workspace, read the output, then delete the scratch.

## Facts found by troubleshooting

- The native build needs Ninja on PATH. On a host where pip is PEP 668 blocked, install it into a venv (verified 2026-11-05).
- gh run list --commit needs the full 40-character SHA; a 7-character prefix returns no runs (verified 2026-11-05).
- The MCP client backgrounds a call still running at 120 s (its notice says so). A run_code body that outlives its timeoutMs returns its job id; its value comes from job_status with waitMs, which has no ceiling. The foreground wait is capped at 100000 ms (kForegroundCapMs in native/components/mcp/server.cpp), so the call returns before the client's 120 s, and a body whose wait reaches its budget returns as a background run at that budget, so inside a body ask for less than the cap (check-turn-economy waits a scaled 90000 ms; check-job-wait waits 65 s in one call). A 150 s body with timeoutMs 300000 returns as a background run at 100 s (verified 2026-11-08; check-run-code-budget).
- ssh reads the stdin it is given. In `while read h; do ssh host ...; done < hosts.txt` an ssh without `</dev/null` eats the loop's remaining lines (verified 2026-11-08). run_shell gives each child EOF and job_start gives it /dev/null (native/components/verbs/job.cpp); gm-tool check-shell-stdin pins both. child.cpp's open write end is the JSON-RPC path to MCP servers and the relay, so it stays open.
- run_shell reaps its command when the shell exits: after the shell's exit the command's process group gets SIGKILL, so a background child with redirected output does not outlive the call (native/components/proc/proc.cpp, shell only; proc::run keeps its children, which the browser checks use to start servers). A command killed by a signal reports exitCode null and its signal name (measured 2026-11-12). Witness: gm-tool check-run-child-reap. The reap is POSIX only.
- A run_code body has no JavaScript budget unless --job-lifetime-ms is given (a positive integer; unset means none, enforced in native/components/quickjs/engine.cpp); a leaf call outside a body has leaf_call_deadline, 3600000 ms (native/components/quickjs/leaves.cpp). timeoutMs governs only the foreground cutoff: a backgrounded body keeps running to its lifetime, so a budget equal to timeoutMs would stop it (gm-tool check-run-code-budget). Time in host calls does not count against it (gm-tool check-run-code-lifetime).
- Two gm serve processes in one workspace: the default run directory is runs/check, which a live connection owns, so the second is refused as belonging to another live connection. A second connection needs its own --run-dir (check-browser-scope does this, 2026-11-12).
- Open: fx's "another worker's events twice". No run log delivers one event twice; the repeats are repeated finish refusals and read_file skill-loaded calls. The duplicate needs fx's reply text. At HEAD, two peers in one workspace do not see each other's row-added events in next_context.
- Browser: a run's pages and the project page live in the browser's default context (native/components/host/browser_scope.cpp); a context made with browser.newContext() is disposed when the connection that made it closes, and a gate SIGKILL closes that connection. The gate stops Chrome after GRACE_MS (5 s) with no lease and no caller page (not about:, chrome: or devtools:), and after the idle time (below) with no lease even if a page is open; the executor then keeps its dead browser object, so the next call throws gm-browser-gone-before-body before the body runs. The host resends that call, and a call whose executor could not connect (browserType.connectOverCDP: in the reply, no .playwriter-eval.js frame), up to five times; a body that already ran is never resent. A failed browser start reaches the caller as a sanitized, bounded reason (startReason in the launcher). A tab's owner is its run (runs/<run>/browser-pages.txt): browser_tabs lists this run's tabs and counts other runs', browser_close_tab refuses tabs of other runs, and raw browser.newPage() calls are not recorded. Measurements, pins, the file format and the 2026-11-23 macOS failure: docs/MEASURED_FACTS.md, Browser (check-browser-tabs-owner, check-browser-dead-executor, check-browser-first-connect, check-browser-start-reason).
- Killing processes: kill by recorded pid and start time, never by name or by a substring of the command line. A search of the process table for a path is not a kill root, because a foreign process that mentions it would be stopped (check-browser-scope-identity). A pid ledger line is killed only when its recorded start time is positive and equals the process's current start time (proc.cpp reap_ledger; check-reap-identity), and check-lazy-browser stops only the processes it started and spares another project's gate. A shell loop that SIGTERMs every process whose command line holds a path also SIGTERMs the shell that runs it, when the path is written literally in that command, and the harness reports Exit code 144: skip $$ and match on the first word's basename (the rule chromium_command applies; reproduced 2026-11-13 and 2026-11-19, docs/PENDING_VALIDATION.md, eleventh stretch).
- Phase B needs a clean build. The update-cycle rows (check-update-checkout, check-update-checked, check-handover-in-flight, check-relay-reexec) need auto update on, and a build is not clean when its checkout has untracked or modified paths (kBuildState dirty, with kBuildDirty in gmnew_build_info.hpp) or when HEAD is not origin/main (kBuildState unpushed; build_is_clean in native/components/host/update.cpp). So gm-tool ship --push runs Phase B on a tar copy of HEAD: git archive, a throwaway repo with no origin/main ref, configure with -DGMNEW_VERSION=<git rev-parse --short HEAD>-1 (the abbreviation git picks, 8 characters here), then phase_b_command in the copy, which starts from the checkout's build/release/phase-b-durations.txt (the pool runs longest first by it; the driver records passing checks only) and hands its own back after a pass. On success it writes build/release/phase-b.pass (HEAD and its tree id), pushes, and then reads the release and arm-diagnose runs of the pushed commit once, with up to 30 s for the runs to appear so their ids are named: green exits 0, red exits 1, anything else prints "unconfirmed", the run ids and the gh run list command and exits 2, and a remote that is not GitHub, or no gh, reports not applicable. It does not wait for CI unless GM_SHIP_CI_WAIT_MINUTES=n asks (a wait held a turn for two hours; the dispatcher reads CI once). check-ship-push uses fakes for GM_SHIP_PHASE_B (replaces the build and Phase B step), GM_SHIP_CI_ORIGIN_URL, GM_SHIP_CI_POLL_SECONDS and a gh on PATH. Measured 2026-11-22: the same tree gave 133 run and 0 failed on the copy and 4 failed in the checkout while it held untracked directories and an unpushed HEAD.
- The build stamp: cmake/gmnew_stamp.cmake runs on every build and hashes the tree the build compiles: HEAD read into a temporary index, the working native and defaults trees staged over it, then git write-tree. The stamp is the first 12 hex digits of the sha256 of that tree id, plus -dev. The repo index is not touched, so a dirty tree has its own stamp and a build made before a commit keeps the stamp of what it compiled. The tree id covers every tracked file, so any commit, including one that changes only docs or skills, gives a new stamp; on a clean checkout the stamp equals the sha256 of HEAD's tree id. The header gmnew/gmnew_build_info.hpp is rewritten only when the stamp changes. A stamp is replaced only when GMNEW_VERSION is the short HEAD sha, or starts with it and a dash (-DGMNEW_VERSION=<sha>-1 is the CI shape). An install with the same stamp keeps the binaries only when gm and gm-core are the same bytes. gm-tool installed and gm-tool ship run gm --version on the built binary (native/components/tool/installed.cpp, ship.cpp).
- Restart survival: proc records each body child's pid and start time in jobs/body-<action>.pids, and a restart reaps every ledger by pid, skipping a pid whose start time changed (check-body-reap). A shell job's wrapper writes its exit code to jobs/<name>.exit; a restarted worker adopts a job whose pid is alive with its remaining timeout and settles an exited job from its exit file, while bodies are killed (check-restart-jobs). Adoption trusts kill(pid, 0), so a reused pid is adopted until its exit file appears, and the poller gives up 10 ticks after a kill request. Windows has no wrapper, so native settles such a job as killed. A restarted native worker takes the gm skill read from its run log when a skill-loaded event carries its own parent pid (check-restart-skill-read); Windows logs no parent pid, so a restarted worker there asks once.
- Skill gate: every run_code on a connection that has not read the gm skill is refused, on every call, and no refusal credits the read. An MCP client advertises no resources capability, so the gate cannot key on one (check-no-resource-client). The one-line refusal names the reads that clear it (resources/read, ReadMcpResourceTool with server gm, the gm prompt) and the skill's path on disk (SkillFile.disk, native/components/mcp/skills.cpp), and says that a host's own file read of that path does not clear the gate. Hosts without resource reads are out of scope (dispatcher decision 2026-11-12), because gm cannot observe a file read. Background: docs/MEASURED_FACTS.md, Skill gate.
- A gm.read_file of a skill uri with no offset or limit returns the whole text (aaafcccc; red-skill-whole-read), so the skill may pass 20000 characters (20568 on 2026-11-23, check-skill-read-fallback and check-no-resource-client ok); a read with offset or limit pages at 20000 characters. Every character of the skill is read at the start of every run, so keep it short.
- Relay re-exec and updates: on an install-pointer change the relay re-executes while only next_context calls are in flight and passes them on with --resend. A running body job holds the re-exec until it ends (the worker sends gm/bodies, publish_bodies), but a relay built before that gate re-execs at once and kills running bodies, so check the live workers for bodies before an install. The relay reads the install pointer on its own thread (watch_install_loop) and cancels an in-flight download before it re-executes. An install re-exec waits for every call except next_context, and the run log restart event is the record of when a relay moved, because the relay's say lines reach the host log only at startup. Update order: when the running build and the published asset both carry a commit time, the older commit is kept and the other is taken; otherwise a running build with serial 1 or no numeric serial refuses with cannot be ordered against this build, and other builds compare serials (check-update-order). The relay checks (check-relay-reexec, check-body-reexec, check-handover-in-flight, check-build-handover) run with GMNEW_AUTO_UPDATE=0 and offer versions ffff111-9999999999 and ffff222-9999999999 with commit time 4102444800, so a CI serial cannot pass them. phase-b fails a row whose output reads ok (skipped ( unless the skip is for a platform, so build the set with -DGMNEW_VERSION=<sha>-1; clock-mutations is outside the default set (GM_CHECK_MUTATIONS=1 runs it). check-relay-reexec failed once on hosted x64 Linux with the cause unknown (docs/MEASURED_FACTS.md, Relay and update).
- check-browser-first-open finds Chromium from PLAYWRITER_BROWSER_PATH, then /opt/google/chrome/chrome, /usr/lib/chromium/chromium.real, the macOS app bundles, or PATH, and runs the launcher with PLAYWRITER_IDLE_MS=20000. WebGPU in a headless playwriter session needs PLAYWRITER_BROWSER_PATH=/usr/bin/chromium with the four PLAYWRITER_CHROMIUM_ARGS flags of defaults/mcp.json, because /usr/local/bin/chrome is a wrapper that overrides the angle flags when /dev/nvidia0 is present (measurements: docs/MEASURED_FACTS.md, Browser).
- ASan on this host: LD_PRELOAD holds three interposer libraries and an asan build then exits at startup, so run asan checks with env -u LD_PRELOAD. On arm64, ASan's stack use-after-return detector costs about 4 s per run_code, so the asan-arm job runs with it off and asan-arm-stackuse keeps that coverage with it on. asan-arm-stackuse runs the same 36 checks in two parallel shards, listed with their recorded seconds in .github/asan-checks.txt (check-asan-shards: each check once, the shards within 10 percent, a timeout of 1.6 times setup plus the slowest shard); one job took 37 to 47 minutes (check step 2432 s on 2026-11-23); the two shards ran 19 minutes in parallel (run 45180811005, 964 s and 937 s of checks, check-spawn-sites 25.8 s), of which check-spawn-sites took 555 s, because std::regex ran on all 41026 lines of native/ with the detector on (5.2 s on x64 at -O0, 0.3 s with a substring prefilter that leaves 781 lines). Sanitizer builds are Debug (-O0, the asan preset), so a per-byte iterator loop over a large file is cheap in the release build and very slow there: comparing two identical 126 MB files with std::equal over istreambuf_iterator took 24.7 s (detector off) and 48.2 s (on) on x64, and 63 ms in 1 MiB blocks (measured 2026-11-22). That loop was same_file in the installer, and it made the identical install in check-build-handover outlast its 120 s limit in asan-arm-stackuse; read files in blocks.
- A body's load-error frame (2026-11-10): the vendored quickjs-ng (7b5f588) prints `at <anonymous> (<body>:L:C)`, where QuickJS-NG printed `at <body>:L:C`. load_error in native/components/quickjs/runcode.cpp matches `<body>:`; the parity row `run_code syntax error` checks the line (DESIGN.md, "Embedded txiki.js runtime (2026-11-10)").
- A gm relay stopped by a termination signal prints the signal and then tears its worker down before it exits (check-serve-signal-reason, check-relay-hup-gate), so the worker's MCP servers and their playwriter gate release; a second signal, a crash signal or SIGKILL exits at once. A host connects to `gm serve` over stdio only: no port or socket is involved.
- Leftover scratch (measured 2026-11-23): gm-tool check roots its TMPDIR at g<pid> (marker .gm-tool-scratch) and ship builds Phase B in gm-ship-<sha8>-<pid> (marker file beside it, .gm-ship-copy, about 2 GB). A run killed by a signal leaves them, so the next gm-tool check or ship removes marked ones whose process is gone and nothing else (native/components/tool/scratch.cpp, check-scratch-sweep); a failed ship removes its copy and keeps only the logs. browser.log and gate.log move to .1 past PLAYWRITER_LOG_LIMIT_MB (5) when a gate starts (check-browser-log-bounds).
- Hosted macOS (measured 2026-11-21 to 23, 10 runs): macos-latest is Apple silicon, so the x64-macos job runs the x86_64 build under Rosetta. Its Phase B took 970-1400 s on one lane against 690-830 s for arm64, its Package step 80-117 s against 4-5 s, and the whole job 1119-1657 s, which hit the 30-minute cap once at 30.4 min. release.yml gives x64-macos 45 minutes (matrix.minutes) and the other builds 30. gm-tool package prints each phase's seconds and runs strip and tar through arch -arm64 when sysctl.proc_translated is 1; that translated tools are the 90 s is a hypothesis, to be read from those lines. Build steps stay 25-60 s with a warm ccache and 105-260 s when a header changes; queue time was 2-4 s.
- check-embedded-runtime's timer bound: a libuv timer fires up to two loop ticks early (the loop clock lags and truncates to a tick; 299.34 ms for 300 ms measured on x64) and Date.now truncates one more, so the check allows three of the Date.now ticks it measures in the body. Load cannot change that, because load only delays a timer. 298 ms was seen once on arm64 under ASan (2026-11-23).
- Do not cache the tokenized text of every file: one worker reached 1399 MB of heap on a 108 MB tree.

## Known gaps, native

- The native client refuses an initialize result with no capabilities object or no serverInfo (native/components/mcpclient/client.cpp; gm-tool check-protocol-versions).
- The SDK (native/third_party/cxxmcp/include/cxxmcp/protocol/serialization.hpp) lists six protocol versions: 2024-11-05, 2025-03-26, 2025-06-18, 2025-11-25, 2026-07-28 and DRAFT-2026-v1. The native server accepts five on initialize (2025-11-25, 2025-06-18, 2025-03-26, 2024-11-05, 2024-10-07; kAcceptedVersions in native/components/mcp/server.cpp), and server/discover lists two (2025-11-25 and 2025-06-18; kSupportedVersions). With `--protocol-2026-07-28 on` (off by default) both also take 2026-07-28 (kFlaggedVersion), and an unknown version still answers 2025-11-25 (check-protocol-flag).
- Native answers an unknown request method with JSON-RPC error -32601 and an unknown resource uri with -32002 and data.uri (measured 2026-11-12; decided 2026-11-10 for resources/read, skills/get and subscriptions/listen). resources/subscribe and resources/unsubscribe are served and resources.subscribe is declared (check-resources-subscribe).
- fetch (native/components/verbs/fetch.cpp): check-fetch (ok, 6.4 s on 2026-11-12) witnesses data URLs (text, cut and match), refuses base64 data URLs and invalid input, rejects timeoutMs below 1 (no upper bound; the timeout is unset by default), and retries an unreachable http host 3 times before it reports exhaustion. check-fetch-transport (17a9571) witnesses https with a local certificate, a 3-hop redirect chain, a 31-hop loop refused as ETOOMANYREDIRECTS (kMaxRedirects 30), a 16777216-byte body accepted and a larger one refused as EFBIG, and file: refused.

## Platform notes

- Windows, macOS and arm64 builds are not verified on this host (Linux x86_64; no Windows, macOS, arm64 or clang toolchain on PATH, measured 2026-11-12), and the process-group kill is unverified on Windows. Hosted CI builds them: .github/workflows/release.yml has windows- and macos- runners, and gh run list shows its runs.
- Install writes no harness settings file (2026-11-12, owner decision): gm install and gm uninstall take no --config, and they print the server entry and the files they touched under ~/.gmnew. The earlier registration wrote ~/.claude.json and printed a Claude Stop-hook entry; both were Claude-specific, so they went. Witness: check-cli-flags.
- Turn-end release is an MCP event (2026-11-12, owner decision): ServerOptions::release_leases(reason, run_end) releases every idle lazy MCP server when a run ends (end_run in native/components/mcp/server.cpp, run_end true) and when the transport closes (input_ended, run_end false). A server whose config sets releaseAtRunEnd false is kept across a run end and released at session close only; defaults/mcp.json sets it for playwriter, because Chrome disposes the contexts a connection made when the connection closes (check-turn-end-release checks each reason in the run log). The Stop-hook path (gm turn-end, a marker under ~/.gmnew/turn-end, --release-at-turn-end) is gone, because a Stop hook exists only in Claude Code.
- The playwriter execute tool returns a value only for one expression, or for an async arrow that returns. A top-level const or let yields "no output"; keep values in `state`.

## Browser flags and project roots (pw bbcc988)

- playwriter-project honours PLAYWRITER_CHROMIUM_ARGS, a JSON array of strings appended to the browser arguments of the project's gate browser; an invalid value exits 1 before a gate starts, the gate log names the flags applied, and a GPU-enabling flag in it keeps the launcher from adding --disable-gpu.
- The project root is the nearest directory from the working directory upward that has .playwriter or .git, unless PLAYWRITER_PROJECT_DIR names it (gm sets that per run). An older lookup took the farthest .playwriter first, so stray .playwriter directories in /workspace, /tmp and /config captured every project below them.
- PLAYWRITER_IDLE_MS: the gate stops the browser after this many ms with no traffic and no lease, even with a page open, and reads the value once when it starts. The default entry in defaults/mcp.json sets 28800000 (8 hours) in envDefaults, which applies only when the variable is not already set, and a layer that restates the whole entry replaces it (check-browser-idle-default; README.md).
- Every playwriter result gets the gate line and the page list from the launcher. The list is repeated only when it changed: lib/browsers.js caches the scan for 2 s, and the scan time in the first line stays out of the comparison (SCAN_TIME_PATTERN). With it in, 79 of 89 results in one docstudio session repeated a 1.4 KB list, 108 KB. The first call with 5 s or more of waitForTimeout gets one early-return hint per launcher process (WAIT_HINT_MS); that session slept 823 s in 102 fixed waits. When only launcher hooks are missing, gm install reapplies the launcher diffs without npm ci (check-browser-feedback, check-launcher-refresh). A second gate that cannot listen on the project's port exits and leaves the first gate's browser up (keepBrowser; before, it stopped it because stopChrome counts the profile lock's pid as owned; check-browser-second-gate). The gate reads the browser's websocket address with the probe's own client, not fetch: on the arm64 Linux runner of release 45318312676 the probe answered and the fetch of /json/version then failed, so every upgrade got 503 with body "fetch failed" for 100 s (cause of the fetch failing there not found; check-browser-ws-address breaks fetch with a preload and expects a 101). A gate whose launcher file is a different build from the caller's (its ping carries build, a hash of the launcher file) is handed over when idle: GET /__pwp/handoff answers 409 while a lease is held, else the gate exits keeping its browser and the caller starts the new gate, which adopts it; kill -USR2 does the same for an operator. A browser that does not answer a probe (busy tabs; "probe failed ... timeout after 3000 ms" fills docstudio's gate.log) is held while its process lives: isHeld read a timed-out /json/list as no open page, and on 2026-11-25 10:16 UTC the grace stop closed docstudio's browser with 8 tabs and its sign-in (check-browser-keeps-pages). A start waits for a closing browser of the profile to exit and then reports ready only once the browser has answered for 2 s (check-browser-start-closing). PLAYWRITER_RESTORE_SESSION=1 (set in defaults/mcp.json) adds --restore-last-session: persistent cookies survive a stop either way, session cookies and the tabs only with it (check-browser-session-restore). A browser start removes the profile's Cache, Code Cache and GPUCache when together they exceed PLAYWRITER_CACHE_LIMIT_MB (default 200; check-browser-profile-cache), and nothing else in the profile. A caller whose browser fingerprint differs gets a note and keeps the browser (check-browser-fingerprint-mismatch). A handover (GET /__pwp/handoff?loaded=) needs a caller launched after the gate and no lease with a call in flight or one called within PLAYWRITER_HANDOVER_IDLE_MS (60 s); check-browser-idle-handover.
- A POSIX header (unistd.h, sys/wait.h, dirent.h and the rest of the list in native/components/tool/checks/portable_includes.cpp) is included only inside a branch Windows does not compile: 6e1ec455 put unistd.h at the top of checks/support.hpp and both Windows builds of release 45318312676 stopped on it (check-portable-includes reads every native file; Linux compiles such a header, so only that check or a Windows build sees it).
- Read /proc with proc::read_text_of, never an istreambuf_iterator (check-proc-read-exits).
- A headful Chromium exits when its last page closes (measured 2026-11-26): the gate keeps an about:blank window it does not own (keepAnchor), so a client closing its own page leaves the browser up (check-browser-last-window).
- Dead code: Linux builds link with --gc-sections, and check-dead-symbols fails on any gm function the linker drops whose name appears only at its declaration and definition. Delete such a function instead of keeping it for later; a function that is only inlined into its callers is not flagged.
