gm: a skill that makes LLM coding agents check their work against real command output

How the checks, gates and walks fit together, for developers who use an LLM coding agent.

AnEntrypoint / gm
Describes the gm project as published on its main branch. The node and edge counts in section 3 are computed from the file named in their caption.
Abstract

gm is a skill for LLM coding agents. It targets three failures: acting on an unverified guess, losing resolved work when the context window fills, and declaring a task done before it meets the requirement. Each check moves out of the agent's reasoning and into files and gates, and a step closes only on the output of a real command run. Section 3 maps the graph that enforces this.

gm is for developers who run an LLM coding agent in their own project. Install it with the one-line command in README.md, or read install for the skill, runner and MCP server steps. Section 3 names the node a walk starts from, and section 5 gives its verbs and completion conditions.

1. Introduction

gm keeps the state graph, the PRD rows and the mutables in files, and a step closes only on the output of a real run.

This paper describes the system as this repository ships it.

3. The discipline graph

The state machine that enforces gates and transitions is gm-config/fsm/graph.json, schema version 2. Its nodes and edges carry no phase field. Its nodes are principles, tensions, gates and terminals, and its edges join them. The policy block names the Jobs To Be Done (JTBD) node as the start of a walk (initial_phase) and G_FIXPOINT as its terminal (terminal_phase). The graph is a set of independent nodes, not a sequence of phases (skills/gm/SKILL.md, Section 2).

Each node carries a key, a kind, a label and a prose_key that selects its served prose. Each edge carries from, to, kind (forward or backreference), a label and its list of gate predicates. The graph keeps both forward and backreference edges.

Three graph files exist, and they are not all the same. The state machine that the walk enforces is gm-config/fsm/graph.json, with 146 states, 376 edges and 26 gates. Its enforced copy is rs-plugkit/crates/plugkit-core/src/orchestrator/lean_graph.json, which rs-plugkit/AGENTS.md describes as a vendored copy of it; the two are identical at this revision. The hop graph is skills/dream-rsi/gm-graph.json, a catalogue of 145 nodes (6 gate nodes) and 360 edges (224 forward, 136 backreference), and the gm-orchestrate skill launches each hop from it. The DADA graph, skills/dream-rsi/dada-graph.json, is converted from an external flowchart (366 nodes, 625 edges). The published DADA page is built from it by scripts/build-graph-page.mjs, and no file under skills/gm or rs-plugkit names it.

4. Gates that refuse a step

A transition is a request to move along an edge. The orchestrator evaluates the gate predicates on that edge, and a failed predicate refuses the move. The graph names 26 gate predicates. Twenty-four are blocking. The two advisory gates never refuse a transition, because code cannot observe their condition: lean-contract-only-description and lean-verifier-independent. The names are listed in gm-config/fsm/predicates.md.

Each gate's predicate in gm-config/fsm/graph.json names a predicate listed in gm-config/fsm/predicates.md. A condition outside that list needs a jit hook under fsm.hooks_dir, or a Rust change that adds a compiled predicate. The denial text lives in messages.gates_dir and messages.residual_dir, and an operator can edit it without changing when a gate fires.

A denial names the failed predicate and the verb that recovers it. It is authoritative: the agent satisfies the named predicate and dispatches the transition again, and it does not route around the denial. A gate that names a predicate outside the compiled set emits fsm_unknown_predicate and is denied permanently, never passed.

5. Walks and completion

A walk is one run of the state machine from the start node toward a terminal. The agent drives it with the instruction and transition verbs. instruction returns the served prose for the node the walk stands on, and it is reserved for an orient. transition moves the walk along an edge, and the gates of that edge decide whether the move succeeds. phase-status answers a bare state check (phase, prd_pending_count, mutables pending). The split is stated in skills/gm/SKILL.md, Section 1.

A walk completes only when all three conditions hold: the live state machine accepts COMPLETE, every required PRD row is resolved, and gm-continue has checked for remaining work. COMPLETE has a forward edge to G_FIXPOINT. G_FIXPOINT is the convergence point of a sweep: it is reached when no gate reopens, no counterexample appears, and the artifact does not grow. The convergence rule is stated in skills/dream-rsi/gm-graph.json.

The main thread runs a walk through gm-orchestrate. A shortfall is a live count below the floor while independent work is open and headroom allows launches, and each one is logged as FAILURE. A repeated shortfall restarts the walk at most twice, and a third repeat files a blocker row, <row>-blocker-<session>, and stops (skills/gm-orchestrate/SKILL.md, Shortfall and FAILURE).

6. When the agent may stop or ask

The agent asks the user only at a world-scoped one-way door, the sole interruption that skills/gm/SKILL.md (Section 4) sanctions. Every other question is a default. The agent chooses the most defensible default, states it in one line in the durable artifact (a commit body, an ADR or a PRD note), and continues. A missing fact gets a codesearch, a fetch, a recall or a prd-add.

The served rules fix what the agent does without asking. A read-only step runs at once. Under git, an append is never asked: commits, pushes, tags, reverts, merges and every collision recovery run without a question. A rewrite is asked: a force push, a rebase of pushed commits, a branch or ref deletion, or a remote reset. Work the user has already asked for, or a plan they have approved, is go-ahead.

Only the terminal phase G_FIXPOINT with prd_pending_count at zero authorizes a stop of the verb spool, and the last dispatch then is gm-continue. While a walk is in flight, every turn ends in a verb dispatch, and a turn without a tool call is a stop (rs-plugkit/crates/plugkit-core/src/orchestrator/instructions/prose/entry.md). A stop hook that re-fires is not a reason to stop (skills/gm/SKILL.md, Autonomy).

7. Hops

A hop is one traversal of one node. The orchestrator launches each hop with one JSON object carrying these fields: node (its id, label, book, author, kind, advocate and links), principle (the id of the node the hop applies), surface (the path it works on), session (its own SESSION_ID), wave, depth and rhetoric (skills/gm-orchestrate/SKILL.md, step 2, shows the launch payload). A missing node, surface or session gives VERDICT: NOT-APPLICABLE.

The hop runs eight steps, numbered 0 to 7 in the skill. Step 0 applies the node's discipline to the surface, named by node.label, with node.advocate as its spec. Step 1 argues the open question in one paragraph. Step 2 lists the node's testable claims, each with its test. Step 3 searches every instance those claims govern and cites the lines it found. Step 4 closes what one exact-match edit closes, when no other writer holds the file, and witnesses the change with a live dispatch. Step 5 records every other finding as a PRD row. Step 6 names the biggest remaining need in one sentence, and step 7 nominates the next node. The receipt is 120 words at most (skills/gm-hop/SKILL.md, Receipt) and names an executed witness. A receipt without one is refused.

A hop never reads the graph. Its links come from the payload. gm-orchestrate builds each link from the edges of the node and sorts the links by to. Each link carries the edge's condition, when the edge has one, as its guard. A link is eligible when every guard holds on the surface. The hop nominates the next node only from eligible links, and the chain stops at depth 6, the default max_depth in skills/gm-hop/SKILL.md, with next: none, depth limit.

gm-hop directs each hop to write .gm/lean-walk/<NODE>.json on every verdict, including NOT-APPLICABLE. The file lists the links offered and the link taken. The link taken is either null or one of the links offered. A discipline the surface demands that the catalogue lacks is appended as a line to .gm/lean-walk/new-nodes.jsonl. A hop never edits the catalogue; the graph's owner promotes an emitted node into it.

A hop commits its own change and does not push. The orchestrator publishes the tip of each wave in one push. A hop issues at most one git_status and one git_commit, plus one branch_status only when it needs remote state, and it does not pull. A hop never dispatches gm-continue. That call is the parent's terminal move.

8. Parallel subagents (the pool)

A walk runs its hops and PRD rows as subagents in a pool. The ceiling is the number of subagents the platform accepts at once, and the orchestrator finds it by launching: a spawn refusal states the ceiling, which pool-observe records in .gm/pool/ceiling.json. When no ceiling is recorded, spawn_ceiling in rs-plugkit/crates/plugkit-core/src/orchestrator/pool_slots/state.rs falls back to DEFAULT_SPAWN_CEILING, which rs-plugkit/crates/plugkit-core/src/orchestrator/pool_slots/mod.rs defines as 20. The floor is min(10, ceiling). While PRD rows are open, the live count stays at or above the floor, and the pool-floor-met gate refuses a transition while open rows leave pool slots free.

The orchestrator runs a tick in five steps, as skills/gm-orchestrate/SKILL.md lists them: observe, launch, log, wait, and re-count the live pool. Observe runs pool-observe, dispatched in rs-plugkit/crates/plugkit-core/src/orchestrator/mod.rs and implemented in rs-plugkit/crates/plugkit-core/src/orchestrator/pool_slots/observe.rs. It reads the body fields live (the ListAgents count), refusal (the spawn refusal text) and held (the ids of the running workers). Its reply carries a slots block with candidates, launch, live_rows, aging_heartbeats, candidates_removed, launch_filters, already_fixed_on_head and open_rows, and top-level floor, ceiling, free_slots and refill_needed. The launch step starts PRD rows first and then one hop per untraversed principle node, from the advertised ids in slots.launch (skills/gm-orchestrate/SKILL.md, step 2). Log writes each launch to .gm/pool/ledger-<wave>.txt and each tick to .gm/witness-log.md. Wait pauses for up to 600000 ms (MAX_WAIT_MS in rs-plugkit/crates/plugkit-core/src/orchestrator/wait.rs), and each completion refills its slot in the same turn before any other step. A freed slot stays empty when the reply's refill_needed is zero: when open_rows is zero, when no slot is free, or when no candidate row and no traversal entry can launch.

Each subagent brief opens by writing .gm/pool/<session>.live and deletes that file on finish. The count of record comes from the subagent list. slots.live and the ledger's live are not the count. A successor that the ceiling refuses is parked at .gm/pool/<session>.next, and the orchestrator relaunches that spec into the first freed slot.

Each failure mode has a fixed response. A subagent whose transport drops mid-run keeps its row open and frees its slot. The orchestrator resumes that subagent by SendMessage to its id. Many drops inside one window are one drain event: the orchestrator waits out the window and refills in half-waves. A dispatch that the serial lane starves is re-dispatched once, unchanged, and a second starvation is logged as lane-starved. A hop whose git verb is starved a second time files a PRD row (skills/gm-hop/SKILL.md). A headroom stop is separate from these. At CPU of 80 percent or more, or available memory below 2048 MB (skills/gm-orchestrate/SKILL.md, Headroom and leases), launches pause. A headroom stop does not end the turn.

9. Planned work (PRD rows) and the nine stages

A PRD row is one unit of planned work. Each row is one file, .gm/prd/<id>.yml. A write is a compare-and-swap of that one file, so editing one row never touches another. prd-add refuses an id that already exists, unless the body carries overwrite:true. prd-list with status set to pending lists the open rows.

prd-resolve closes a row. It moves the row into .gm/prd-log.jsonl, an append-only, hash-chained log (rs-plugkit/crates/plugkit-core/src/orchestrator/instructions/prose/entry.md). A resolved id stays answerable: prd-list with that id reads the log.

gm-prd closes one row in one run, with no subagent in the stages. Each stage writes a create-only receipt, .gm/receipts/<row>/NN-<STAGE>.md.

The nine gm-prd stages, in order
StageWhat the stage does
SPECIFYRestates the row and its acceptance, and checks each cited line against the tree. A line that is absent makes the row stale.
PROVERuns the precondition, the invariant and the postcondition, each as a live check.
EMITMakes exact-match edits only, and witnesses them through the live entry point.
STATEShows that the change replays idempotently, and names the state it owns.
CONCLists each touched file and the hunks other writers hold in it.
SECChecks secrets, injection and identity, each as a run.
RESRuns each failure mode, partial failure included.
DECIDEChecks the receipts and the live witnesses against the words of the row, and checks the push or CI result.
COMPLETECalls prd-resolve with the witness evidence and a witness dispatch id.

A stage that cannot run becomes a blocker row, <row>-blocker-<session>, filed with prd-add. A stage is never skipped. The row is closed by a witness binding: a witness_dispatch_id, or all four of witness_exit_code, witness_output_sha256, witness_output_path and witness_ts. The COMPLETE stage requires the witness to come from another session, so a self-witnessed close stays pending. prd-resolve refuses a witness output sha256 that is already bound to another row (prd-resolve-duplicate-witness). A worker records each witness run as one line in .gm/witness-log.md (rs-plugkit/crates/plugkit-core/src/orchestrator/instructions/prose/entry.md).

10. Mutables

A mutable is an open condition that a decision or a change depends on. mutable-add writes a file under .gm/mutables/, and mutable-list reads the open set. mutable-resolve closes one and accepts a measured_value. Two gates refuse a transition while mutables remain open: mutables-all-resolved and mutables-all-typed.

AGENTS.md requires a falsifiable hypothesis, with the live witness that would refute it, before each change.

11. Witnessed execution and the no-test rule

Execution is a spool verb. An exec verb takes a plain text body, sent as raw_body. The optional first line timeoutMs=<ms> sets the wall-clock limit, which defaults to 300000 ms and has a hard ceiling of 900000 ms (gm-mcp/src/dispatch.js, gm-mcp/src/verb-table.js). At expiry the child's process tree is killed, and the out-file reports killed:true with exec_timeout. A reply longer than its limit, 24000 characters by default (DEFAULT_REPLY_MAX_CHARS in gm-mcp/src/dispatch.js), is cut, and the truncation notice names a spill_file that holds the whole text.

A witness is a live dispatch whose reply carries the value under test. AGENTS.md requires one before each change.

The gate no-synthetic-test-files refuses a test file or test directory in the diff, and verification is a live witness against real code instead. The MCP server's own test files are in gm-mcp/test/. The diff gates no-secrets-in-diff, no-graphical-symbols-in-diff, no-hedge-language-in-diff, no-unchecked-panics-in-diff and no-admit-deferral-markers refuse the matching text, and claim-audit-clean is the claim-audit gate.

12. Search and code insight

codesearch is the search verb, with the aliases code_search and search. Its literal mode finds a string, and grep, with the alias rg, is the exhaustive scan that answers where a string occurs. A scan that hits a bound returns exhaustive: false with partial: true and a partial_reason, and path or path_glob narrows the scan.

Structural questions go to the symbol graph first. callers lists who calls a symbol, callees lists what it calls, and impact walks the callers of a symbol up to max_depth (default 3), or its callees with direction set to callees. The graph comes from the treesitter index, so an empty call graph is trusted only after codeinsight_index runs on a fresh checkout, and AGENTS.md requires that an empty call graph be confirmed with codesearch. codeinsight with action outline requires a path.

A project lists its generated and vendored trees in a .codesearchignore at its root. The file uses gitignore syntax and is read in addition to .gitignore. Dropped paths appear in excluded_by_rule_summary and excluded_by_rule_count. Any exclusion other than gm's own state clears exhaustive. The index build has a wall-clock budget of 45000 ms (index.wall_budget_ms in gm-config/gm.config.json), and index.max_file_bytes caps the size of a file the index reads.

rs-search is a dependency-free library with two source modules beside its crate root, rs-search/src/lib.rs. rs-search/src/fusion.rs implements reciprocal rank fusion (RRF) with RRF_K = 60, and rs-search/src/tokenize.rs tokenizes identifiers. Its source modules contain no BM25 or vector code. rs-plugkit runs the BM25 lexical channel and the embedding channel of section 13, and calls rs-search for tokenization and fusion: bm25_rank_cfg in rs-plugkit/crates/plugkit-core/src/code_index.rs tokenizes its query with rs-search, and rs-plugkit/crates/plugkit-core/src/dataflow_exec.rs calls rs_search::fusion::fuse_n_cfg to fuse the ranked lists. The BM25 parameters are k1 at 1.2 and b at 0.75 (scoring.bm25_k1 and scoring.bm25_b in gm-config/gm.config.json).

13. Memory

Memory is a set of markdown entries and a vector index over them. memorize writes its text to the memory index under a namespace, default unless the body names another, and memorize-fire writes its body as one .md file into the memorize inbox under .gm/exec-spool/in/memorize/. recall returns the ranked hits for a query, auto-recall returns up to three hits for a prompt, and each instruction reply carries recall hits for its own query, up to instruction_recall_hits (5 in gm-config/gm.config.json). forget deletes one key, and memorize-prune, memorize-vacuum and memorize-retention maintain the memorize inbox. The memory namespaces are default and codeinsight (memory.namespaces in gm-config/gm.config.json).

Embeddings come from the bge-small-en-v1.5 weights in agentplug-bert. memory.embed_dim is 384, and AGENTS.md requires that a change to it drop every stored vector through an explicit drop-if-mismatch path, never silently.

Each candidate is scored by its cosine similarity multiplied by a recency factor. The recency factor has a half-life of 30 days (scoring.half_life_ms is 2592000000) and a floor of 0.4 (scoring.recency_floor). Near-duplicate hits are removed when their Jaccard overlap reaches 0.7 (scoring.dedup_jaccard_threshold), and the reply compaction removes a second set at 0.85 (NEAR_DUPLICATE_JACCARD in rs-plugkit/crates/plugkit-core/src/recall_compact.rs). recall returns 8 rows by default (memory.recall_limit).

AGENTS.md sets the durable-memory rule: the agent deletes every entry that is not current (each path, verb and setting it names still resolves) or not reusable (it states a rule for a future task with no session, date or incident).

14. The learning loop

The learning loop has three parts: recall, memorize, and the Dream-RSI observation and replay cycle. Each instruction reply carries recall hits for its own query (section 13). Memorize stores the decisions a later task would otherwise re-derive (gm-config/prose/lean-p1.md, Memorize). Dream-RSI turns the record of real work into strategy proposals.

Dream-RSI records each real work dispatch automatically into .gm/dream-rsi/<session>/observations.json. Orchestration bookkeeping and Dream-RSI's own maintenance dispatches are not recorded, so only real work counts. The current selection is held in active-strategy.json, which observe_dispatch in rs-plugkit/crates/plugkit-core/src/orchestrator/dream_rsi.rs rewrites on each observed dispatch.

A cycle trigger runs inside the agentplug-runner daemon. spawn_dream_rsi_cycle_ticker in agentplug/crates/agentplug-runner/src/daemon.rs wakes once every 60 seconds. For each known project it writes one dream-replay-cycle request, and only when at least 20 new observations have accumulated and at least 15 minutes have passed since the last cycle, as docs/dream-rsi.md states.

A replay result is planning input and never execution authority. It cannot run a tool, evaluate a new outcome, or make an unrecorded branch observed; those need a real dispatch. Deploying an accepted strategy is a dispatch that an agent makes under the same gates as any other state change. No daemon tick or scheduled job redeploys a strategy.

15. The spool and its transports

A body is written to .gm/exec-spool/in/<verb>/<task>.txt, and the reply lands in .gm/exec-spool/out/. An exec reply names its output in a result_file, and a reply longer than its limit spills to the spill_file that the reply names. While the claim in/<verb>/<task>.txt.inflight exists, the dispatch is claimed. The file .gm/exec-spool/.status.json reports the watcher's heartbeat.

gm-mcp wraps the spool for MCP clients. It registers one tool, gm_codemode, whose code body calls every verb as gm.<verb>(body). It serves stdio, which is the default registration, and stateless streamable HTTP on 127.0.0.1:8787/mcp. Its transport failure modes and registration command are owned by gm-mcp/README.md. The Node launcher bin/gm exposes the same dispatch as its dispatch subcommand.

The native host is agentplug-runner. It loads the plugkit WASM guest, which implements orchestration, the spool verbs, memory and code search. The runner is the only supported loader. Git is a verb, not a shell command: the deviation bash-git-bypass denies a shell command that invokes git, and its denial names the git verbs that replace it.

16. Git delivery

Every change lands on main, in the shared work tree. No branch, worktree or side checkout is opened to avoid a collision. A collision is recovered on main in the same turn. The agent reads the conflicted set with git_status, re-reads each path against the remote state, stages the resolved paths with git_add, commits without paths while .git/MERGE_HEAD is set, pushes the full sha of the tip with git_push {rev, allow_foreign_commits:true}, and finishes on main. git_push {rev:"HEAD"} is refused.

git_finalize {message, paths} commits the named paths and pushes them. In a shared work tree the publish path is the Git API route, with blobs, a tree on the remote tip, and a commit parented on that tip, then a read of each published blob. A git_finalize whose push is refused is reported as redundant, never as unpushed work. git_remote reads the remote URLs and the upstream without fetching or changing state. A pushed change is witnessed by two separate reads: git_show {rev} for the commit, and ci-status {sha} for the CI (continuous integration) state. A status of unknown is reported as unknown, never as success.

A commit body states the change and nothing else, with one author and no Co-Authored-By, Signed-off-by, Generated with or assistant footer, because attribution on every project here is lanmower alone (skills/gm/SKILL.md).

17. Invariants and what would break them

AGENTS.md states the repository's invariants. Each item below states one of them with the condition that falsifies it.

  • Configuration precedence. A vendored key in the project replaces the cached and compiled prose. Falsified by a vendored key whose instruction reply still carries the cached text.
  • Gate names. A gate names only a predicate generated into gm-config/fsm/predicates.md. Falsified by a gate that names a predicate outside that file.
  • Path safety. fs_read {"path":"../etc/hostname"} returns error_code: failed. Falsified by an ok: true reply for that path.
  • Remote transports. The system accepts only HTTP(S) remote transports with a nonempty authority, and refuses any other scheme. Falsified by a live dispatch that accepts a remote transport with another scheme or an empty authority. The URL allow-list in rs-plugkit/crates/plugkit-core/src/config_path.rs also names ssh://, which AGENTS.md does not allow.
  • One writer per surface. Each shared file, ref, submodule pin or spool directory has one writer. Falsified by two briefs that write the same surface.
  • Pin parity. Each parent gitlink points to its submodule's main tip, and .github/workflows/bump-pins.yml advances it. Falsified by a parent gitlink that differs from its target's remote main tip after a green bump run.
  • Replay identity. git_commit_dedup_lookup shall answer a replay only while rev-parse HEAD equals the recorded sha_full, because object existence is not enough after git_reset. Falsified by a replay answered after git_reset moves HEAD off the recorded sha_full. The code checks only that the object exists (git cat-file -e) and that the record is younger than 180000 ms, so this invariant does not yet hold.
  • Build identity. The update guard locally_built_installed_reason refuses to replace a runner whose build_info::is_release_build() is false, unless update_over_local_build_allowed() permits it. Falsified by a release swapped over a runner whose RELEASE_BUILD is false.
  • Single-writer markers. A single-writer or lock guard creates its marker by atomic create or atomic rename. Falsified by a plain write in the guard's source.
  • Text encoding. Every tracked text file is UTF-8 without a byte-order mark. Falsified by a tracked file that begins with EF BB BF.
  • Lean graph sync. scripts/sync-lean-graph.mjs emit never writes a path under rs-plugkit/. Falsified by an emit that writes there.

18. Limits

  1. The live ceiling is not measured here. Section 8 gives the fallback default and says how the orchestrator finds the live value, and the paper records no value that any platform accepted.
  2. Memory goes stale. An entry is a claim written at one time, and section 13 gives the rule for removing stale ones.
  3. A walk is bounded, not proven complete. The graph is finite (section 3), the hop chain stops at its depth limit (section 7), and the orchestrator stops after a third repeated shortfall (section 5). These bounds end a walk. They do not show that the walk found all the work a request contains, and AGENTS.md requires a gm-continue check for remaining work before a walk completes.
  4. The paper measures nothing. It reports no speed, failure rate or effect size. No #[bench] or [[bench]] target exists in rs-plugkit or agentplug. AGENTS.md requires a falsifiable hypothesis and a live witness before each change.

19. Conclusion

Section 1 states the core design. Section 18 lists the limits of this paper.
