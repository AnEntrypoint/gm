The Complete Discipline: Lifecycle Control,
Governance, and Operational Hard Rules
for LLM Coding Agents

AnEntrypoint - gm (glootius maximus)
June 2026 - the complete discipline, in one document, from start to end
Abstract
LLM coding agents make the same mistakes again and again when they check their own work. An agent treats a guess as a fact. An agent loses track of the current state. An agent forgets earlier decisions over time. An agent stops work before it meets the real requirement. An agent reports fake output that looks the same as real, checked output. This paper states the gm discipline. gm (glootius maximus) is a tool built from more than 14000 hours of supervised work with coding agents. Each rule in gm removes one of these failure types from agent output. gm also cuts wasted talk. An agent must not narrate a step it did not really do. Unchecked narration adds no value, and it hides errors. This paper covers a phase-gated FSM (finite state machine), where FSM means the fixed sequence of stages an agent moves through on a task. The FSM lets an agent move forward only when it meets the exit rule for its current stage. The FSM sends the agent back to an earlier stage the moment it finds a new unknown fact. This paper also covers the named-mutable discipline, where the agent must mark every open question and close it only through real, checked execution. This paper covers rules for search quality and code structure inside each stage. This paper covers a governance layer: named routes, separate state layers, and quality measures. This paper covers a second set of rules: full work coverage and bounded independent action. It also covers a memory loop that records and recalls facts across sessions. It covers a model for how much work an agent may do per run. This paper covers operational hard rules. Fix a problem the moment the agent sees it. Check real changes in a real browser, and ship no fake output. Search the web before the agent stops to ask a question, and load memory before planning. Run one real integration check instead of a test suite. This paper covers a third set of fixes to the dispatch boundary. This boundary is the exact point where the agent sends a command and gets a real result back. The spool is the only path for an agent to execute a real action, so a prose description of an action is never enough. The mutables file makes every unknown fact either UNKNOWN or WITNESSED, and an outside check enforces this, not the agent's own judgment. A discipline is a named, isolated block of rules, marked with an @ symbol, so one discipline's rules never merge into another's by accident. Execution under WASM (WebAssembly) runs each command in strict order, so the agent always gets one clear result before its next step. A gate denial stops the current action and reports why, instead of changing state on its own. The CI/CD (continuous integration and continuous delivery) pipeline is the one true build check the agent must pass. A residual scan blocks the agent from stopping while real work still remains. Semantic dispatch lets the agent send one clear command directly, rather than routing the same task through a stack of extra subagents. Together, these rules form one complete set of limits on how the agent may act. gm ships as one WASM-backed skill through npm, where npm is the Node package manager.

1. Introduction

LLM coding agents are capable but not reliable at every step. Gm runs as one skill (gm-skill, npm-published, WASM-backed, where WASM is WebAssembly, the binary format the tool compiles to) across every Claude-style skill host. This use shows three failure types. Each type injects a different kind of error between the request and the finished work:

  1. Assumption propagation: the agent treats an unverified guess as a proven fact. Later steps build on this guess. When the guess turns out wrong, the error spreads through every later step. The agent cannot tell an UNKNOWN value from a WITNESSED value by its surface form alone.
  2. State amnesia: the context window fills up and drops older resolved work from view. The agent then re-derives that same work again, and this re-derivation wastes effort with no way to check the new result against the old one.
  3. Premature closure: the agent declares a task done before it meets the real requirement. This is the costliest failure type, because the agent reports it as a success.

The agent cannot fix these three failures by checking its own reasoning. The same reasoning process that takes the shortcut is the process that would have to catch it, so self-checking never catches it. Only enforcement placed outside the agent's own reasoning works. This enforcement takes four forms: spool-dispatch gates, marker files on disk, and FSM transitions the orchestrator enforces. The fourth form is the hard rules the WASM instruction verb serves fresh on every call. Here FSM means finite state machine, the phase graph gm moves through.8,9 Independent research finds the same three failures. Premature termination, assumption propagation, and over-helpful substitution dominate when an agent regulates itself with no outside constraint. A constrained pipeline beats a free-form agent on real software-engineering benchmark tests.7,3

This paper is the production reference for the gm discipline. Each later section targets one of the three failure types above, or states a mechanism that keeps the agent's information intact. Sections 2 through 8 cover the lifecycle. Sections 9 through 12 cover in-phase quality. Sections 13 through 16 cover governance. Sections 17 through 20 cover autonomy and scope. Sections 21 through 29 state operational hard rules. Sections 30 through 37 state dispatch-boundary rules.

2. The State Machine Model

The state machine model blocks the two most damaging failures. The agent acts on an UNKNOWN value, or the agent stops before it meets the real requirement. A forward transition checks only resolved facts, never a guess. A backward transition fires at once when the agent finds any new unknown, so no workaround can carry across a phase boundary. The current phase depends only on the last transition the agent made, never on what the agent says it intends. The FSM has no other path to change phase.

2.1 Phases

The graph has nine phases. The agent moves forward only when a guard passes, or moves backward on a feedback edge. SPECIFY covers alignment and research. It repeats until it closes every open unknown, and it exits when a pass finds no new unknown. PROVE resolves each mutable through witnessed execution. It exits only when every mutable reaches the WITNESSED state, and a gate checks this before exit. EMIT writes the artifacts. A gate checks the source: no test file, no decorative symbol, no marker that defers work. STATE checks the functional core: it checks totality, ownership, and idempotency, and a gate checks that a replay stays safe. CONC checks concurrency: happens-before order, disjointness, and contention bounds. SEC checks security under zero trust: injection, identity, and authority, and a gate checks that the diff holds no secret. RES checks resilience: the exception model, graceful degradation, and stress cases. DECIDE checks the work like an adversary, not like a reviewer who agrees by default. It runs every reachable corner case through real execution. It owns git consolidation and CI/CD validation, where CI/CD means continuous integration and continuous delivery. It allows the move to COMPLETE only when every one of these conditions holds together. Three conditions concern work state: the PRD is empty, every mutable is witnessed, and the worktree is clean. Two conditions concern git: the remote branch has the push, and the residual scan has run. Two conditions concern automated checks: the CI marker matches HEAD, and the browser-witness check has run. Three conditions concern final review: every submodule is clean, the claim audit is clean, and the text holds no hedge language. COMPLETE refreshes the docs and closes the session.

The agent dispatches the instruction verb on every turn. The WASM orchestrator (rs-plugkit/src/orchestrator/) builds each phase's response on that same call, from the live FSM state, the PRD, the mutables, and the recall pack. This response is a pure function of the current state. The served prose can never drift from the real state, because the real state is its only input. No skill file exists per phase. The one shipped skill is a short body that names the agent as the state machine itself. It tells the agent to dispatch instruction every turn and to run the verb the response names. Plugkit never advances the phase on its own; only the agent dispatches transition.

2.2 Forward Transitions (Ladders)

An exit condition is a set of checks. Every check in the set must pass at the same time. This rule rules out a state where code exists before the check that should have caught its fault.

2.3 Backward Transitions (Snakes)

A new unknown at any phase forces a backward transition at once. No count builds up toward a limit, and no override can stop it:

  • PROVE to SPECIFY: a discovery that reshapes the plan, or a mutable that stays unresolved after 2 passes
  • STATE, CONC, SEC, or RES to EMIT: a code repair; any phase to SPECIFY: a genuinely new unknown, or a plan reshape
  • CONC to STATE, and SEC to STATE: an ownership or boundary check that flows back into the functional core
  • DECIDE to SPECIFY: real-world test result feeds back into the plan; DECIDE to PROVE: an unproven claim surfaces late

The agent must fix an invariant violation at its root cause. A local patch over the symptom is not an acceptable fix. An unexpected behavior found during EMIT forces a fix at the true source of the fault.

Observation (Termination). The set of discoverable unknowns is finite, and each planning pass reduces it. These two facts together prove the process ends. Sessions observed so far reach this end point in 2 to 4 passes.

3. The Mutable Discipline

An unverified guess looks the same as a checked fact until a later fault tells them apart. This false match is the exact hazard the mutable discipline removes. A mutable holds one of two states, UNKNOWN or WITNESSED. A mutable starts at UNKNOWN. The agent moves it to WITNESSED by exactly one rule: a real action produces a real result, and the agent records that result. No other path, direct or indirect, moves a mutable from UNKNOWN to WITNESSED without that real result.

3.1 Named Unknowns

A named mutable names every free variable the decision or the code depends on, before the agent uses that variable. Each named mutable states an identifier, an expected value, a current value (UNKNOWN at first), and a method of resolution. The rules block any progress past an open mutable still in the UNKNOWN state. This is a hard rule, not a suggestion.

Naming an unknown turns a hidden guess into a checkable item. Code built on a plausible but unchecked guess is the main source of assumption-propagation failure.

3.2 Resolution by Witnessed Execution

Only one rule moves a mutable to WITNESSED. The agent assigns the value from the observed output of real execution, run against a real service and real data. The list below states each source the discipline refuses as a witness. Each refused source produces an unsound conclusion:

  • Documentation: not authoritative, and it may lag behind the current code (HEAD)
  • Reasoning about expected behavior with no execution: this checks a model of the system, not the system itself
  • Reading the source code alone: this finds only properties visible in the text, and misses a fault that only appears at runtime

Witnessed output is the only fact the discipline accepts as ground truth. Without it, the mutable stays at UNKNOWN, no matter how plausible the guess looks. Research on code-generation errors reaches the same conclusion: verification by reasoning alone misses a fault that only appears at runtime. Checking the result against a live system repeatedly is the method proven to reduce fabricated results.10,11

3.3 The Two-Pass Rule

If a mutable stays unresolved after two resolution attempts, the agent reclassifies it as a new unknown and forces a backward transition to SPECIFY. This rule stops the agent from repeating one failing strategy in an endless loop.

3.4 Surprise Absorption Prohibition

The agent must not silently absorb a gap between an expected result and the real result. Every such gap creates a new named mutable and forces a backward transition to SPECIFY. This rule stops workaround debt from building up.

4. Work Item Management: The PRD

Scope drift means the agent ships a smaller, easier slice of the work and calls the rest a follow-up. This loses real work with no way to recover it. The PRD is the list of planned and resolved work rows, tracked in .gm/prd.yml. It stores the full request set on disk, so the agent can always check it against the complete request. A pending item is work still in flight. It is never a dropped item.

4.1 Structure

Each row in .gm/prd.yml states an id, an imperative subject, and a status (pending, then in_progress, then completed). It also states acceptance criteria, edge cases, and dependency links in both directions. It also states an effort estimate, a route-family tag, and a load score lambda between 0 and 1. Every task beyond a single-line, single-file edit must use a PRD row.

The formula verification_budget = lambda x (1 - tier_confidence) sets how much more verification a row needs. A row with lambda greater than 0.75 needs a witness before EMIT.

Two independent studies support this design. A SANER 2026 registered report finds that writing the spec before the code reduces errors. A separate study of the Agentless method finds that a constrained sequence of localize, repair, and validate steps beats a free-form agent loop. This constrained sequence wins on the SWE-bench benchmark, at lower cost.16,7

4.2 Wave-Based Parallel Execution

A dependency DAG (directed acyclic graph) sets the order of waves. Each wave batches every pending item whose dependencies are met into one message of concurrent spool dispatches. The width of this fan-out is bounded by the spool's concurrency cap, not by the number of agents. The rules forbid platform Task or Explore subagents, because a subagent that returns only prose in isolation stalls the chain (see section 38). Parallel work runs only as N concurrent spool dispatches the orchestrator serves.

4.3 Stop-Checkpoint Enforcement

A marker-file gate checks three conditions at the stop checkpoint. Each condition on its own blocks the stop: a non-empty .gm/prd.yml, a dirty worktree, or an unpushed HEAD. The gate reads state from disk. It does not depend on a hook event.

4.4 Cross-Session Continuity

The PRD persists across sessions as the durable contract between the agent and the request. An item a prior session discovered is a current-session obligation, regardless of whether the current turn mentions it. A session is one unit of scheduled work. The PRD stays the same across every session.

5. Cross-Session Memory Architecture

A context window loses data: when it fills up, it drops the oldest content first. Re-deriving a dropped subproblem repeats work the agent already did. Persistent memory fixes this loss across the session boundary. The exclusion rule and the verification rule below stop a stale memory entry from coming back as if it were new, current fact.

5.1 Memory Types

The vector store holds four types of memory:

user:
the user's profile, role, expertise, and preference
feedback:
a behavioral correction or confirmation; the channel that carries a lesson forward across sessions
project:
work context, deadlines, and decisions
reference:
pointers to an external system

Memory lives with the project, never as scratch state on the host platform. The agent commits it to the repository, so it survives across a change of machine, session, or CI run. No raw-text search index exists for memory. The memorize-fire verb embeds each entry with an in-WASM bge-small model. It saves the content and its 384-dimension embedding as two files at the same location: .gm/disciplines/<ns>/<key>.json and .gm/disciplines/<ns>-vec/<key>.json. Retrieval works only through embeddings. The agent compares the query against every candidate by cosine similarity, then applies a recency decay (a 30-day half-life, with a floor). It then removes near-duplicates by Jaccard similarity. No text index exists anywhere in this path. The recall and auto_recall verbs re-score memory on every dispatch. They never load one fixed snapshot at session start. This design matches recent work on agent memory. A-MEM links embedded notes in a Zettelkasten style, and Mem0 builds a production store through consolidation and salience. MemoryAgentBench finds that even a strong RAG-augmented agent (RAG means retrieval-augmented generation) trails a human at three skills. Those skills are retrieval accuracy, learning during a task, and forgetting the right things. This last finding is the evidence for scoring memory fresh on every turn, instead of once per session.13,14,15

5.2 Exclusion Principle

The store excludes anything the agent can derive from the live project state: code patterns, architecture, paths, git history, and prior debugging steps. Storing such a fact would create a second copy of the truth, and the two copies could drift apart. Acting on a stale cached fact is one of the costliest failure types.

5.3 Verification Before Recall

Before the agent acts on a memory that names a specific file, function, or flag, it checks that the named item still exists. A memory is a claim recorded at write time. It is not a claim about the present state.

5.4 Feedback Loop

The feedback type is a channel that carries a behavioral correction forward across sessions. The agent records each correction, and each confirmed non-obvious approach, as a {rule, reason, context} entry. This record stops the agent from making the same mistake again in a later session.

6. Implementation: The gm Orchestrator

A rule that lives only in the agent's own context is a rule the agent can edit or ignore. The same process that would break the rule also holds the power to change it. The orchestrator moves every gate out of the agent's own context: onto disk, and into the WASM verb surface. Enforcement lives at this fixed external boundary (the ABI, or application binary interface), not as an internal habit the model has to choose to keep.

6.1 Single-Skill Architecture

Gm ships as one skill, gm-skill. It carries one short body of hard rules and holds no per-phase content. It tells the agent to dispatch instruction every turn, and the orchestrator builds the phase-specific instruction on each call. This design replaces an earlier chain of fifteen skills (gm, planning, gm-execute, gm-emit, gm-complete, update-docs, governance, code-search, browser, ssh, pages, create-lang-plugin, memorize, textprocessing). The instruction response and the verb-dispatch surface now cover everything those fifteen skills did. This fix removes the friction of keeping fifteen coupled prose files synchronized. One short, fixed body plus a response built from live data replaces all fifteen.

6.2 Spool Dispatch and Marker Gates

Marker files on disk drive state-machine enforcement. No event drives it. The earlier design used host-process hook callbacks (session-start, prompt-submit, pre-tool-use, stop). Gm retires that design. The gate now runs inside plugkit.wasm itself (rs-plugkit's gates.rs, plus its hook_pre_tool_use and hook_stop exports). It reads disk state before any tool runs. The WASM host calls the gate. On denial, the gate shows its reason text to the model. The marker files under .gm/ hold the discipline's persistent state:

.gm/prd.yml
Its presence triggers the needs-gm gate. This gate blocks every write, edit, and git operation until the agent invokes the gm skill this turn.
.gm/mutables.yml
A row with status: unknown blocks Write, Edit, NotebookEdit, git commit, git push, and the stop checkpoint.
.gm/needs-gm
The bootstrap step writes this file. It tells the dispatcher that the agent must invoke the gm skill this turn before it can use any tool.
.gm/gm-fired-<sessionId>
The agent's Skill(skill="gm") call writes this file and clears the needs-gm gate. The system clears it again at the start of the next turn.
.gm/residual-check-fired
This one-shot marker makes sure the residual-scan check fires exactly once per stop window. It clears at the next prompt-submit event.

The session-start bootstrap step (lib/skill-bootstrap.js) sets up the WASM artifact, starts it, writes .gm/exec-spool/.bootstrap-status.json, and lays down the markers. The auto-recall step fires on every turn entry. It builds a 2 to 6 word query from the prompt. It then adds a "## Recall for this prompt" section to the next instruction response.

The agent's own reasoning cannot route around this enforcement. Each marker is a fact on disk. The dispatcher reads it with no dependency on the agent's own context. The gate sits below the tool surface, so the agent's decision layer cannot reach around it. This design is more reliable than the retired hook-event system. There is no event to miss, no callback to forget, and no per-host lifecycle to track. Only files exist, and the system reads them once.

6.3 Unified Code Execution

Every execution runs through the exec_js verb. The agent writes a file at .gm/exec-spool/in/<verb>/<N>.txt. The WASM watcher reads this file. The host runs child_process.spawnSync. The agent reads back one JSON response at out/<verb>-<N>.json or out/<N>.json, holding {ok, stdout, stderr, exit_code, timed_out, duration_ms}. Separate language verbs cover each runtime: nodejs, python, bash, typescript, deno, go, rust, c, cpp, java, and browser.

6.4 Single-Package Deployment

Gm ships as one GitHub Release tarball, gm-skill, which any Claude-style skill host can load. A shell or PowerShell installer downloads the WASM artifact, checks its sha256 hash, and loads it directly, with no package manager involved. A cascade pipeline runs over three WASM-only Rust repositories: rs-plugkit, rs-search, and rs-codeinsight. rs-plugkit now holds the retired rs-exec host-helper and rs-learn memory code directly. This pipeline, together with the plugkit-bin release process, auto-publishes on every push, with no manual step. This design replaces an earlier set of fifteen per-platform repositories, now archived. Those repositories were: gm-cc, gm-gc, gm-oc, gm-kilo, gm-codex, gm-qwen, gm-copilot-cli, gm-hermes, gm-thebird, gm-vscode, gm-cursor, gm-zed, gm-jetbrains, gm-antigravity, and gm-windsurf. One install now replaces fifteen.

7. Constraint Tiers

Four tiers rank each constraint by how much damage its violation causes. A Tier 0 violation corrupts the agent's whole information channel. A Tier 3 violation only reduces density. The tiers run in order of decreasing severity:

Tier 0 (Absolute):
no_crash, no_exit, ground_truth_only, real_execution. The spool-dispatch gate enforces this tier, and no override can bypass it.
Tier 1 (Quality):
max_file_lines=200, hot_reloadable, checkpoint_state
Tier 2 (Modularity):
no_duplication, no_hardcoded_values
Tier 3 (Style):
no_comments, convention_over_code

8. Pre-Emit Verification Protocol

A check that only runs in memory, and fails once the code touches disk, is a false pass. This is the costliest kind of failure, because it looks like a real pass. Two-stage verification closes this gap between the in-memory state and the file the agent actually saves. Pre-emit: the agent imports the target module and runs the proposed logic in memory against real input and error input. It records the expected output, checks that every gate condition holds, and only then writes the file.

Post-emit: the agent imports the module again, this time from disk, re-runs the same input, and compares the result exactly against the pre-emit result. A known difference gets a fix, then a re-check. An unknown difference forces a backward transition to SPECIFY. This second stage catches faults a test written after the code would miss. Examples include a serialization bug, a mismatch in how imports resolve, or a filesystem race condition.

9. In-Phase Quality: The Search and Code Discipline

Two search methods can reach the same correct answer, but at very different cost. A blind grep search re-derives a fact the project's index already holds. A single search against the real index retrieves that same fact directly. This discipline keeps search grounded in the real index and keeps code structural. It cuts wasted effort along the whole path, not only at the final answer.

9.1 Codebase Search Protocol

A claim that something does not exist in the codebase needs a minimum search effort first:

  • Start with a 2-word query. Change one word on each later pass.
  • Run at least 4 search attempts before the agent may claim the item is absent.
  • Use only the codesearch verb. The spool-dispatch gate blocks a direct Glob, Grep, or Find call during agent phases. Every search runs through this one indexed surface.

The codesearch verb retrieves results only through embeddings. It holds no raw-text index. The corpus is a vector space, not a set of lines to grep, so a result ranks by meaning, not by exact text match. It combines BM25 lexical scoring with vector cosine similarity through Reciprocal Rank Fusion (see rs-search, section 42). It also raises the rank of a file touched by a commit that is topically close to the query. This adds a time-aware boost on top of the meaning-based match. Both codesearch and recall return the full result set, not a cut-down snippet, so the agent can act on a hit without a second fetch. Every output stays sized to fit the calling context, with no unbounded dump. When the agent finds an existing concern, it folds the new work into that existing code. It never builds a second version beside it. A second abstraction over an already-indexed concern creates duplicate code to maintain from the moment it is written.

9.2 Minimal-Code Resolution Order

When more than one way solves a problem, the agent checks four options in order and stops at the first one that applies:

  1. Native first: does the language or runtime already have this?
  2. Library second: does an existing dependency solve this pattern?
  3. Structure third: can the agent encode the problem as data (a map, a dispatch table, a pipeline), so the structure itself enforces correctness?
  4. Write last: the agent writes new logic only after it rules out the three options above.

A dispatch table is better than a chain of switch statements. A pipeline is better than a loop with an accumulator. A map is better than a long chain of if/else statements. Each of these is a correctness property, not a style choice. The right structure removes a whole class of invalid state that a hand-kept, manually consistent version would otherwise allow.

10. Structural Parallelism and Wave Execution

Running independent work one item at a time wastes available time. Wave discipline fills that gap. The agent batches every pending item whose dependencies are met into one message of concurrent spool dispatches, collects the results, then plans the next wave. It runs until it clears the whole related PRD family, and it never stops mid-wave to ask for direction.

Only one part of the work must run one at a time: the browser verb. It shares one Chromium instance, so it cannot run two sessions at once. Every other kind of work can run in a wave.

11. Permanent Observability

A problem the agent cannot measure is a problem it cannot reduce. Observability makes every part of the system visible. Every subsystem answers a query with no restart. The agent reads drift straight from structured state, never from a guess based on rendered output.

11.1 Mandatory Enumeration

Every planning pass lists each subsystem that lacks a queryable inspection endpoint, and creates one PRD item per gap. SPECIFY exits only when a pass finds zero gaps.

11.2 Server-Side

Every subsystem exposes a /debug/<subsystem> endpoint. This endpoint emits structured JSONL (JSON Lines) in the shape {subsystem, severity, ts}. A plain console.log call does not count as observability. The agent wraps instrumentation around the dispatch boundary once. It never adds instrumentation to each handler separately.

11.3 Client-Side

The window.__debug object is a live structured registry. It registers state when a component mounts and deregisters it when the component unmounts, and it tracks active requests and sockets. The agent can query any entry by key with no restart, and no other observability surface exists in parallel. The agent checks this registry through a live browser dispatch, never a standing test file.

11.4 Stack Observability

The system writes structured JSONL to ~/.claude/gm-log/<YYYY-MM-DD>/<subsystem>.jsonl. It writes the watcher's stdout and stderr output, plus the WASM cdylib's own println! and eprintln! output, to .gm/exec-spool/.watcher.log, which rotates at 10MB. The spool root also holds diagnostic files: .status.json, .last-session-start.json, and .bootstrap-error.json. A stale modification time on .status.json means the watcher has died; the absence of .bootstrap-error.json means the system is healthy. The health verb runs a one-shot probe across every component. The agent must read the log or dispatch health before it diagnoses a problem. Skipping this step turns a diagnosis into a guess.

12. The Memorize Sub-Agent

The agent should never pay twice for information it already resolved once. Memorize is the write half of this loop. It turns a resolved WITNESSED fact into a durable store entry, so the fact does not decay back to UNKNOWN at the next session boundary. Every UNKNOWN-to-WITNESSED transition fires a background dispatch in the same turn:

write .gm/exec-spool/in/memorize-fire/<N>.txt
  body: "<fact>"
read  .gm/exec-spool/out/memorize-fire-<N>.json

When one turn resolves N facts, the agent fires N parallel dispatches, one per fact, never batched together. A batch of facts sent as one call would collapse into a single classification and lose the separate meaning of each fact. A self-check at the end of each turn scans for any resolved fact the agent has not yet memorized. The write uses a content hash as its key, so the write is idempotent (running it twice gives the same result as running it once). Firing an identical fact again matches its existing key and does not create a duplicate, even under at-least-once dispatch. The memorize-fire verb is the only writer of AGENTS.md and CLAUDE.md. The agent must not edit those files inline. Those files are a staging ground; the store is the surface the agent reads from. The agent writes every load-bearing rule twice. It writes once inline in AGENTS.md, so the rule survives context compaction. It writes once more fired to the default-namespace store, so a later turn's recall or auto_recall call can surface it. This flow runs in both directions, and one direction limits the other. Each memorize session also moves a few existing detail-heavy AGENTS.md entries into the store. It fires their real content to the store and shrinks the file entry to a one-line pointer. This keeps the staging ground from growing without bound, at the same rate the store grows. The classifier refuses a changelog-shaped fact (one written in the past tense with a date) from AGENTS.md. The default namespace in rs-learn still accepts that same kind of fact directly.

Recall and memorize are the two halves of one closed learning loop. Using either one alone leaves an open loop, and an open loop costs unbounded effort to re-discover the same fact again.

13. Governance Layer

Governance turns the paper's goal into a working system. Route families, state planes, and refused collapses turn a general aim for low error into a fixed check that each transition passes or fails. The lifecycle stops errors by its own design. Governance checks that this holds true, with real instruments.

13.1 Seven Route Families

Every PRD item carries one of seven route-family tags. Each tag sets which quality rules apply to that item:

grounding:
sets rules for how the agent forms a belief: what counts as evidence, what counts as knowledge, and when the agent must return to planning. This family governs every information-gathering step.
reasoning:
sets rules for a chain of inference. Each reasoning step must be witnessable. A conclusion must never outrun its premise. This family enforces the two-pass rule and the surprise-absorption prohibition (see sections 3.3 and 3.4).
state:
governs a change to mutable state. Every change must appear in the PRD. Any operation that changes state needs a stated precondition and postcondition. The PRD is the one authoritative record of state.
execution:
sets rules for code execution: real services only, witnessed output, dispatch through exec_js, and a fixed timeout budget. No stub, no mock, and no hardcoded response is allowed.
observability:
requires every subsystem to answer a query with no restart. This covers the /debug endpoints, window.__debug, structured logging, and the gm-log JSONL stack.
boundary:
governs how the agent reaches an external system: git, CI, a remote API, or the user. The remote-execution boundary in section 16 is the main concern this family covers.
representation:
governs how the agent encodes and passes on information. Skill prose states rules by implication, not by direct instruction. Memory must use one of the four types from section 5.1, and a PRD item must use the required schema.

13.2 Four State Planes

The system tracks agent state across four separate planes. All four must agree with each other at every phase transition. Each plane has one concrete test that detects an inconsistency:

epistemic:
what the agent knows, what it remains unsure about, and which mutables stay unresolved. Detection test: count the unresolved mutables (epsilon). PROVE exits only when epsilon equals 0. Any named UNKNOWN with no witness is still an open mutable.
operational:
what the agent has done: which artifacts exist on disk, and which code has run. Detection test: run git status (an uncommitted change means this plane is inconsistent). Also check the acceptance-criteria assertions (a failing assertion means this plane is inconsistent). Also check that exec_js returned a real witnessed value, not just a predicted one.
relational:
what the agent has told the user, and which commitments remain open. Detection test: the agent's prior response has an open statement such as "I will" or "next I'll". This statement has no matching completed action in the operational plane, so the gap is a relational inconsistency.
temporal:
what happened in an earlier session, and what the PRD keeps across a context reset. Detection test: .gm/prd.yml exists and still has a pending item while the phase claims COMPLETE: this is a temporal inconsistency. A recall hit that surfaces a prior design decision different from the current plan is a weaker temporal inconsistency, and it needs a fresh witness.

A phase transition is valid only when all four planes agree with the exit condition for that transition. If the agent advances from PROVE toward EMIT while the epistemic plane still holds an unresolved mutable, the agent's state is inconsistent. This holds true no matter what the operational plane shows.

13.3 Five Refused Collapses

The discipline refuses five patterns outright. Each one breaks the discipline while still looking like it follows the discipline:

  1. Narrating as executing: the agent describes what code would do, instead of running the code
  2. Assumption as resolution: the agent treats a plausible value as a witnessed value
  3. Partial closure: the agent marks a PRD item done while its acceptance criteria remain unmet
  4. Deferred observability: the agent ships code with no inspection endpoint and notes the endpoint as future work
  5. Asking-as-progress: the agent asks the user a question it could answer itself with its own tools

14. Quality Metrics

Four metrics drive every quality-gate decision at a phase transition:

DeltaS (state delta):
the number of state-plane inconsistencies a proposed change would introduce. The agent must reject a change with DeltaS greater than 0, or resolve the inconsistency, before it advances the phase.
lambda (load score):
the consequence weight of a PRD item, a number from 0.0 to 1.0. An item with lambda greater than 0.75 needs a witnessed check before EMIT. The formula verification_budget = lambda x (1 - tier_confidence) sets how much verification remains. Here tier_confidence is the fraction of this item's acceptance criteria already witnessed (0.0 means none witnessed, 1.0 means all witnessed). More prior witnessing shrinks the remaining budget in direct proportion.
epsilon (epistemic gap):
the count of unresolved mutables in the epistemic plane. PROVE exits only when the final pass reaches epsilon equal to 0.
Coverage (0.70 or higher):
the share of load-bearing behaviors witnessed by a live exec_js/browser dispatch against the real system, never a standing test file. Coverage of 0.70 or higher across the behaviors an EMIT pass touches is the acceptance criterion. Any behavior a session cannot witness live this way is not load-bearing, by definition.

15. Failure Taxonomy

This taxonomy lists sixteen failure modes across four categories. Each mode is a specific way an error enters the process, or a specific way the agent loses real information. Each mode maps to a rule elsewhere in this paper that stops it. Every SPECIFY pass checks each PRD item against this full list:

Grounding Failures

  1. Assumption propagation: the agent treats an unverified guess as a proven fact
  2. Documentation trust: the agent uses stale documentation as proof that a mutable is resolved
  3. Static analysis substitution: the agent reads the code instead of running it
  4. Memory staleness: the agent acts on an outdated memory with no check

Execution Failures

  1. Stub shipping: the agent presents placeholder code as a real, working implementation
  2. Mock leakage: a test fixture ends up in a real production code path
  3. Timeout blindness: an execution result is cut short, and the agent does not detect the cut
  4. Orphan accumulation: a background process from a prior run stays alive after a restart

State Failures

  1. Partial closure: the agent marks a PRD item complete while its acceptance criteria remain unmet
  2. Epistemic advance: the agent attempts a phase transition while a mutable stays unresolved
  3. Cross-session amnesia: the agent fails to find and complete a PRD item from a prior session
  4. Dirty exit: the agent closes the session with an uncommitted or unpushed change still pending

Boundary Failures

  1. CI blindness: the agent declares COMPLETE before it knows the CI result
  2. Remote-execution misread: the agent treats a git push as local execution and does not watch the CI result
  3. Forced pause: the agent pauses for a question a web search could have answered
  4. Asking-as-progress: the agent asks the user a question its own tools could answer

16. Remote Execution Boundary

16.1 A git Push Runs Code on a Remote System

A git push is not a local action. A push starts a build, test, and deploy pipeline on a remote system. The CI result is the true measure of correctness. The agent must not report COMPLETE before CI finishes.

16.2 CI Watch Protocol

After each push, the agent sends gh run watch through the spool. The agent polls until the run finishes, then checks the result. A green CI run must exist before the agent can move from VERIFY to COMPLETE. The stop-checkpoint gate blocks session close when the latest push has no recorded green run. The agent must not move past DECIDE while CI is pending or red.

16.3 Five CI Failure Types

The agent sorts each CI failure into one of five types:

  1. Import error: the system cannot find a module. Check package.json or Cargo.toml, not the source file.
  2. Type error: a schema does not match. Return to SPECIFY and check the interface again.
  3. Test failure: an assertion does not match. Find the root cause first. Do not silence the assertion.
  4. Lint failure: the code breaks a style rule. Fix the code. Do not add // eslint-disable.
  5. Build timeout: run the build again once. If the timeout repeats, find and fix the cause: split the job, cache the dependencies, raise the CI timeout, or find the hang. A repeated timeout always has a real fix.

17. Maximal Cover

Hard Rule: Maximal Cover [SPECIFY]

When the scope is larger than the agent can reach in one pass, the agent must build the largest possible plan. The agent must not refuse the task. The agent must not do one small part and leave the rest for later. A plan that covers only part of the task is a refusal in disguise. The agent must plan the widest, deepest reading of the request that this session can do. A smaller plan is the exception, and the agent must give a reason for it.

Required action: list every bounded part of the request that this session can do. Write this list into the PRD, with each part's dependencies stated. Do all of the listed work. Build cost, CI run time, work across repositories, and the size of a breaking change are reasons to do the full plan. They are never reasons to cut it down.

The agent may find extra work that fits the spirit of the original request. The agent may add this work to the PRD and do it without asking first. Every piece of work is possible to finish. When a task looks unreachable, the agent must find a way to reach it. The agent runs the failing tool directly, or starts a new copy of the service. The agent opens the change in another repository, or writes the script that gets the needed credential. The agent must not name a task unreachable and stop. Only work truly outside the original request goes into a later plan, and even that work gets its own PRD row. The agent must never simply stop.

When the agent adds extra work on its own authority, the agent must state its reason in the response. For example: "I am adding X because Y." This lets the user correct the agent during the same chain of work. Adding work without stating the reason is the exact failure this rule prevents.

Check: the finished work plus the named extra items must equal the full scope the agent can reach from the request. A gap between them means the plan is not maximal. The agent must return to planning.

A dropped requirement is hard to notice. It causes no error and no failed test. It is a silent gap between what the agent delivers and what the request specifies. The Maximal Cover rule finds this gap. A scope larger than one pass can reach is an input to planning, not a reason to stop. The agent lists every part of the request it can do in this session, and this list is the plan. The agent then does all of it. Doing one small part and stopping is a refusal that looks like triage. Both leave reachable work undone. Both end the task before it is finished. Controlled studies measure this same failure: agents skip sections, write less than the task needs, and do the minimum instead of the full task. These studies show the failure as a repeated pattern, not a single story.17

18. Bounded Autonomy

Hard Rule: User Request = Authorization [SPECIFY, PROVE]

The user's first message asking for X is approval to do X. The PRD records this approval. The PRD is not a second approval gate. The user already said to do X. The agent must not then ask whether to proceed, whether to do X, or which form of X to use. Each of these questions is a stall, not caution. Each one makes the user wait.

The agent may state a tradeoff inside the same chain, in one sentence -- for example, "using shape A because Y". This lets the user interrupt if needed. The agent must not use this as a reason to stop and wait. Work across many repositories, build cost, CI run time, and binary size are never reasons to ask the user to check again.

A written PRD is the user's approval. Once the PRD exists, the PROVE phase owns the work through to COMPLETE. The agent resolves every doubt during the work by a witnessed check, by recall, or by reading the PRD again. The agent must not ask the user to resolve a doubt.

The agent asks the user only as a last resort. This applies when the action is destructive, cannot be undone, and the PRD does not cover it. It also applies when the user's intent cannot be found in the PRD, memory, the code, or the web. The channel for this is pause, which renames prd.yml to prd.paused.yml and puts the question in the header. Asking inside the conversation is a last resort below this last resort. When a question starts to form, the agent must first widen its search and send a WebSearch/WebFetch pack. The agent asks the user only when both of these searches return nothing. Most questions an agent wants to ask are really an attempt to narrow scope. The answer the user would give often matches what one web search would find.

pause and the stop checkpoint: when the agent sends pause, the system renames the PRD to prd.paused.yml. The stop gate then reads .gm/prd.yml, finds no active PRD, and lets the session close as normal. At the start of the next session, skill-bootstrap.js finds prd.paused.yml with no active prd.yml. It renames the file back, and the agent resumes from where it paused. The rename is a single file operation that finishes before stop runs, so there is no timing conflict.

A question the agent could answer itself, but sends to the user instead, wastes the user's time and delays the work. Each question the agent asks costs at least one round trip of waiting. A question the agent's own tools could answer turns agent work into user work. This cost adds up across many questions in a session. This added cost is a real defect in the work, as serious as a failed test.

19. The Learning Loop

The learning loop makes the ratio of useful signal to noise rise over time across sessions, instead of staying flat within one session. Each fact the agent recalls, instead of finding again from scratch, has a discovery cost. The loop pays this cost once and reuses the fact in every later session. The loop needs both of its operations to run every cycle:

19.1 Recall (Read)

The agent runs this before it tries to work out something new:

recall
<2-6 word query>

The agent runs recall in four cases. First, an unknown feels familiar. Second, a subtask is on a project the agent already knows. Third, the agent is about to ask something the team likely discussed before. Fourth, the agent is about to design something a past decision likely already covers. A hit from recall is a weak_prior. The agent must check the hit again before it treats the hit as true. Cost: about 200 tokens and about 5 milliseconds.

19.2 Memorize (Write)

Each time an unknown becomes witnessed, the agent sends a background memorize-fire call in the same turn. When there are N new facts, the agent sends N parallel write calls in one message. When the agent skips this write, the loop breaks. Every future session must then pay the full discovery cost again for a fact this session already found.

19.3 rs-learn Backend

Both operations write to and read from the rs-learn key-value and vector store at .gm/rs-learn.db. Git tracks this file, so memory and index state move with the repository, not with one machine. The auto-recall verb calls rs-learn inside the WASM (WebAssembly) module. It inserts a "## Recall for this prompt" section into the next instruction response, before the agent reads the user's turn.

20. Execution Budget Model

The rule to save tokens applies directly to how the system runs code. Each call has a required time limit, so the worst case never wastes unlimited time. A timeout gives back partial results instead of blocking the channel. Every exec_js call carries two layers of time budget:

  1. Dispatch layer: the request body must set timeoutMs. A missing or zero value is a hard reject.
  2. Host layer: child_process.spawnSync runs with this timeout. When the timeout passes, the system keeps the partial output it has streamed so far, and marks the result timedOut: true.

The [exec timed out after Nms; partial output above] message is a true report of a cut-off result, not an error. The agent must send the call again with a higher time budget. Sending the same call again with the same budget only repeats the same timeout forever.

The system runs inside WASM (WebAssembly) in a single sequence. This means a long subprocess blocks the watcher for its full run time. No separate background execution exists. For a long-running task, the agent must pass a real timeout and accept that the watcher cannot serve other callers during that call.

21. ORIENT: Pre-Planning Recall Pack

Hard Rule: ORIENT [SPECIFY]

At the start of every planning session, the agent sends 3 to 5 recall calls against the nouns in the request. The agent also sends 3 to 5 codesearch calls against the same nouns, all in one message. A hit gives a weak_prior. A miss confirms the unknown is genuinely new.

The agent must send this pack of calls together in one message, never one at a time. An agent that skips ORIENT still pays the same search cost later in the turn. That agent also risks giving an answer that disagrees with a fact an earlier session already found.

ORIENT costs little compared to the cost of finding the same fact twice, or of giving an answer that disagrees with an earlier witnessed fact. Its true cost equals the cost of skipping it. The agent will run the same searches anyway, only later, after it has already named unknowns that may already be stale.

ORIENT loads existing project knowledge before planning starts. An unknown the agent names is then a genuinely new gap, not a fact it simply failed to look up. The agent must not claim a fact is absent without searching for it first. The agent must not build a new abstraction without checking whether one exists already. The pack of parallel calls runs at full concurrency, so it adds no serial delay to planning.

22. Fix on Sight

Small rough edges build up over time. Each edge left unfixed is a small, lasting flaw. Together, these flaws make the work look machine-made, even when each line of code is correct on its own. The Fix on Sight rule stops a known flaw from surviving past the turn that finds it.

Hard Rule: Fix on Sight [PROVE, EMIT, DECIDE]

The agent fixes every problem it finds during the work, in this same turn, at its root cause. A defer marker, a swallowed error, hidden output, a skipped test, and a note to "fix this next session" are all the same failure. Each one carries a known bad signal past the moment the agent found it.

The correct sequence is: find the problem, find its cause, fix the root cause, check the fix, then continue. When the fix reveals a new unknown, the agent returns to planning. When the fix is out of scope and cannot be undone, the agent adds it to the PRD as a residual before moving on. A sentence in the response is not a substitute for a PRD row.

22.1 Add Unplanned Errors to the PRD Automatically

The agent adds any reasonably fixable error it meets mid-task to .gm/prd.yml in the same turn, without being asked, and fixes it before COMPLETE. This covers a pre-existing broken build, an out-of-date lockfile, or a broken dependency. It also covers a lint failure or a type error in a nearby file, a stale generated file, or a dead import. Closing the task while a known bad signal still appears ends the task before it is truly finished, no matter where the signal came from.

When an error seems to depend on something outside the current tree, the agent finds the concrete action that solves it, and does not stop. A missing credential becomes a PRD row to write the script or request that gets the credential. A service that is down becomes a row to retry it, escalate it, or use an alternative. A choice for the user to make becomes a row that surfaces the choice to the user as the next step. A broken tool becomes a row to fix it or replace it. The agent drives its protocol directly, starts a new copy of it, or builds the missing link. Every problem has a fix. The blockedBy field only carries forward the path to a fix while the agent builds that path. It is never the final state of a row. It is never a resting place, and never a way to end a turn with the work still undone.

22.2 Add Architecture Improvements to the PRD Automatically

The same rule applies to a clear chance to improve the code structure that the agent notices while doing the user's task. Examples: a hand-written piece of code that a well-known library already does better, or an ad hoc multi-file system that one import could replace. Other examples: duplicate logic that needs one shared helper, or a repeated pattern that one existing tool already covers. The agent does not defer these to a separate session. The agent adds each one to the PRD in the same turn it notices it, and finishes it before COMPLETE.

The bar for adding this kind of row is: the improvement is clear, and the agent can reach it from this session. This bar excludes a speculative change or a change made only for looks. Replacing local code with a library is a specific case of this rule. Before the agent keeps a local copy of something a published package already does, the agent adds a PRD row. This row replaces the local copy with the library. Local code that duplicates a maintained package will lose that comparison every time.

The agent treats the architecture as changeable. The architecture is not a fixed base the agent must work around. It is a shape the agent may reshape as needed. Every architecture change that clearly improves the design becomes a PRD row right away, not a deferred idea. The same applies to a change that clearly lowers the future cost of maintaining the code. The agent is encouraged to replace custom code with a built-in feature or a well-maintained, widely-used library. The agent may only do this when the change leaves less code for the team to maintain. Adding a large new dependency to remove a few lines of code raises the total maintenance cost, and the rule forbids this case. The agent may make the swap only when both the line count and the maintenance burden go down.

22.3 The Jank Sweep

At SPECIFY, the agent lists in the PRD every possible item of unfinished or rough work, for every part of the system the request touches. This means every part still immature, every unfinished edge, and every path only half built. This spans the graphic interface, the user experience, and the visual interface. It also spans the state the client holds, the state the server holds, the boundary between the two, and any other part the request reaches. The word jank names the target: the sweep looks for work that is rough or unpolished or nearly done, not only for outright bugs. Each item becomes its own PRD row, including a row for performance measurement and a row for security review wherever those checks apply. The sweep covers only the part of the system the request touches, not the whole repository without limit. Inside that boundary, the sweep must be complete. Every problem the agent finds along the way gets its own debug-and-fix plan, added to the PRD in the same turn. Every small improvement the agent notices gets added too.

22.4 The Tell-Tale Sweep

The agent may find one sign of machine-written design along the way. Examples: a generic decoration, an over-explained comment, a generic placeholder name, or any other clearly machine-authored shape. This one finding starts a sweep of the whole codebase. A single instance is never a one-off local fix. It is proof that the same pattern likely exists elsewhere. The agent adds this sweep to the PRD as its own rows. One row scans the codebase. One row covers each group of findings. One row fixes and checks the fixes across every file the sweep can reach. One sign left unfixed anywhere shows that the whole codebase looks machine-made, so the sweep must not stop at the first instance it finds.

23. Browser Witness

Hard Rule: Browser Witness [PROVE, EMIT, DECIDE]

When the agent edits code that runs in a browser, the agent must check the change live in a browser. The agent runs this check in the same turn as the edit. A later phase must check the change again. A later phase's check does not replace this one.

The agent follows four steps. First, start the real system, bring the server up, and check the page loads with an HTTP 200 result. Second, call browser, navigate to the page, and wait for the global value the change affects. Third, run page.evaluate to check the exact value the change should produce, and record the value the check returns. Fourth, when the value does not match, fix the root cause and check again, per the Fix on Sight rule. The agent must not move forward on client-side behavior it has not checked live.

An edit to plain prose in a static document, with no change to JavaScript, canvas, or DOM behavior, does not need this check. The agent must state this exemption and its reason directly, so the skip can be reviewed later. Skipping the check silently, when the change does affect real behavior, is a forced and incomplete closure of the task.

This rule applies at three points. PROVE checks right after the edit. EMIT checks again after emitting the code. DECIDE runs the final check before closing the task.

A check against a mock DOM (Document Object Model) can pass fully while proving nothing real. It finishes green and says nothing about how the page truly runs. The Browser Witness rule replaces this mock check with a check on the real, live page. A passing check and a working feature then mean the same thing. Only a check against a real, live DOM counts as proof that a client-side change renders correctly. A mock is a model of the page. It is not the page.

23.1 The Live Page Is the Debugger

To debug the client, the agent puts the state it needs into window.* globals. The agent then reads these globals directly with a page.evaluate loop against the real running page. The agent must not restart the app blindly and look at it by eye. Each session already captures the console, error, network, and performance streams, so the evaluate loop can read even more than the page itself would print. Restarting and watching gives almost no new information each cycle, and costs a full turn. Exposing a global value and reading it with page.evaluate gives the exact live state in a single call. There is no restart and no rebuilding of state. When client behavior is unclear, the agent exposes the relevant state as a global, reads it live, and checks it against the expected value. The agent must not guess again across a restart. The live page is the debugger: the same page.evaluate call that checks an edit (section 23) also finds the cause of a bug in it. The step from editing to COMPLETE is blocked until this check has run (see client-edit-no-witness, section 43). No client-side behavior reaches a final phase unchecked.

24. Nothing Fake

Hard Rule: Nothing Fake [PROVE, EMIT, DECIDE]

What the agent ships must run against real services, real data, and real binary files. The agent must not put a stub, a mock, or a placeholder return value into source code the user will run. The same ban covers a path that only works with test fixtures, a "TODO: implement" note, a hardcoded sample response, and a demo-mode fallback. Code like this passes a check now, but reaches production and misrepresents what actually works.

Scaffolding and thin wrapper code are allowed when they call through to real behavior. Examples: an empty file placed before the agent writes its body, or a thin adapter that wraps a real upstream API. A build target that compiles, but is not yet wired to anything and calls only itself, is another example. The test is: if the agent runs this code, does it do the thing it claims to do? When the answer is no, the code is a stub.

Before the agent writes a wrapper or adapter, the agent must check whether an existing library or tool already does the same job. Keeping a local copy of something an upstream package already solves is its own failure. The local copy drifts out of date and collects bugs the upstream package has already fixed.

The agent finds a stub by what the code does, not by a keyword in it. A stub is code that always succeeds. A stub also always returns the same value regardless of its input, or skips a real call just to satisfy a type signature. A comment that claims the code is real does not make the code real.

A stub shipped in the product looks completely trustworthy while proving nothing. It returns a clean result, it passes its check, and it has no connection to the behavior it claims to give. The Nothing Fake rule bans this class of code from the source entirely. Real code must produce every witnessed check. The Nothing Fake rule bans code built only to pass a check without doing the real work. Together these two rules mean: no fake witness, and no fake code standing behind a real one. The same real-execution rule applies to related coding practices. A comment should not exist by default. A comment earns its place only when it states a fact the code's own structure cannot show. Examples: a hidden constraint, a workaround for a specific bug in another system, or a rule a reader would not expect. A comment must never restate what the code already says in a second, separate form that can drift out of sync. The agent must not create a test file such as *.test.*. The agent must not use test fixtures or a mocking library, because these are a stub-shaped way to fake verification. The agent must not use a decorative Unicode symbol, because a running program can never check whether a decoration is correct. The only real form of verification is running the real service and watching the real, live result. A fixture must never stand in for the real system.

25. Web-Search Before Pause

Hard Rule: Web-Search Before Pause [SPECIFY, PROVE, EMIT, DECIDE]

The agent may need to send pause, or ask a question in the conversation, whose answer likely exists on the public web. Examples: a missing artifact, a prebuilt binary, or the status of a library. Other examples: a build recipe, a version compatibility fact, an upstream issue, or "does X exist for Y". Before doing either, the agent must first run WebSearch and at least one targeted WebFetch. The agent may pause or ask only after the web search returns nothing useful, or returns options the agent has already checked and ruled out.

Pausing on a question the web could answer is a stall disguised as caution. Fix on sight: return to planning, search the web, then resume the task.

Some questions genuinely need the user: a private credential, or a choice between options the agent has already presented. Another example is approval for a destructive action that cannot be undone.

This rule targets the agent stalling on a question the public web already answers. Stalling makes the user wait for an answer the agent could find itself. This follows the general rule of agent autonomy: when the agent can find an answer itself, finding it is the agent's job, never the user's.

26. Zero Standing Test Files, Live Witness Only

Hard Rule: No Test Files, Ever [VERIFY, COMPLETE]

The project has no standing test file of any kind, not one file and not many. The agent must not add a *.test.* file, a *.spec.* file, a test/ or __tests__/ directory, or a jest/mocha/vitest/pytest/unittest import, ever, for any reason. Verification runs a live exec_js or browser dispatch against real data and the real system. This dispatch runs in the same turn as the change it checks, and it reads the real output. A failed check sends the task back to PROVE.

A test file of any kind, single or many, standing in for that live check is the same rule violation. It reports a pass the real path never produced. When a behavior needs a check inside the page, the agent registers it in window.__debug and asserts it from a live browser dispatch, not from a file on disk.

26.1 A Budget on the Witness Pass, Not a File

The verification effort for an EMIT pass is a budget, not a target to fill. Each witness must check one behavior the system depends on. A repeated assertion inside one dispatch is dead weight, and the agent must remove it. Each subsystem starts with its own witness pass, but the normal outcome is to combine passes into one dispatch. An example: checking profiles+observability+auth+context together against one running system. Combining passes keeps the total witness effort growing at the same rate as the number of subsystems, not faster.

26.2 Use Overlap to Remove Passes

When witnessing subsystem A also exercises subsystem B as a side effect, subsystem B does not need its own separate witness. Real examples: the agent-machine tool-loop witness also exercises the bash dispatch code, and the dashboard witness checks the API surface and the tool registration together. A gateway witness that runs one platform through a stub-shaped loop covers all 18 adapters at once. Overlap is a signal to remove the now-redundant pass, not to add another assertion.

26.3 Keep Each Witness Dispatch Focused

Every witness dispatch should stay small and targeted, never grow into a standing suite. When one dispatch grows unwieldy, the agent splits it by concern or combines it with an adjacent live check, never converts it into a file that persists on disk between sessions. When a single dispatch cannot cover every behavior, the agent runs more dispatches, never authors a test file to hold them.

26.4 How to Name a Combined Witness Pass

The agent names a combined witness pass by joining its subsystem names with a + sign, for example home+config+skin, mcp+swe+distributions+account+credpool, or env+pi+cli+tui+setup+website. A pass covering 4 to 6 subsystems is a healthy size. A pass covering only 1 subsystem should raise a question about why it stands alone.

27. Sync-Before-Emit

rs-codeinsight and rs-search must run against a freshly built index before they give output. The digest is made of the file modified-time sum, the git HEAD, and a dirty-tree marker. The cache only serves a result when this digest exactly matches the live filesystem state. The default path always builds a fresh index. The --read-cache flag needs an exact match with .codeinsight.digest, and the system rebuilds automatically when the match fails.

rs-search runs its scan, embed, and sweep steps before it returns its first result. It prints [index fully synced: ...] so the freshness of the index is visible. Giving output from an index that is unchecked or only partly built means acting on a state of the files that no longer exists.

28. Auto-Recall on Prompt-Submit

The auto-recall verb runs at the start of every turn. It builds a 2 to 6 word query from the prompt, and calls the rs-learn Searcher through the shared tokio runtime. It then inserts a "## Recall for this prompt" section into the next instruction response, before the agent acts on the turn. Auto-search, which uses codeinsight, runs once at session start. Auto-recall runs on every prompt. The spool carries this mechanism. It is not a callback tied to one host's prompt-submit event, so every harness that loads gm-skill gets the same behavior.

Every turn therefore starts with prior memory already loaded. An agent that skips the ORIENT step still receives the auto-recall result. The ORIENT step adds 3 to 5 more targeted queries on top of it.

29. Implicit Skill Prose

A skill file or system prompt must bring out a behavior in the model. It must not describe the behavior. The agent writes short, direct rules whose wording matches patterns the model already knows, not numbered steps that spell out each action.

Skill prose must not contain a numbered list like "1. agent runs N parallel calls 2. then writes 3. then...". It must not cite a site page or a paper section number. It must not reference the documentation as a source, for example "as described in docs/skills.html". It must not contain a multi-step recipe. A skill is a prompt, not a manual. When a skill reads like a manual, the model copies it as a fixed script. The script then breaks at the first case it did not expect.

The papers and the site are outputs of this discipline. They are not inputs to it. A rule that applies across many parts of the system, and needs a citation, belongs in AGENTS.md, not in a skill file. The project's root CLAUDE.md file only points to @AGENTS.md. The agent writes nothing else directly into CLAUDE.md.

30. The Spool Dispatch Surface

Hard Rule: Every Dispatch Through The Spool [SPECIFY, PROVE, EMIT, DECIDE]

Code execution and every utility verb write a file to .gm/exec-spool/in/<verb>/<N>.<ext>. The language verbs are: nodejs, python, bash, typescript, deno, go, rust, c, cpp, and java. The host verbs are: fs_read, fs_write, fs_stat, fs_readdir, kv_get, kv_put, kv_query, fetch, exec_js, env_get, recall, codesearch, memorize, browser, and health. The git inspect verbs are: git_status, branch_status, git_log, git_diff, git_show, and git_branch. The git mutate verbs are: git_add, git_commit, git_finalize, git_push (stage, commit, and push), git_checkout, git_fetch, git_rm, git_revert, and git_reset. The orchestrator verbs are: instruction, transition, phase-status, prd-add/prd-resolve/prd-list, mutable-add/mutable-resolve/mutable-list, memorize-fire, residual-scan, and auto-recall. Output lands at out/<verb>-<N>.json for a nested verb, and at out/<N>.json for a root verb.

Git is a first-class spool surface. It is never a shell command. The dispatch gate denies any bash/sh/powershell body whose command is mostly git (deviation.bash-git-bypass), and the denial names the matching git verb. The Bash gate denies inline tool arguments, JSON-form dispatch, and any attempt to bypass the spool, for example Bash(node script.js) or Bash(python -c ...). Only gh runs directly through Bash.

A prose or API-call surface has a real cost. Each call negotiates its capability inline, in natural language. The system re-parses and re-checks each call. No call leaves a persistent record. No gate sits between intent and execution. The spool removes this cost. It moves the instruction off the prose channel. A complex operation becomes a file write to a fixed path. It is not a described intent that an interpreter must recover. Git shows this most clearly. Session close used to cost four or more separate Bash events: a porcelain probe, an add, a commit, a push. Each event was a separate round trip. The agent had to sequence these events correctly by convention. The porcelain-witness step depended on the agent remembering to run the probe as its own event. This convention-dependent correctness is exactly what the spool ABI removes. git_finalize {message} reduces this to one dispatch. It stages all changes, commits them, checks porcelain again (it refuses to push over a dirty tree), pushes with rebase-retry, and emits git.commit/git.push witnesses. Four or more turns become one turn. The porcelain gate becomes internal and structurally impossible to forget, rather than dependent on convention. The dispatch ledger shows the whole flow, rather than scattering it across shell history. Inspect verbs (git_status, git_log, git_diff, git_show, git_branch) and granular mutators (git_add, git_commit, git_checkout, git_fetch, git_rm, git_revert, git_reset) cover the rest. The agent never needs raw git. All these verbs route through one host_git import. That import resolves to the .exe file directly, because a Windows .cmd shim would defeat windowsHide and show a terminal window. The import accepts a JSON argv array, so a multi-word commit message survives intact instead of splitting on whitespace. The general rule: a capability reached through a verb is auditable, gated, and portable. The same capability reached through the shell has none of these properties. It is a free-text surface with no persistent trace.

File-based dispatch makes the channel readable. A request survives context compaction. A response stays auditable after the fact. The ledger tells executed work apart from merely narrated work. This is the system's sharpest cut between signal and noise. Tool-call arguments are temporary: scoped to one call, not persistent, not replayable, and not inspectable without re-running the agent. This is the same cost problem named above. A file-based surface reverses each of these properties. The request sits durable on disk before the watcher reads it. The watcher runs as a process separate from the agent. The response is one JSON file, auditable by any tool that reads a directory, with no need to re-run anything.

The agent-facing surface is one file per dispatch. The watcher writes out/<verb>-<N>.json (or out/<N>.json at root) when a verb completes. This file carries the result plus metadata: exitCode, durationMs, timedOut, stdout, and the thrown-error stack. One read tells apart a clean finish, a budget kill, and a data return. Streaming execs keep incremental stdout/stderr in host-owned internal stream files. The agent never parses these directly; it reads only the resolved JSON.

The Bash gate enforces this boundary. Any attempt to run code outside the spool, such as node script.js or an inline python -c command, gets a denial. The denial throws an error and names the correct spool path. It does not turn the call into a form that fails on its own. This is the only execution surface the discipline recognizes. Any other surface leaves no way to check whether the call ran at all. Independent research supports this constrained-surface choice. SWE-agent names its Agent-Computer Interface as the main reliability lever. Recent fault-tolerant-sandbox work converges on policy-based interception plus transactional filesystem snapshots as the safe baseline for execution.3,12

from the gm field guide One folder. One contract. The watcher reads, the agent writes, and the output lands in three files. An agent that tries to skip the folder finds out fast that the folder is not optional.

31. The Mutables File as Co-Equal Hook Gate

Hard Rule: Mutables File Co-Equal With PRD [SPECIFY, PROVE, EMIT]

.gm/mutables.yml lives alongside .gm/prd.yml. Every unknown found during SPECIFY becomes a row with status: unknown. The dispatcher blocks Write, Edit, NotebookEdit, git commit, git push, and the stop checkpoint while any row still has status: unknown. A row changes to witnessed only once witness_evidence holds real proof: a file and line number, a codesearch hit, or an exec output snippet.

Section 3 tracked each named mutable only inside the context window. A fact "tracked" purely in reasoning disappears on compaction, on restart, or when a subagent spawns. This in-memory tracking gives no guarantee that the fact stays around. The mutables file moves this tracking onto disk. It stores an on-disk row that the spool-dispatch gate reads on its own, apart from agent memory. This row is the durable form of the UNKNOWN or WITNESSED state.

The split between mutables.yml and prd.yml separates what to do from what must be true. A PRD item can finish its work while a mutable it references still holds UNKNOWN status. Item completion and invariant checking are separate conditions, and the dispatcher checks each one on its own.

The witness-evidence rule blocks a state change made only through narration. Evidence must take one of three forms: a file and line number, a codesearch hit, or an exec output snippet. A status change with no evidence gets rejected on read. The row stays UNKNOWN, and the EMIT gate stays closed. Before this rule, the agent could talk past this check. A file structurally refuses to let that happen now.

32. Discipline Isolation via @sigil

A discipline is a per-project namespace at <project>/.gm/disciplines/<name>/. Each discipline has its own rs-learn database and its own code-search index. This design guards against one specific failure: memory from one namespace can bleed into another and show up as a weak_prior from a different project. That prior fact can contradict the current code, or point to a symbol that does not exist. A false prior is worse than no prior at all, because it earns a level of trust it never should have gotten.

The @<name> sigil turns on strict single-discipline isolation for recall, codesearch, and memorize. Without a sigil, the default behavior is asymmetric. A read merges results from default plus every discipline listed in enabled.txt, and each result carries a rank tag naming its source discipline ([discipline:<name>]). A write, in contrast, always targets default only.

This asymmetry follows a least-privilege rule. A broad read is recoverable, because a bad prior fails at the witness step before it does harm. A broad write is not recoverable, because a misplaced fact pollutes every future read in a namespace it does not belong to. Reads stay broad. Writes stay narrow.

33. Synchronous-Under-Wasm Execution Contract

Hard Rule: Every Exec Carries A Real Timeout [PROVE - EMIT]

exec_js runs synchronously under the wasm host. The orchestrator runs the user subprocess through child_process.spawnSync and blocks the watcher for the whole duration. Every dispatch must carry a positive timeoutMs value; a missing or zero value is a hard error. On a timeout, the system keeps any partial streamed output and marks the response sidecar with timedOut: true.

This limit follows directly from how wasm runs code. Wasm gives the host no thread to run a subprocess separately. It gives no process handle across dispatches, and no port for an external process to connect to. The host runs a subprocess, blocks up to timeoutMs, then returns. No background work can run unattended after a dispatch ends.

exec_js replaces silent internal reasoning with real execution. Instead of reasoning silently about what a piece of code would do, the agent writes a hypothesis as runnable code and dispatches it. The response gives real ground truth about the hypothesis, not a guess about it. Witnessed execution replaces reasoning-as-verification everywhere (see section 3). Because of this, most of the driving model's own extended-thinking or reasoning-effort budget duplicates work that exec_js will check anyway. The recommended setting is to run gm with the driving model's reasoning-effort or thinking setting at LOW or OFF. gm replaces expensive, unverifiable internal token spend with cheap, real, externally checkable execution on the same question.

This limit is a deliberate trade-off. An earlier version of this project ran rs-exec as a native daemon. That daemon used a port file, a task store, and a set of resumption verbs (tail, watch, wait, sleep, close). It gave more flexibility, but it also caused constant operational pain. This pain included dead process IDs and port-leak races on Windows. It also included tuning for idle cleanup, and kill-tree edge cases on bash pipelines that escaped their parent process group. The wasm-only surface gives up support for long-running tasks and gets back operational simplicity. There is no daemon to supervise, no port to leak, and no orphan process to track. Recent industry and academic work supports this same wasm-for-agents pattern. The NVIDIA Developer Blog argues for WebAssembly sandboxing of LLM-generated code, and MCP-SandboxScan defines a WASI sandbox for untrusted MCP tool execution.20,19

Browser sessions are the one exception to this rule. The browser verb opens a managed Chrome session, and the wasm host keeps this session open between dispatches. The session's state lives outside the wasm instance itself, inside the Node process that hosts it. A browser session stays open across turn-stops. It closes only on a real exit reason: clear, logout, or prompt_input_exit. The running_task_ids field on every dispatch response lists any open browser sessions, so the agent sees them on every turn.

34. Hook Denials Throw, Never Mutate

Hard Rule: Throw on Denial [SPECIFY, PROVE, EMIT, DECIDE]

A hook that blocks a tool call throws an error, and that error carries a direct instruction as its text. The hook does not rewrite the call's arguments into a form that fails on its own. It is not a shell command that exits with code 1, and not a Node one-liner that writes to stderr and calls process.exit. The thrown error is the whole denial surface.

The difference matters in how the model reads the failure afterward. A thrown error reads as a policy refusal. The model updates its understanding of the surface and tries a different tool next time. An argument-mutation that produces the same exit code reads differently. It reads as "the tool is broken". This reinforces a wrong model of the system, and it turns a one-time denial into a retry loop that never converges.

This rule applies to every denial-issuing hook: throw an error, never mutate the call. A thrown error signals: use a different tool. A mutated call signals something else: run this corrected call instead. That second signal is rarely what a guardrail should send.

35. CI Is the Build

Hard Rule: Push, Watch, Fix On Red [PROVE, EMIT, DECIDE]

For the Rust crates in this org (rs-plugkit, rs-search, rs-codeinsight) and for the gm publish chain, git push triggers the build pipeline. cargo build and cargo test never run locally. A toolchain mismatch, an rustc version difference, or a missing system dependency never blocks a push. Push first, then watch CI through gh run watch dispatched over the spool, and fix any red result.

The real witness for a Rust crate is green CI on the pushed HEAD commit, not a green local build. Every crate compiles to wasm32-wasip1 as a cdylib, and that compiled artifact is what actually loads and runs. A local cargo build proves nothing about the wasm import surface or the contents of the published tarball.

The cascade pipeline gives this witness. A push to a sibling repo fires cascade.yml (through gh workflow run plus a PUBLISHER_TOKEN) into rs-plugkit/release.yml. That workflow rebuilds the wasm module and publishes it to plugkit-bin Releases and to npm as plugkit-wasm. It then bumps gm.json::plugkitVersion and the sha256 pin. That version bump triggers publish.yml. It uploads a gm-skill-VERSION.tar.gz GitHub Release from the repo root. The repo root is itself the published artifact, with no npm registry involved. It also tags a fresh gm-skill release. The real witness sits at the far end of this chain, not at its start.

This pairs with Browser Witness (section 23). Both follow the same witnessing principle at a different execution boundary. In each case, the witness must live outside the agent's local environment, because the local environment cannot answer the question on its own.

36. The Residual-Scan Stop Gate

Hard Rule: Stop-Checkpoint Residual Challenge [COMPLETE]

When .gm/prd.yml is empty or missing, and no browser session is open, and no task is running, the stop-checkpoint gate fires one residual-scan challenge. This challenge fires before the gate allows the agent to stop. The agent must then do one of two things. It can re-enter planning, add to the PRD, and do the work, or it can state directly "residual scan: none reachable in-spirit". The marker file .gm/residual-check-fired makes this challenge fire only once per stopping window. The marker clears at the next prompt submission, so the next stopping window starts fresh.

An empty PRD is a needed condition for done, but not enough on its own. The PRD records work the agent already decided to do. The gate instead checks the complement of that set: work that should have been decided but was not. This gap is exactly where a session can stop too early. It finishes every item it wrote down, stops, and leaves real remaining work undiscovered.

The gate fires only once per stopping window, so the gate itself does not become noise. A second refused stop in the same window would loop without ever ending. The marker clears at the next prompt submission, and that starts a fresh window.

This gate pairs with Maximal Cover (section 17, the in-spirit boundary set at PLAN). It also pairs with Fix on Sight (section 22, PRD folding done at EXECUTE time). This gate is the COMPLETE-phase backstop that catches what those two steps miss.

37. Meaning Through the Agent, Mechanics Through Code

Hard Rule: Semantic Work Is the Agent's Own Judgment [SPECIFY - PROVE - EMIT]

A task whose correctness depends on real understanding is the agent's own judgment, made inline, never a separate model call. This covers tasks such as summarizing, classifying, and extracting intent. It also covers rewriting, translating, removing semantic duplicates, scoring, labeling, and deciding whether two pieces of text mean the same thing. plugkit is the harness, and the agent is itself the model plugkit dispatches. So the agent makes each semantic decision on the spot, from the situation in front of it. When the work covers many independent items, the agent fans them out as N parallel spool dispatches in one message, one item per dispatch.

A regular expression that tries to decide a meaning question produces noise disguised as a real answer. It runs, returns a value, and that value bears no real relation to the question. Meaning routes to the agent's own judgment. Mechanics route to deterministic code. Each engine handles only the work it does well. Mechanics means parsing, sorting, hashing, and counting, all decidable by a fixed procedure. Meaning means understanding language. Is this change a fix or a feature? Does this docstring contradict its function? Do these two error messages mean the same thing?

A keyword list or a regex over meaning-bearing phrases is the same failure named in Nothing Fake (section 24). Here it applies to judgment instead of code. It looks correct because it runs and returns, but it has no real connection to what was asked.

Fan-out is the parallel half of this rule. N independent items become N parallel dispatches in one message, never one batched call. A single batched judgment call dilutes the signal for each item by averaging across the whole batch. The added cost of fan-out is small, and the gain in judgment quality is large. This mirrors memorize-fire's own fan-out rule (section 12): one unit of work per call.

38. The Continuation Invariant: A Toolless Turn Is A Stop

Hard Rule: While The Chain Is In-Flight, Every Turn Ends In A Tool Call [SPECIFY - PROVE - EMIT - DECIDE]

Every programming agent reads only tool calls and their outputs. An assistant message that ends in prose with no tool call is the end of the turn, and the harness stops there. So while the chain is still running (phase not equal to COMPLETE, or prd_pending greater than 0), the agent never ends a turn in prose. It never writes a summary or a recap; a summary is itself a stop. The only event that allows a prose-only turn is plugkit returning phase=COMPLETE and prd_pending=0. Before any apparent stop, the agent dispatches phase-status and checks the result again. A non-terminal phase means the urge to stop was a mistake, and the fix is to dispatch instruction and keep going.

This rule targets the main mechanical cause of long-horizon failure. A completed sub-piece of work, plus a "here is what I did" paragraph, plus zero tool calls, reads to the harness as a terminal state. This holds regardless of the agent's real intent. No amount of in-context reminder to "remember to continue" survives this. The closing sentence and the stop are the same event by construction.

This failure has two faces. One is the summary, which looks backward. The other is deferred intent, which looks forward: a final sentence naming the next move instead of making it. Deferred intent slips past a summary-only rule because it reports itself as a continuation. The fix is the same for both: take the described move in the same turn, with no exception for surfacing a decision. A decision lands through a tool call, never through prose alone.

This rule reverses the usual default. The default is not "continue unless done". The default is instead "dispatch until the gate says done". Doneness is plugkit's own COMPLETE-gate pronouncement, never the agent's self-report. A self-reported doneness replaces the gate's judgment with the agent's own judgment. This is the main cause of premature stopping on long tasks.

This rule depends only on the verb spool. It needs no hook, no stop-interceptor, and no platform-specific continuation feature. Each of those would tie the system to one specific host, and each would create a single point of failure. The rule itself is prose served through instruction. It produces the same behavior on any model that reads text and calls tools. This is the only way to get predictable behavior across different hosts.

38.1 Terse Output

Prose around tool calls stays limited to real content: an actual finding, a one-line decision with its reason, or a blocker. The system suppresses ordinary output such as boot-probe narration, dispatch echoes, restated prose, and status recaps. This terseness rule works together with the continuation invariant above; it never overrides it. Terse means shorter text, never zero tool calls, and never silent work. Output shrinks toward zero exactly where the tool calls already carry the meaning on their own.

39. Spool Dispatch Replaces Platform Hooks

Hard Rule: The Gate Is The Spool, Not A Host Hook [SPECIFY - PROVE]

Marker files in .gm/ track orchestration state, and the dispatch layer gates on those files, never on an agent-host hook event. No skill prose, gate denial, or instruction names a host-specific invocation form, such as a plugin-namespaced skill or a host-specific subagent type. The action that satisfies a gate is always a portable spool dispatch: write .gm/exec-spool/in/instruction/<N>.txt, then read the response.

An earlier design used host PreToolUse hooks. Those hooks emitted host-specific permission JSON and named host-specific skill or subagent forms. This design created hidden coupling. Under a different harness, the hook either never fires or names a form that does not exist there, and the gate silently stops working. Subagent orchestration made this worse. An isolated subagent that returns a prose summary reads as a stop to its parent session (see section 38).

The replacement uses marker files plus spool dispatch. checkDispatchGates reads .gm/prd.yml, .gm/mutables.yml, and the needs-gm/gm-fired markers. It returns an allow or deny result that names the next portable verb, never a host-specific tool. Every behavior the old hooks enforced now survives as a spool gate that works the same way on any host. The old wasm_hooks exports remain in the code as dead interface with no caller.

40. The Memory Architecture: File-Vec Recall and the rs-learn Algorithm Layer

Memory has two layers: a live layer and an algorithm layer. The live layer is the file-vec store. memorize-fire creates an embedding using the in-wasm bge-small model. It then writes two files for each memory: the text under .gm/disciplines/<ns>/<key>.json, and its 384-dimension embedding under .gm/disciplines/<ns>-vec/<key>.json. recall and auto_recall read this data fresh each time. Each result gets a score from cosine similarity multiplied by recency, using a 30-day half-life and a 0.4 floor. Duplicate results get removed by Jaccard overlap. This store lives in git and stays scoped to one project.

Pruning bad memory matters as much as writing good memory. A false-positive recall hit is worse than a miss. It poisons every future query that matches it, not just the one query that surfaced it. memorize-prune removes the text and its embedding together, in one atomic step. It works either on an explicit key or on a review-only candidate query. It never removes by blind similarity match, because an automatic similarity-based prune would itself generate bad memory. Precision matters more than keeping every memory.

The algorithm layer is a separate wasm cdylib named rs-learn. It holds five continual-learning cores. The first is an instant rank-2 Hebbian MicroLoRA core with a norm bound and EWC correction, derived from the sona method. The second is an EWC++ deep core with an online Fisher exponential moving average and z-score boundary detection. The third is a bi-temporal knowledge graph, derived from the graphiti method. It invalidates a contradicted edge rather than deleting it. A query can ask for the graph's state at any past point in time. The fourth is an 8-head graph-attention layer using relation and recency as edge features. The fifth is a FastGRNN router that combines a sparse matrix with a low-rank matrix. It explores model choices with an epsilon-greedy policy over model, context bucket, temperature, top_p, and confidence. rs-learn owns no input or output of its own. It imports host_kv_*, host_vec_search, host_log, and host_now_ms, and exposes one JSON dispatch surface.

This design keeps the concerns apart: the host owns input/output, scheduling, embedding, and transport, and rs-learn owns math only. This split lets each side be tested alone, and lets any host that supplies the same six imports reuse rs-learn as-is. The agent-facing spool reaches it through plugkit's learn verb. That verb routes through dispatch_json over a PlugkitKv backend (a three-method KvBackend trait built on kv_get, kv_put, and kv_query). This split also makes results reproducible: the learning cores hold no platform-specific assumption, and the host holds no learning-rate constant of its own.

Each dispatch to the learn verb builds a fresh LearnSession, because the host itself holds no state between dispatches. Any state that lives only in that session's memory disappears once the dispatch ends. This does not affect the bi-temporal graph, because every edge writes straight through host_kv_* and becomes durable on write. The three cores that hold learned weights (the MicroLoRA/EWC adapter, the FastGRNN router, and the GAT attention layer) persist their state explicitly. Each writes its learned tensors to a fixed KV namespace after every update, and reloads them lazily when the in-memory slot is empty. Only genuinely learned values persist this way: low-rank weights, quality counters, feedback counts, and edge-feature weights. Matrices that start from a fixed seed get rebuilt from that seed instead. A load checks tensor dimensions first. A mismatch rebuilds the tensor clean from config instead of loading corrupt data, so one bad run cannot poison a later run. Each namespace resolves under the project's own .gm tree, so no project's learned weights leak into another project. This design keeps each core continual across dispatches, rather than starting fresh and forgetting everything each time.

The router ties into the turn lifecycle directly. Every instruction dispatch creates an embedding of the active prompt and routes it through FastGRNN. This adds a route_hint to the response: a recommended model, temperature, top_p, context bucket, and confidence score. A fresh project falls back to a fixed rule policy (algo: rule). Once enough record_outcome dispatches cross a set trajectory threshold, the router switches to its learned low-rank weights and explores off-policy choices with an epsilon-greedy strategy. This hint is advisory only; nothing forces the agent to follow it. In concrete terms, model selection becomes a learned policy. It is set per turn and saved across the whole life of the project, rather than a fixed constant reset every turn. The hint's prompt embedding reuses the same per-query cache the recall path already uses, so no second embedding pass runs.

The MicroLoRA core learns to score, not to transform embeddings. It is a rank-2 adapter over a 384-dimension bge-small vector that emits one score per target (apply_adapter: logit[k] += B - (A - embedding)). A feedback call nudges the factors A and B using one trajectory-quality score between 0 and 1. This update is norm-bounded and EWC-corrected, so a new adaptation never erases an earlier one. This core learns which targets this project's embeddings should favor. The quality signal behind this update is something only the model in the loop can supply. So the agent reports it itself at the close of each turn, and the head's weights move toward the targets that score well. The router learns which model to dispatch. MicroLoRA learns to score this project's targets. Both learn from the same self-reported signal. One open piece of integration work remains: wiring this head's score into recall re-ranking.

This self-report closes the loop from end to end. The bi-temporal graph fills itself in automatically. Every memorize-fire call inserts a graph edge using the same embedding it already computed for file-vec storage, at no extra embedding cost. A prune invalidates the matching edge in the same step, so no edge points at deleted data. Because plugkit is the harness and the agent is the model it dispatches, the model already knows its own identity and its own outcome. It reports both directly. rs-learn never calls out to get that judgment; it states the need, and the agent supplies the answer.

41. The WASM Migration

The orchestrator runs as a WebAssembly cdylib, loaded by agentplug-runner, a sha256-verified native wasmtime host published for each platform. The wasm module itself does not depend on any host: one sha256-pinned module runs the same way on every platform the runner supports. The orchestrator needs no per-architecture build, and the user needs no platform-specific install path. The wasm module imports a small host contract: filesystem access, key-value storage, vector search, fetch, subprocess, clock, and log. The runner supplies all of these natively. The wasm module holds the logic; the host holds the input and output. The wasm module also routes plugin calls out to shared sibling modules. The same wasm module loads under any host that supplies this same import contract.

The orchestrator's own code stays small, and a separate plugin supplies the embedding model. The orchestration logic (the state machine, gates, dispatch, and verb routing) compiles down to a few megabytes, and this is the entire content of gm.wasm. The embedding model does not live inside this module. Instead, BAAI/bge-small-en-v1.5 (12 hidden layers, 384-dimension output, a safetensors weights file plus its tokenizer) ships as a separate sibling plugin named bert.wasm. agentplug-runner loads this plugin once and shares it across every project registered on the machine. Embedding still runs entirely on the local machine, with no delegation to a host process and no external service call. So it stays offline and never leaks text by construction. The large embedding-model download happens once per machine instead of being bundled into every artifact. The orchestrator itself stays small enough to update on its own separate schedule.

Keeping the orchestrator to one file gives it stability. Every write to that file is atomic: it writes to a temp file first, then renames it into place. If the running instance's version differs from the on-disk version file, the orchestrator triggers a clean self-restart rather than a partial reload. The system checks embedding initialization through embed_init_ok before the first recall runs. Shared resources (key-value storage, the vector index, and the embedding model) stay owned by the host. They stay shared across every verb dispatch in a session, so the model loads only once per session.

42. The Rust Service Crates: codeinsight, search

This project keeps two zero-dependency static Rust crates, and folds execution directly into rs-plugkit. Language execution used to live in a standalone crate named rs-exec. This covers nodejs, python, bash, typescript, deno, go, rust, c, cpp, and java, all run through the spool. So did browser sessions, per-call timeout, and task isolation. That crate required a mandatory positive timeout on every call. It ran subprocesses synchronously under the wasm host, and it blocked the watcher on an unbounded child process. rs-exec is now retired; its surfaces run directly inside rs-plugkit's wasm_dispatch instead. rs-codeinsight gives an AST-level view of a codebase. It uses tree-sitter across thirteen languages and analyzes a 500-file project in under 200 milliseconds in one pass. So the agent learns an unfamiliar repo's files, symbols, and shape without running exploratory searches. rs-search is a hybrid finder. It combines BM25 lexical scoring, using identifier-aware tokenization that splits snake_case, kebab-case, and camelCase names, with vector similarity through Reciprocal Rank Fusion. It respects .gitignore, ingests PDF files, and keeps a content-addressable embedding cache, so a re-index only re-embeds content that changed.

Model selection keeps meaning and mechanics apart across the whole stack. Semantic work, such as summarizing, classifying, or judging equivalence, routes to a small fast model through fetch. It runs one item per call, in parallel by default. Mechanical work, such as parsing, sorting, hashing, and counting, stays in deterministic Rust code. The bge-small model gives a 384-dimension embedding at a small weight footprint relative to its recall quality. This split follows the same reasoning as the wasm migration and the rs-learn boundary above. Each layer owns one concern: the model owns meaning, Rust owns mechanics, the host owns input and output, and the algorithm crate owns math. Each layer can be tested, reproduced, and swapped out on its own.

This static split fixes which engine handles a given kind of job; it does not fix which model handles a meaning-based job. FastGRNN makes that second decision. The per-turn route_hint (section 40) recommends a model, temperature, and top_p, learned from this project's own prior turns rather than fixed as a hard-coded constant. These two decisions compose. The layer-concern split decides model-versus-Rust in a fixed way. Within the model tier, the router turns the choice of which model into a learned policy. This policy is saved per turn, and it compounds across the life of the project. Agent-as-LLM applies the same one-concern-per-layer rule one level up. The harness owns orchestration, and the router owns the model-selection policy, with neither hard-coded into the other.

43. Deviation Gates: Predictability Across LLMs

The goal for cross-model predictability is a worst-case target. A weaker driving model should reach the same reliability floor as a strong one, because the gates hold the line, not the model's own capability. The gates hold this line through pure on-disk-state checks. These checks fire the same way under any LLM or any harness, never by trusting the model to behave well. long-gap-no-instruction refuses a non-orienting verb when more than 5 minutes have passed since the last instruction dispatch. complete-chain-poll flags a re-dispatch of instruction on a chain that already reached a terminal state. push-dirty refuses a push from an unclean worktree. client-edit-no-witness refuses a COMPLETE transition when a client-side edit has no matching browser witness. A gate never changes the command it receives. It only returns a refusal, and that refusal's text is itself the next instruction. So it steers a weak model the same way a strong model already steers itself.

A gate's signal quality depends on its accuracy: it must fire on real agent mistakes and stay silent on the mechanism's own routine bookkeeping. Two refinements make this work. First, the long-gap clock resets whenever the watcher restarts fresh. A gap caused by a version upgrade is not the agent's fault, so a fresh boot stamps the last-instruction time to now. Second, complete-chain-poll fires only for dispatches tied to a real session. A cron job or a stop-checkpoint probe with an empty body against a terminal chain is not the agent re-polling. Counting those would inflate the rate without reflecting real agent behavior. This generalizes: a deviation is an agent action that goes against discipline. So a gate must tell an agent's own dispatch apart from the harness's own internal bookkeeping, or the gate ends up measuring the wrong thing.

Three-Layer Admission Filter

Sections 2-37 each apply one shared rule. Every candidate action must pass three separate checks, in order, before the agent may commit it.

candidate to [L1 cost] to [L2 bounds] to [L3 direction] to execute

L1 Cost. The agent must measure the real cost of an action before it commits the action. An unmeasured cost claim is not admissible. ORIENT (section 21) gives the agent its baseline measurement.

L2 Bounds. Only one writer may act on a given surface at a time. Each managed resource has a hard limit; when the agent hits that limit, it must place new work in a wait queue. A state change made outside an approved surface cannot be reconciled with the true state, so the discipline forbids it.

L3 Direction. Each accepted write must move the task closer to done, never further away; a write that does not make progress is rejected. Each accepted write gets an audit record: an id, a hash, and a timestamp. The system classifies the recent run of writes as one of four types: convergent, flat, divergent, or chaotic. Work must stop when the run is not convergent. The DECIDE phase checks four facts together as the sign of real convergence. The worktree is clean, and the remote branch has the latest push. The PRD list is empty, and every mutable is witnessed.

Closure anti-shape. This is the most common way an agent fails the L3 check. The agent's own response text is never a valid place to make a change. When the agent writes an action inside its response instead of sending a real dispatch for it, the action fails L3: it gets no id, hash, or timestamp; the recall index never sees it; the trajectory classifier never counts it; and the gate does not let the agent advance. The system detects this failure by its structure, not by checking a list of known bad phrases.

Maturity-first emit. The agent's first attempt at a change must complete the whole task, not a part of it. A partial change leaves unfinished work as a hidden, unchecked state, and the next session must pay the cost to work out what is missing. When a task turns out bigger than expected, the agent must split it along its real dependency links (see the Maximal Cover DAG in section 17), never split it to fit a fixed schedule.

Summary. Measuring cost first stops the agent from making an unproven optimization claim. Fixed bounds stop one runaway surface from breaking every other surface. Checking direction stops the agent from doing work that does not move the task forward. The agent can tune each of the three layers on its own, apart from the other two.

Each phase applies the filter at a different point of commitment. SPECIFY runs the L1 and L2 checks cheaply, using ORIENT and the PRD dependency graph. PROVE runs the L3 check over every witnessed change it writes to the central store. EMIT runs the L3 check as an audit of the files on disk. DECIDE runs the trajectory classifier over the four facts named above. The filter drives the work; the phases only schedule when each check runs.

Code Invariants

The rules in the instruction response apply to code, not only to process. Every file the agent writes must follow the same structural rules below.

  • Minimize state. Data must flow in one direction, in sequence. The code must check each state flag in a single phase, not spread across many phases. External input must pass through one queue before it changes any state. Every state change must be a clear, explicit assignment, never a hidden side effect.
  • Respect real hardware limits. The agent must measure real speed before it adds an abstraction layer. The code must pass scope values explicitly; a closure that hides its scope-lookup cost is too slow inside a hot loop. The code must reuse a pool of objects instead of allocating new ones. A performance-critical path must use plain native data flow; it must not use promise chains, class hierarchies, or operator overloading.
  • Keep a flat structure. The code must use flat, denormalized data over nested documents. The code must update only the changed fields, not the whole record. Transport must use raw bytes, not JSON: use varint fields of variable width, and compute the exact size once before it allocates memory. The code must sort data lexically to break ties in the same way every time.
  • Write files as vertical slices of at most 200 lines. Each file must hold one responsibility. Each file must take an input, process it, and produce an output, start to finish. The default configuration must work correctly for most projects with no setup. The code must run the same way in a browser, in Node, on mobile, and under Bare.
  • Make async boundaries explicit. The code must call async steps as sequential, awaitable operations. The code must never depend on an implicit callback order. The code must send every error through one shared error channel. Every check on async code must await a real operation; it must never use a mock.
  • Name things by their scope size. A function under 50 lines may use a short, single-letter name. A function of 50 to 200 lines must use a short descriptive name. A function over 200 lines must use a full, clear name. An iterator variable may stay short. Every public function name must state its purpose in full.
  • Fail fast, fail loud, fail the same way every time. The code must stop at once when a precondition fails. It must report the exact state at that point. A check must test the real output the code produces, not only its return value. The code must check a sentinel value and a checksum header on every read.
  • Use binary transport and append-only storage. The code must use lexical cursors to read a sparse subset of records. The code must append new records for replay, never rewrite old ones. The code must split large data into lexical-range chunks and change only the one chunk that needs the change.
  • Keep one focused task per work session. The agent must not make an unrelated code change in the same session. When this keeps the code easier to read, the agent must compute a value once and place it inline. It must not compute the same value more than once.

Token discipline. A sentence describing what code should do is waste once the code itself states it clearly. A comment is waste once a clear name and a clear structure already say the same thing. Two copies of the same logic that must stay in sync are a liability. The rules above hold through the structure of the code itself; the agent must not describe them in extra prose.

44. Discussion

44.1 Relationship to Formal Methods

gm looks similar to model checking, since both use named state variables and explicit transitions. gm also looks similar to design-by-contract, since both gate progress on stated pre- and post-conditions. gm works at a broader level than each: a gm phase marks a stage of task work, not a state inside a running program. A gm contract concerns what the agent knows, not whether the program's logic is correct. The 13 route families act like typing domains: each one marks a set of valid operations, rather than checking a property of the program itself.

44.2 Relationship to Test-Driven Development

gm has a loose link to test-driven development, since both check work before the agent calls it done. gm differs in one key way: gm checks work through real, witnessed execution during EXECUTE, not through a saved test suite. The single integration test named in section 26 is the one check the COMPLETE phase runs to check that real work happened. The 200-line file budget trades deep regression coverage for a smaller context window.

44.3 External vs. Self-Regulation

gm checks the agent's work from outside the agent, instead of asking the agent to check itself. The same reasoning process that solves a problem can also reason its way to an excuse for a shortcut. The agent's own judgment cannot catch this failure by itself. A marker-file gate reads .gm/prd.yml and .gm/mutables.yml directly; it does not depend on the agent's own judgment. Hard rules 21 through 37 live in the orchestrator's output and in marker-file gates, not in the agent's own reasoning. An earlier version of gm used a hook-event pump, so its checks worked only when that callback chain ran correctly. The current version needs only one file read to run the same check.

44.4 Overhead vs. Benefit

Each backward transition costs the agent time: it must re-plan and redo any partial work the transition discards. In real use this cost is smaller than the cost it prevents. A backward transition surfaces a problem while the task scope is still small. Without it, the agent finds the same problem only at the COMPLETE phase, after every later step has built on the same error.

44.5 Limitations

  1. The finite-unknown assumption: gm's stop condition needs a finite, discoverable set of unknown facts. This may not hold under an adversarial or a chaotic input. The two-pass reclassification rule in section 9.2 does not remove a fact that stays unresolved after both passes. When a fact stays unresolved past pass two, the agent must pause and record the blocker in the PRD header. The agent must not reclassify the same fact over and over with no limit.
  2. Witnessed-execution cost: real execution against a costly external API may be too expensive to run on some paths.
  3. The memory staleness window: time passes between when the agent writes a memory and when it checks that memory again. In that window, a stale fact can cause an error.
  4. Browser witness scope: gm runs one managed Chromium instance at a time, so browser checks run one after another, never in parallel waves.
  5. The test budget ceiling: the 200-line file cap forces compact coverage. A large subsystem may get less real-execution coverage than it needs within that limit.

45. Conclusion

The complete gm discipline has these parts. It has a phase-gated FSM. It has a framework that names each unknown fact and closes it only through witnessed execution. It has a quality discipline that runs inside each phase. It has a governance layer of seven route families and four state layers. It has a second set of rules for autonomy and scope. It has operational hard rules. It has a third set of rules that move the whole discipline onto disk, into marker-file gates.

gm is not a set of goals; it is a set of enforced rules. The spool-dispatch gate enforces every rule below the agent's own decision layer. The gate reads disk state on its own, apart from the agent. The instruction response encodes each hard rule directly, so the agent cannot reason its way around it. The agent acts inside this fixed set of limits; the limits stop the discipline from collapsing to whatever the agent judges best in the moment.

gm ships as one GitHub Release tarball and one WASM artifact, and it runs on every Claude-style host. Reliable agent work depends heavily on controlling the task lifecycle, not on model skill alone. gm moves its state out of the agent's own memory and out of the host's event system. It moves that state into files any process can read: a spool file, a mutables row, a stop-checkpoint marker, a CI run. The agent takes part in the discipline; it does not hold the discipline in its own memory. The host delivers the discipline; the host, not the agent, enforces it. gm is a working engineering tool, not a theory.

Every rule above serves one goal. gm comes from more than 14000 hours of supervised work with coding agents. Those hours went toward raising the share of each token and each action that makes real, checked progress. They went toward cutting drifting, making things up, forgetting, and stopping too soon. Cutting wasted talk serves the same goal at low cost, since the cheapest wasted signal is the one the agent never sends. Phase gates, witnessed mutables, full work coverage, the continuation rule, the spool record, and deviation gates are the set of tools those hours produced. Each one removes one specific kind of error between what the user asked for and the software gm ships.
