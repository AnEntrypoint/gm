gm: a skill that makes LLM coding agents check their work against real command output

How the checks, the gates that refuse a step, and the walks that drive a task to COMPLETE fit together, for developers who use a large language model (LLM) coding agent.

AnEntrypoint / gm
Describes gm on its main branch. The counts in section 3 come from gm-config/fsm/graph.json.
Abstract

gm is a skill for LLM coding agents. It targets three failures: acting on an unverified guess, losing resolved work when the context window fills, and declaring a task done before it meets the requirement. Section 3 maps the discipline graph that enforces the gates, section 4 gives the gates, and section 9 gives how a PRD row (planned work) closes.

gm is for developers who run an LLM coding agent in their own project. Install with the two commands in the README Install section (Node.js required), or follow install and release paths for the skill, runner and MCP server steps.

3. The discipline graph

The discipline graph is the state machine that enforces gm's gates. Its nodes are principles, tensions, gates and terminals, and its edges join them. It is stored in gm-config/fsm/graph.json (schema version 2). The policy block names the Jobs To Be Done (JTBD) node as the start of a walk (initial_phase) and G_FIXPOINT as the terminal phase (terminal_phase).

Each node carries a key, a kind, a label and a prose_key that selects its served prose. Each edge carries from, to, kind (forward or backreference), a label and its list of gate predicates. A forward edge leads onward through the graph, and a backreference edge leads back to an earlier node.

Three graph files exist. The state machine that the walk enforces, gm-config/fsm/graph.json, and its enforced copy, rs-plugkit/crates/plugkit-core/src/orchestrator/lean_graph.json, are byte-identical in the current tree, and rs-plugkit/AGENTS.md describes the copy as vendored. The hop graph is skills/dream-rsi/gm-graph.json, a catalogue of 498 nodes and 1210 edges (914 forward, 296 backreference), and the gm-orchestrate skill launches each hop from it.

4. Gates that refuse a step

A transition is a request to move along an edge. The orchestrator evaluates the gate predicates on that edge, and a failed predicate refuses the move. Six edges of gm-config/fsm/graph.json carry gate predicates: five carry one predicate each, and one carries 21. All 26 of these predicate entries name different predicates. Two gate entries carry advisory: true: lean-contract-only-description and lean-verifier-independent. Both predicates always return true, because code cannot observe their condition, so neither refuses a transition. gm-config/fsm/predicates.md also labels lean-hop-witness-receipt ADVISORY, and no graph gate names it. The other 24 gate entries carry no advisory flag, and the denial message of each contains the word blocking. gm-config/fsm/predicates.md is generated from the predicate registry and lists 28 predicates: the 26 gate predicates above, plus remote-hook-refused and lean-hop-witness-receipt, which no graph gate names. Of those 28, the file labels four BLOCKING and three ADVISORY, and leaves the other 21 unlabeled.

A condition outside the predicates in gm-config/fsm/predicates.md needs a jit hook under fsm.hooks_dir (hooks in gm-config/gm.config.json), or a Rust change that adds a compiled predicate. The denial text lives in messages.gates_dir and messages.residual_dir, and an operator can edit it without changing when a gate fires.

A denial names the failed predicate and the verb that recovers it. The denial is authoritative: the agent satisfies the named predicate and dispatches the transition again, and it does not route around the denial. A gate that names a predicate outside the compiled set emits fsm_unknown_predicate and is denied permanently, never passed.

5. Walks and completion

The agent drives a walk with the instruction and transition verbs. instruction returns the served prose for the node the walk stands on, and the agent calls it only for an orient: a fresh prompt, a phase transition, drift, or uncertainty about the served prose. transition moves the walk along an edge, and the gates of that edge decide whether the move succeeds. phase-status answers a bare state check (phase, prd_pending_count, unknowns pending). The split between an orient and a state check is stated in skills/gm/SKILL.md.

A walk ends when the edge into COMPLETE passes all of its gates (README.md, The walk). The completion checks are: the live state machine accepts COMPLETE, every required PRD row is resolved, and gm-continue has checked for remaining work (AGENTS.md). COMPLETE has a forward edge to G_FIXPOINT, the convergence point of a sweep. A sweep is one re-walk of the whole artifact, from G_DONE to G_SWEEP. It converges when a full sweep changes nothing, meaning its measures equal the previous sweep's measures exactly: no gate reopens, no counterexample is found, and the artifact does not grow (skills/dream-rsi/gm-graph.json).

The agent may stop only at G_FIXPOINT, the node one edge after COMPLETE, with prd_pending_count at zero, and the last dispatch is then Skill(skill="gm-continue") (skills/gm-continue/SKILL.md), which checks for remaining work. While a walk is in flight, every turn ends in a verb dispatch, and a turn without a tool call is a stop (rs-plugkit/crates/plugkit-core/src/orchestrator/instructions/prose/entry.md, Continuation invariant). A stop hook that re-fires is not a reason to stop (skills/gm/SKILL.md, Autonomy).

The main thread runs a walk through gm-orchestrate. A shortfall is a live count below the floor (section 8) while work is open and the machine has headroom (section 8), and each one is logged as FAILURE. A repeated shortfall restarts the walk at most twice, and a third repeat files a blocker row (section 9) and stops the walk (skills/gm-orchestrate/SKILL.md, Shortfall and FAILURE).

6. When the agent may stop or ask

The agent asks the user only at a world-scoped one-way door (a step that reaches beyond the repository, such as deleting anything with no recoverable copy, spending money, or deploying to production), the sole interruption that skills/gm/SKILL.md (Section 4) sanctions. Every other unknown becomes a PRD row (rs-plugkit/crates/plugkit-core/src/orchestrator/instructions/prose/complete.md), and the agent continues.

The rules in skills/gm/SKILL.md, Section 4, fix what the agent does without asking. A read-only step runs at once. Under git, the agent runs commits, pushes, tags, reverts, merges and every collision recovery without a question. It asks before a rewrite: a force-push, --force-with-lease, rebasing pushed commits, branch or ref deletion, or a remote reset (skills/gm/SKILL.md, Section 4). Work the user has already asked for, or a plan they have approved, is go-ahead.

The conditions for stopping are stated once, in section 5 (Walks and completion).

7. Hops

A hop applies one principle to one surface and returns one receipt that names an executed witness. A hop is one traversal of one node. The orchestrator launches each hop with one JSON payload, and skills/gm-orchestrate/SKILL.md (step 2) shows its fields.

The hop runs eight steps, numbered 0 to 7 in the skill. Step 0 applies the node's discipline to the surface, named by node.label, with node.advocate as its spec. Step 1 argues the open question in one paragraph. Step 2 lists the node's testable claims, each with its test. Step 3 searches every instance those claims govern and cites the lines it found. Step 4 closes what one exact-match edit closes, when no other writer holds the file, and witnesses the change with a live dispatch. Step 5 records every other finding as a PRD row. Step 6 names the biggest remaining need in one sentence, and step 7 nominates the next node. The receipt is 120 words at most (skills/gm-hop/SKILL.md, Receipt) and names an executed witness. A receipt without a witness does not set applied:true.

A hop never reads the graph. Its links come from the payload. gm-orchestrate builds each link from the edges of the node and sorts the links by to. Each link carries the edge's condition, when the edge has one, as its guard. A link is eligible when every guard holds on the surface. The hop nominates the next node only from eligible links, and the chain stops at depth 6, the default max_depth in skills/gm-hop/SKILL.md, with next: none, depth limit.

gm-hop directs each hop to write .gm/lean-walk/<NODE>.<SESSION>.json on every verdict, including NOT-APPLICABLE. The file lists the links offered and the link taken. The link taken is either null or one of the links offered. A principle the surface demands that is not among the links offered is appended as a line to .gm/lean-walk/new-nodes.jsonl. The appended line is not written to the catalogue.

A hop commits its own change and does not push. The orchestrator publishes the tip of each wave in one push. A hop issues at most one git_status and one git_commit, plus one branch_status only when it needs remote state, and it does not pull. A hop never dispatches gm-continue, because that dispatch is the parent orchestrator's terminal move.

8. Parallel subagents (the pool)

A walk runs its hops and PRD rows as subagents in a pool. The ceiling is the number of subagents the platform accepts at once, and the orchestrator finds it by launching: a spawn refusal states the ceiling, which pool-observe records in .gm/pool/ceiling.json. When no ceiling is recorded, spawn_ceiling in rs-plugkit/crates/plugkit-core/src/orchestrator/pool_slots/state.rs falls back to DEFAULT_SPAWN_CEILING, which rs-plugkit/crates/plugkit-core/src/orchestrator/pool_slots/mod.rs defines as 20. The floor is min(10, ceiling). While PRD rows are open, the live count, which is the count of record described below, stays at or above the floor, and the pool-floor-met gate refuses a transition while open rows leave pool slots free.

The orchestrator runs one tick, which is one pass through five steps, as skills/gm-orchestrate/SKILL.md lists them: observe, launch, log, wait, and re-count the live pool. Observe runs pool-observe, dispatched in rs-plugkit/crates/plugkit-core/src/orchestrator/mod.rs and implemented in rs-plugkit/crates/plugkit-core/src/orchestrator/pool_slots/observe.rs. It reads the body fields live (the ListAgents count), refusal (the spawn refusal text) and held (the ids of the running workers). Its reply reports the ceiling, the floor, the free slots and whether a refill is needed, and its slots block lists the launch candidates and the open rows. The full reply shape is in rs-plugkit/crates/plugkit-core/src/orchestrator/pool_slots/observe.rs. The launch step starts PRD rows first and then one hop per untraversed principle node, from the advertised ids in slots.launch (skills/gm-orchestrate/SKILL.md, step 2). Log writes each launch to .gm/pool/ledger-<wave>.txt and each tick to .gm/witness-log.md. Wait pauses for up to 600000 ms (MAX_WAIT_MS in rs-plugkit/crates/plugkit-core/src/orchestrator/wait.rs), and each completion refills its slot in the same turn before any other step. A freed slot stays empty when the reply's refill_needed is zero: when open_rows is zero, when no slot is free, or when no candidate row and no traversal entry can launch.

Each subagent brief opens by writing .gm/pool/<session>.live and deletes that file on finish. The count of record comes from the subagent list. slots.live and the ledger's live are not the count. A successor that the ceiling refuses is parked at .gm/pool/<session>.next, and the orchestrator relaunches that spec into the first freed slot.

Each failure mode has a fixed response. A subagent whose transport drops mid-run keeps its row open and frees its slot. The orchestrator resumes that subagent by SendMessage to its id. Many drops inside one window are one drain event, logged as one FAILURE ... mass-econnreset-drain-<N> line (skills/gm-orchestrate/SKILL.md). The orchestrator waits out the window and refills in two half-waves, separated by wait {"ms":15000} (skills/gm-orchestrate/docs/recovery.md). A dispatch that the serial lane (the git lane, which runs one dispatch at a time per project) starves is re-dispatched once, unchanged, and a second starvation is logged as lane-starved. A hop whose git verb is starved a second time files a PRD row (skills/gm-hop/SKILL.md). A headroom stop is separate from these. At CPU of 80 percent or more, or available memory below 2048 MB (skills/gm-orchestrate/SKILL.md, Headroom and leases), launches pause. A headroom stop does not end the turn.

9. Planned work (PRD rows) and the nine stages

Each row is one file, .gm/prd/<id>.yml. A write is a compare-and-swap of that one file, so editing one row never touches another (skills/gm-prd/SKILL.md). prd-add refuses an id that already exists, unless the body carries overwrite:true. prd-list with status set to pending lists the open rows.

prd-resolve closes a row. It moves the row into .gm/prd-log.jsonl, an append-only log (skills/gm-prd/SKILL.md). A resolved id stays answerable: prd-list with that id reads the log.

gm-prd closes one row through the nine stages, in order, in one run with no subagent per stage (skills/gm-prd/SKILL.md). Each stage writes a create-only receipt, .gm/receipts/<row>/NN-<STAGE>.md. The gm-config prose gives each open row to one worker subagent (gm-config/prose/complete.md), so the nine stages run inside that one worker. The compiled entry prose at rs-plugkit/crates/plugkit-core/src/orchestrator/instructions/prose/entry.md states the same rule. A codesearch for the stage name SPECIFY returns hits only in prose files under rs-plugkit/crates/plugkit-core/src/orchestrator/instructions/prose and none in Rust source.

The nine gm-prd stages, in order
StageWhat the stage does
SPECIFYRestates the row and its acceptance, and checks each cited line against the tree. A line that is absent makes the row stale.
PROVERuns the precondition, the invariant and the postcondition, each as a live check.
EMITMakes exact-match edits only, and witnesses them through the live entry point.
STATEShows that the change replays idempotently, and names the state it owns.
CONCLists each touched file and the hunks other writers hold in it.
SECChecks secrets, injection and identity, each as a run.
RESRuns each failure mode, partial failure included.
DECIDEChecks the receipts and the live witnesses against the words of the row, and checks the push or CI result.
COMPLETECalls prd-resolve with the witness evidence and a witness dispatch id.

A stage that cannot run becomes a blocker row, <row>-blocker-<session>, filed with prd-add. A stage is never skipped. The row is closed by a witness binding: a witness_dispatch_id, or all four of witness_exit_code, witness_output_sha256, witness_output_path and witness_ts. The COMPLETE stage requires the witness to come from another session, so a self-witnessed close stays pending. prd-resolve refuses a witness output sha256 that is already bound to another row (prd-resolve-duplicate-witness). A worker records each witness run as one line in .gm/witness-log.md (rs-plugkit/crates/plugkit-core/src/orchestrator/instructions/prose/entry.md).

10. Mutables and the gates on them

An unknown is an open condition that a decision or a change depends on. unknown-add writes a file under .gm/unknowns/, and unknown-list reads the open set. unknown-resolve closes one and accepts a measured_value. The gates that refuse a transition on unknowns are mutables-all-resolved, which refuses while any unknown is open or pending, and mutables-all-typed refuses while a pending unknown whose obligation kind is a PROVE kind (precondition, invariant, postcondition, resource-bound or type-shape) is untyped or depends on an unresolved id.

11. Witnessed execution and the no-test rule

Execution is a spool verb. An exec verb takes a plain text body, sent as raw_body. The optional first line timeoutMs=<ms> sets the wall-clock limit, which defaults to 300000 ms (rs-plugkit/crates/plugkit-core/src/wasm_dispatch/verbs.rs) and has a hard ceiling of 900000 ms (EXEC_HARD_CEILING_MS in gm-mcp/src/dispatch.js). At expiry the run is killed, and the out-file (the reply file in .gm/exec-spool/out/, section 15) reports killed:true with exec_timeout. A reply longer than the reply limit, 24000 characters by default (DEFAULT_REPLY_MAX_CHARS in gm-mcp/src/dispatch.js), is cut, and the truncation notice names a spill_file that holds the whole text.

AGENTS.md requires a falsifiable hypothesis and a live witness before each change.

The gate no-synthetic-test-files refuses a standing test file or test directory that the working diff introduces (gm-config/fsm/predicates.md). Verification is a live witness against real code instead, and the gate is diff-scoped, so it does not touch what a submodule already carries. The diff gates no-secrets-in-diff, no-graphical-symbols-in-diff, no-hedge-language-in-diff, no-unchecked-panics-in-diff and no-admit-deferral-markers refuse the matching text, and claim-audit-clean is the claim-audit gate.

12. Search and code insight

codesearch is the search verb, with the aliases code_search and search. Its literal mode finds a string, and grep, with the alias rg, is the exhaustive scan that answers where a string occurs. A scan that hits a bound returns exhaustive: false with partial: true and a partial_reason, and path or path_glob narrows the scan.

Structural questions go to the symbol graph first. callers lists who calls a symbol, callees lists what it calls, and impact walks the callers of a symbol up to max_depth (default 3), or its callees with direction set to callees. The graph comes from the treesitter index, so an empty call graph is trusted only after codeinsight_index runs on a fresh checkout, and AGENTS.md requires that an empty call graph be confirmed with codesearch. codeinsight with mode outline requires a path.

A project lists its generated and vendored trees in a .codesearchignore at its root. The file uses gitignore syntax and is read in addition to .gitignore. Dropped paths appear in excluded_by_rule_summary and excluded_by_rule_count. Any exclusion other than gm's own state clears exhaustive. The index build has a wall-clock budget of 45000 ms (index.wall_budget_ms in gm-config/gm.config.json), and index.max_file_bytes caps the size of a file the index reads.

rs-search is a dependency-free library. Its crate root is rs-search/src/lib.rs, and it has two modules: rs-search/src/fusion.rs (reciprocal rank fusion (RRF), with RRF_K = 60) and rs-search/src/tokenize.rs (identifier tokenization). Its source modules contain no BM25 or vector code.

rs-plugkit runs the BM25 lexical channel and the embedding channel of section 13, and calls rs-search for tokenization and fusion: bm25_rank_cfg in rs-plugkit/crates/plugkit-core/src/code_index.rs tokenizes its query with rs-search, and rs-plugkit/crates/plugkit-core/src/dataflow_exec.rs calls rs_search::fusion::fuse_n_cfg to fuse the ranked lists. The BM25 parameters are k1 at 1.2 and b at 0.75 (scoring.bm25_k1 and scoring.bm25_b in gm-config/gm.config.json).

13. Memory

Memory is a set of markdown entries and a vector index over them.

  • memorize writes its text to the memory index under a namespace. The namespace is default unless the body names another.
  • memorize-fire writes its body as one .md file under .gm/memories/, named by its key, and indexes it in .gm/gm.db.
  • recall returns the ranked hits for a query.
  • auto-recall returns up to three hits for a prompt.
  • Each instruction reply carries recall hits for its own query, up to instruction_recall_hits, which is 5 in gm-config/gm.config.json.

forget is retired. memorize-prune removes entries: {"keys":[...]} deletes the named entries, and {"query":"..."} returns review candidates without deleting any.

The memory namespaces are default and codeinsight (memory.namespaces in gm-config/gm.config.json).

Embeddings come from the bge-small-en-v1.5 weights in agentplug-bert. memory.embed_dim is 384, and AGENTS.md requires that a change to it drop every stored vector through an explicit drop-if-mismatch path, never silently.

Each recall hit is scored by its cosine similarity multiplied by a recency factor. The recency factor has a half-life of 30 days (scoring.half_life_ms is 2592000000) and a floor of 0.4 (scoring.recency_floor). Near-duplicate hits are removed when their Jaccard overlap reaches 0.7 (scoring.dedup_jaccard_threshold).

AGENTS.md sets the durable-memory rule: the agent deletes every entry that is not current (each path, verb and setting it names still resolves) or not reusable (it states a rule for a future task with no session, date or incident).

14. The learning loop

The learning loop has three parts: recall, memorize, and the Dream-RSI observation and replay cycle. Recall, described in section 13, feeds the learning loop. Memorize stores the decisions a later task would otherwise re-derive (gm-config/prose/lean-p1.md, Memorize). Dream-RSI turns the record of real work into strategy proposals.

Dream-RSI records each real work dispatch automatically into .gm/dream-rsi/<session>/observations.json. Orchestration bookkeeping and Dream-RSI maintenance do not become outcomes, so they are not recorded as observations (rs-plugkit/crates/plugkit-core/src/orchestrator/instructions/prose/entry.md). The current selection is held in .gm/dream-rsi/<session>/active-strategy.json, which no rs-plugkit path writes; active_strategy in rs-plugkit/crates/plugkit-core/src/orchestrator/dream_rsi.rs only reads it.

A cycle trigger runs inside the agentplug-runner daemon. spawn_dream_rsi_cycle_ticker in agentplug/crates/agentplug-runner/src/daemon.rs wakes on a fixed tick (DREAM_RSI_CYCLE_TICK_INTERVAL_MS) and hands its loop to dream_cycle::spawn. The loop in rs-plugkit/crates/plugkit-core/src/orchestrator/dream_cycle.rs writes requests for its VERB into .gm/exec-spool/in/dream-replay-cycle under each known project root. It is gated by MIN_NEW_OBSERVATIONS and COOLDOWN_MS.

A replay result is planning input and never execution authority. It cannot run a tool, evaluate a new outcome, or add an observation to observations.json. Those actions need a real dispatch, and only a real dispatch writes an observation. Deploying an accepted strategy is a dispatch that an agent makes under the same gates as any other state change. The cycle trigger's only verb is dream-replay-cycle, and no file under agentplug/ names dreamrsi-select. The verb is routed to dream_cycle::handle at rs-plugkit/crates/plugkit-core/src/orchestrator/mod.rs.

15. The spool and its transports

A body is written to .gm/exec-spool/in/<verb>/<N>.txt, and the reply lands in .gm/exec-spool/out/. An exec reply names its output in a result_file, and section 11 gives its reply limit and spill. While the claim in/<verb>/<N>.txt.inflight exists, the dispatch is claimed. The file .gm/exec-spool/.status.json reports the watcher's heartbeat.

gm-mcp wraps the spool for MCP clients. It registers one tool, gm_codemode, whose code body calls every verb as gm.<verb>(body). It serves stdio, which is the default registration, and stateless streamable HTTP on 127.0.0.1:8787/mcp. Its transport failure modes and registration command are owned by gm-mcp/README.md. The Node launcher bin/gm exposes the same dispatch as its dispatch subcommand.

The native host is agentplug-runner. It loads the plugkit WASM guest, which implements orchestration, the spool verbs, memory and code search. The runner is the only supported loader. Git is a verb, not a shell command: the deviation bash-git-bypass denies a shell command that invokes git, and its denial names the git verbs that replace it.

16. Git delivery

Every change lands on main, in the shared work tree. No branch, worktree or side checkout is opened to avoid a collision. A collision is recovered on main in the same turn:

  1. Read the conflicted set with git_status.
  2. Re-read each path against the remote state.
  3. Stage the resolved paths with git_add.
  4. While .git/MERGE_HEAD is set, commit without paths.
  5. Push the full sha of the tip with git_push {rev, allow_foreign_commits:true}.
  6. Finish on main.

git_push {rev:"HEAD"} is refused.

git_finalize {message, paths} commits the named paths and pushes them. In a shared work tree, do not publish with git_finalize. The publish path is the Git API route, with blobs, a tree on the remote tip, and a commit parented on that tip, then a read of each published blob. A git_finalize whose push is refused is reported as redundant, meaning its content is already published, never as unpushed work. git_remote reads the remote URLs and the upstream without fetching or changing state. A pushed change is witnessed by two separate reads: git_show {rev} for the commit, and ci-status {sha} for the CI (continuous integration) state. A status of unknown is reported as unknown, never as success.

A commit message states the change and nothing else. Attribution is one author, lanmower, with no Co-Authored-By, Signed-off-by, Generated with or assistant footer (skills/gm/SKILL.md, Autonomy). The served skill governs this rule. AGENTS.md does not repeat it.

17. Invariants and what would break them

AGENTS.md states the repository's invariants. Each item below states one of them with the condition that falsifies it, and its status at the revision this paper reads. Status not checked means this paper ran no check for that item.

  • Walk completion. The completion checks are in section 5. Falsified by a COMPLETE reply while prd-list with {"status":"pending"} still returns rows. Status: not checked.
  • Configuration precedence. A vendored key in the project replaces the cached and compiled prose. Falsified by a vendored key whose instruction reply still carries the cached text. Status: not checked.
  • Gate names. A gate names only a predicate generated into gm-config/fsm/predicates.md. Falsified by a gate that names a predicate outside that file. Status: holds for the graph. Every predicate that a gate in gm-config/fsm/graph.json names appears in that file (section 4 gives the gate predicates per edge).
  • Path safety. fs_read {"path":"../etc/hostname"} returns error_code: failed. Falsified by an ok: true reply for that path. Status: holds. A live fs_read of that path returned error_code: failed in dispatch 1791899041532-500-8ffb5e21f24ca6d2.
  • Remote transports. The system accepts only HTTP(S) remote transports with a nonempty authority, and refuses any other scheme. Falsified by a live dispatch that accepts a remote transport with another scheme or an empty authority. Status: violated in the source. The URL allow-list in rs-plugkit/crates/plugkit-core/src/config_path.rs also names ssh://, which AGENTS.md does not allow.
  • One writer per surface. Each shared file, ref, submodule pin or spool directory has one writer. Falsified by two briefs that write the same surface. Status: not checked.
  • Pin parity. Each parent gitlink points to its submodule's main tip, and .github/workflows/bump-pins.yml advances it. Falsified by a parent gitlink that differs from its target's remote main tip after a green bump run. Status: the workflow file exists. This paper does not compare the gitlinks.
  • Replay identity. git_commit_dedup_lookup shall answer a replay only while rev-parse HEAD equals the recorded sha_full, because object existence is not enough after git_reset. Falsified by a replay answered after git_reset moves HEAD off the recorded sha_full. Status: violated in the source. The lookup in rs-plugkit/crates/plugkit-core/src/wasm_dispatch/verbs/git.rs checks only that the object exists (git cat-file -e) and that the record is younger than its 180000 ms TTL.
  • Build identity. The update guard locally_built_installed_reason refuses to replace a runner whose build_info::is_release_build() is false, unless update_over_local_build_allowed() permits it. Falsified by a release swapped over a runner whose RELEASE_BUILD is false. Status: the guard source has both checks (agentplug/crates/agentplug-runner/src/download.rs). This paper does not run it live.
  • Single-writer markers. A single-writer or lock guard creates its marker by atomic create or atomic rename. Falsified by a plain write in the guard's source. Status: not checked.
  • Text encoding. Every tracked text file is UTF-8 without a byte-order mark. Falsified by a tracked file that begins with EF BB BF. Status: not checked.
  • Lean graph sync. scripts/sync-lean-graph.mjs emit never writes a path under rs-plugkit/. Falsified by an emit that writes there. Status: not checked.

18. Limits

  1. The live ceiling, the number of subagents that can run at once, is not measured here. Section 8 gives the fallback default and says how the orchestrator finds the live value, and the paper records no value that any platform accepted.
  2. Memory goes stale. An entry is a claim written at one time, and section 13 gives the rule for removing stale ones.
  3. A walk is bounded, not proven complete. The graph is finite (section 3), the hop chain stops at its depth limit (section 7), and the stop rules of section 5 end it. These bounds end a walk. They do not show that the walk found all the work a request contains (section 5 lists the completion checks).
  4. The paper measures nothing. It reports no speed, failure rate or effect size. No #[bench] or [[bench]] target exists in rs-plugkit or agentplug. The three failures named in the Abstract block are the design motivation, and the paper reports no count of them.

19. Conclusion

Sections 2 to 17 describe the components, gates, walks and verbs of gm. Section 18 lists what this paper does not measure.
