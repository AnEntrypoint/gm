gm: a skill that makes LLM coding agents check their work against real command output

How the checks, gates and walks fit together, for developers who use an LLM coding agent.

AnEntrypoint - gm
Describes the gm project as published on its main branch. Every count can be reproduced from the file named beside it.
Abstract

gm is a skill for LLM coding agents. It targets three failures: acting on an unverified guess, losing resolved work when the context window fills, and declaring a task done before it meets the requirement. Each check moves out of the agent's reasoning and into files and gates, and a step closes only on the output of a real command run. Section 3 maps the graph that enforces this.

gm is for developers who run an LLM coding agent in their own project. Install it with the one-line command in README.md, or read install for every install path. Section 3 names the node a walk starts from, and section 5 gives its verbs and completion conditions.

1. Introduction

The design rationale is that a check made inside the agent's own reasoning can share the shortcut that caused the failure, so gm keeps the state graph, the PRD rows and the mutables in files, and an executor returns the output of a real run.

This paper describes the system as this repository ships it.

3. The discipline graph

The state machine that enforces gates and transitions is gm-config/fsm/graph.json, schema version 2. Its nodes and edges carry no phase field. Its nodes are principles, tensions, gates and terminals, and its edges join them. The policy block names the Jobs To Be Done (JTBD) node as the start of a walk (initial_phase) and G_FIXPOINT as its terminal (terminal_phase). A node is entered from any neighbour with an edge to it and left along any edge out of it, so a walk takes many distinct paths through the graph. The graph is a set of independent nodes with many paths between them, not a sequence of phases (skills/gm/SKILL.md, Section 2).

Each node carries a key, a kind, a label and a prose_key that selects its served prose. Each edge carries from, to, kind (forward or backreference), a label and its list of gate predicates. A backreference edge is how a walk re-enters ground an earlier step changed, so the graph keeps both kinds.

Two graphs exist, and they differ. The enforced copy is rs-plugkit/crates/plugkit-core/src/orchestrator/lean_graph.json, which rs-plugkit/AGENTS.md describes as a vendored copy of gm-config/fsm/graph.json; the two hold the same counts at this revision. The hop payload is built from skills/dream-rsi/gm-graph.json, a hand-authored catalogue of 145 nodes (6 gate nodes) and 360 edges (224 forward, 136 backreference). The gm-orchestrate skill launches each hop from that catalogue. The two files are kept separately, and their counts are not the same.

4. Gates that refuse a step

A transition is a request to move along an edge. The orchestrator evaluates the gate predicates on that edge, and a failed predicate refuses the move. The graph names 26 gate predicates. Twenty-four are blocking. The two advisory gates never refuse a transition, because code cannot observe their condition: lean-contract-only-description and lean-verifier-independent. The names are listed in gm-config/fsm/predicates.md.

The configuration keeps the predicates in one registry. gates.predicate may name only a predicate generated into gm-config/fsm/predicates.md from the same registry the code dispatches on. A condition outside that registry is written as a jit hook under fsm.hooks_dir. The denial text lives in messages.gates_dir and messages.residual_dir, and an operator can edit it without changing when a gate fires.

A denial names the failed predicate and the verb that recovers it. It is authoritative. The agent satisfies the named predicate and dispatches the transition again, and it does not route around the denial. A gate that names a predicate outside the registry, or a denial that prints an unfilled token, is a defect to surface. The agent does not treat it as a pass.

5. Walks and completion

A walk is one run of the state machine from the start node toward a terminal. The agent drives it with three verbs. instruction returns the served prose for the node the walk stands on, with recall and orient data. transition moves the walk along an edge, and the gates of that edge decide whether the move succeeds. phase-status returns only the compact phase-history struct, without that prose. The split between the two is stated in skills/gm/SKILL.md.

A walk completes only when all three conditions hold: the live state machine accepts COMPLETE, every required PRD row is resolved, and gm-continue has checked for remaining work. The walk does not complete on the agent's own statement that the work is done. COMPLETE has a forward edge to G_FIXPOINT. G_FIXPOINT is the convergence point of a sweep: it is reached when a full sweep changes nothing, no gate reopens, no counterexample appears, and the artifact does not grow. The convergence rule is stated in skills/dream-rsi/gm-graph.json.

The main thread runs a walk through gm-orchestrate (section 8). A walk stops after 40 ticks (skills/gm-orchestrate/SKILL.md, Exit and stalls). Two consecutive ticks with no row closed and no launch end the loop after the open rows are recorded. A repeated shortfall restarts the walk at most twice, and a third repeat files a blocker row, <row>-blocker-<session>, and stops.

6. When the agent may stop or ask

The agent asks the user only for a world-scoped one-way door: an action that deletes something with no recoverable copy, spends money, reaches another person, changes production, or carries legal, medical, financial or safety consequences for a real person. The gm skill names this as the sole interruption. Every other question is a default. The agent chooses the most defensible default, states it in one line in the durable artifact (a commit body, a PRD note or a decision record), and continues. An unknown that the agent cannot settle by a search, a recall or a witnessed run becomes a mutable, not a question to the user.

The served rules fix what the agent does without asking. A read-only step runs at once. Under git, an append is never asked: a commit, a push, a merge and each step of a collision recovery run in the turn they are needed. A rewrite is asked: a force push, a rebase of pushed commits, a branch or ref deletion, or a remote reset. The user's first request is the approval for the work it names, and a written PRD is not a second approval gate.

A turn ends in one of two ways: at a terminal state with prd_pending_count at zero, or at a world-scoped one-way door. While a walk is in flight, every turn ends in a tool call. A prose-only message ends the turn, so the agent sends the next verb in the same message instead of a summary. A stop checkpoint that fires before the walk completes is a defect to fix, not a reason to stop.

7. Hops

A hop is one traversal of one node. gm-hop receives one JSON object with these fields: node (its id, label, book, author, kind, advocate and links), principle (the id of the node the hop applies), surface (the path it works on), session (its own SESSION_ID), wave, depth and rhetoric (skills/gm-orchestrate/SKILL.md, step 2, shows the launch payload). A missing node, surface or session gives VERDICT: NOT-APPLICABLE.

The hop runs eight steps, numbered 0 to 7 in the skill. Step 0 applies the node's discipline to the surface, named by node.label, with node.advocate as its spec. Step 1 argues the open question in one paragraph. Step 2 lists the node's testable claims, each with its test. Step 3 searches every instance those claims govern and cites the lines it found. Step 4 closes what one exact-match edit closes, when no other writer holds the file, and witnesses the change with a live dispatch. Step 5 records every other finding as a PRD row. Step 6 names the biggest remaining need in one sentence, and step 7 nominates the next node. The receipt is 120 words at most (skills/gm-hop/SKILL.md, Receipt) and names an executed witness. A receipt without one is refused.

A hop never reads the graph. Its links come from the payload. gm-orchestrate builds each link from the edges of the node, both forward and backreference, and lists the targets in lexical order. Each link carries the edge's condition, when the edge has one, as its guard. A link is eligible when every guard holds on the surface. The hop nominates the next node only from eligible links, and the chain stops at depth 6, the default max_depth in skills/gm-hop/SKILL.md, with next: none, depth limit.

gm-hop directs each hop to write .gm/lean-walk/<NODE>.json on every verdict, including NOT-APPLICABLE. The file lists the links offered and the link taken. The link taken is either null or one of the links offered. A discipline the surface demands that the catalogue lacks is appended as a line to .gm/lean-walk/new-nodes.jsonl. A hop never edits the catalogue; the catalogue's owner promotes new nodes.

A hop commits its own change and does not push. The orchestrator publishes the tip of each wave in one push. A hop issues at most two git verbs, one git_status and one git_commit, and it does not pull. A hop never dispatches gm-continue. That call is the parent's terminal move.

8. Parallel subagents (the pool)

A walk runs its hops and PRD rows as subagents in a pool. The ceiling is the number of subagents the platform accepts at once, and the orchestrator finds it by launching: a spawn refusal states the ceiling, and the orchestrator never sets it from configuration. The floor is min(10, ceiling). While PRD rows are open, the live count stays at or above the floor, and the pool-floor-met gate refuses a transition while it does not.

The orchestrator runs a tick in five steps, as skills/gm-orchestrate/SKILL.md lists them: observe, launch, log, wait, and re-count the live pool. Observe runs pool-observe, dispatched in rs-plugkit/crates/plugkit-core/src/orchestrator/mod.rs and implemented in rs-plugkit/crates/plugkit-core/src/orchestrator/pool_slots/observe.rs, which returns the free slots and the launchable candidates. Launch sends one message, PRD rows first and hops from untraversed nodes after them. Log writes each launch to .gm/pool/ledger-<wave>.txt and each tick to .gm/witness-log.md. Wait pauses for up to 600000 ms (MAX_WAIT_MS in rs-plugkit/crates/plugkit-core/src/orchestrator/wait.rs), and each completion refills its slot in the same turn before any other step. A slot stays empty only when no open row and no untraversed node remain.

Each subagent brief opens by writing .gm/pool/<session>.live and deletes that file on finish. The count of record comes from the subagent list, not from the ledger: a self-spawned successor leaves a launch with no matching completion, so the ledger can overstate the live count. A successor that the ceiling refuses is parked at .gm/pool/<session>.next, and the orchestrator relaunches that spec into the first freed slot.

Three failure modes have fixed responses. A subagent whose transport drops mid-run keeps its row open and frees its slot. The orchestrator resumes that subagent by id first and relaunches a fresh brief only when the resume fails. Many drops inside one window are one drain event: the orchestrator waits out the window and refills in two half-waves. A git verb that the serial lane starves is re-dispatched once, unchanged, and a second starvation is filed as a PRD row. A headroom stop is separate from these. At CPU of 80 percent or more, or available memory below 2048 MB (skills/gm-orchestrate/SKILL.md, Headroom and leases), launches pause. A headroom stop is neither a stall nor a shortfall, and it does not end the turn.

9. Planned work (PRD rows) and the nine stages

A PRD row is one unit of planned work. Each row is one file, .gm/prd/<id>.yml, and the folder is the index. A verb writes only the file of the row it names, so two lanes that add two rows never rewrite each other's work. prd-add refuses an id that already exists, unless the body carries overwrite:true. prd-list reads open rows.

prd-resolve closes a row. It moves the row into .gm/prd-log.jsonl, an append-only log in which each line carries prev, the SHA-256 hash of the line before it. A truncated or edited line therefore breaks the chain and shows. A resolved id stays answerable: prd-list with that id reads the log.

gm-prd closes one row in one run, with no subagent in the stages. Each stage writes a create-only receipt, .gm/receipts/<row>/NN-<STAGE>.md.

The nine gm-prd stages, in order
StageWhat the stage does
SPECIFYRestates the row and its acceptance, and checks each cited line against the tree. A line that is absent makes the row stale.
PROVERuns the precondition, the invariant and the postcondition, each as a live check.
EMITMakes exact-match edits only, and witnesses them through the live entry point.
STATEShows that the change replays idempotently, and names the state it owns.
CONCLists each touched file and the hunks other writers hold in it.
SECChecks secrets, injection and identity, each as a run.
RESRuns each failure mode, partial failure included.
DECIDEChecks the receipts and the live witnesses against the words of the row, and checks the push or CI result.
COMPLETECalls prd-resolve with the witness evidence and a witness dispatch id.

A stage that cannot run becomes a blocker row, <row>-blocker-<session>, filed with prd-add. A stage is never skipped. The row is closed by a witness, and the closing binds that witness in one of two forms: a witness_dispatch_id, or the four fields of exit code, output hash, output path and timestamp. The witness must come from another session, so a self-witnessed close leaves the row pending. A witness output hash already bound to another row is refused with prd-resolve-duplicate-witness. Each witness run appends one line to .gm/witness-log.md, and the row cites that line.

10. Mutables

A mutable is a named unknown: a free variable that a decision or a change depends on. The agent records it before it relies on it. mutable-add writes a file, .gm/mutables/<id>.yml, and mutable-list reads the open set. mutable-resolve closes one and accepts a measured_value for a resource-bound check. Two gates refuse a transition while mutables remain open: mutables-all-resolved and mutables-all-typed.

Closing a mutable takes a value from a run. The served prose asks for a live measurement, and the agent records the dispatch id that produced it. A plausible value that no run produced does not close a mutable. The same rule applies to every change. AGENTS.md requires a falsifiable hypothesis with the live witness that would refute it before the change, and skills/gm/SKILL.md (the Change line) requires a live record of each touched function's current behaviour before the first edit.

11. Witnessed execution and the no-test rule

Execution is a spool verb. An exec verb takes a plain text body, sent as raw_body. The optional first line timeoutMs=<ms> sets the wall-clock limit, which defaults to 300000 ms and has a hard ceiling of 900000 ms (rs-plugkit/crates/plugkit-core/src/wasm_dispatch/verbs.rs). At expiry the child's process tree is killed and the reply reads exec_timeout with the partial output. A reply longer than its limit, 24000 characters by default (DEFAULT_REPLY_MAX_CHARS in gm-mcp/src/dispatch.js), is cut, and the truncation notice names a spill_file that holds the whole text. exec_js evaluates its body in a separate Node process, which receives the body on stdin, so the body never appears on a command line.

A witness is a live dispatch against the running system whose reply carries the value under test. The witness exits 0 only with an explicit line that says what it checked.

The gate no-synthetic-test-files refuses a test file or test directory in the diff, and verification runs a live dispatch instead. The MCP server's own test files are in gm-mcp/test/. The diff gates no-secrets-in-diff, no-graphical-symbols-in-diff, no-hedge-language-in-diff, no-unchecked-panics-in-diff and no-admit-deferral-markers refuse the matching text, and claim-audit-clean refuses a claim that the audit cannot support.

12. Search and code insight

codesearch is the search verb, with the aliases code_search and search. Its literal mode finds a string, and grep, with the alias rg, is the exhaustive scan that answers where a string occurs. A reply with exhaustive: true covered every file in scope. A zero result from a scan that is not exhaustive is not evidence that the code is absent, and the agent re-scopes the scan with path or glob before it concludes.

Structural questions go to the symbol graph first. callers lists who calls a symbol, callees lists what it calls, and impact lists what a change to it reaches. An empty call graph counts as an answer only when codeinsight_index reports complete: true. Otherwise the agent confirms the empty result with a codesearch identifier query. codeinsight gives the symbol overview of a file or project.

A project lists its generated and vendored trees in a .codesearchignore at its root. The file uses gitignore syntax and is read in addition to .gitignore. Dropped paths appear in excluded_by_rule_summary and excluded_by_rule_count. Any exclusion other than gm's own state clears exhaustive. The index build has a wall-clock budget of 45000 ms (index.wall_budget_ms in gm-config/gm.config.json), and index.max_file_bytes caps the size of a file the index reads.

rs-search is the reciprocal rank fusion (RRF) library. It merges ranked lists with RRF_K = 60, in rs-search/src/fusion.rs, and rs-plugkit calls it to fuse the channels. The BM25 lexical channel (a term-frequency scoring formula, bm25_rank_cfg in rs-plugkit/crates/plugkit-core/src/code_index.rs) and the vector cosine channel run in rs-plugkit. The BM25 parameters are k1 at 1.2 and b at 0.75 (scoring.bm25_k1 and scoring.bm25_b in gm-config/gm.config.json).

13. Memory

Memory is a set of markdown entries and a vector index over them. memorize writes an entry to .gm/memories/<key>.md, and memorize-fire flushes the write and indexes its embedding in .gm/gm.db. recall returns the ranked hits for a query, and auto-recall attaches the hits for each prompt to the next instruction reply. memorize-prune and forget remove entries, and memorize-vacuum and memorize-retention maintain the index. The memory namespaces are default and codeinsight (memory.namespaces in gm-config/gm.config.json).

Embeddings come from the bge-small-en-v1.5 weights in agentplug-bert, which run on the local machine. memory.embed_dim is 384, and AGENTS.md requires that a change to it drop every stored vector through an explicit drop-if-mismatch path, never silently.

Each candidate is scored by its cosine similarity multiplied by a recency factor. The recency factor has a half-life of 30 days (scoring.half_life_ms is 2592000000) and a floor of 0.4 (scoring.recency_floor). Near-duplicate hits are removed when their Jaccard overlap reaches 0.7 (scoring.dedup_jaccard_threshold). recall returns 8 rows by default (memory.recall_limit).

AGENTS.md sets the durable-memory rule: the agent deletes every entry that is not current (each path, verb and setting it names still resolves) or not reusable (it states a rule for a future task with no session, date or incident).

14. The learning loop

The learning loop has three parts: recall before planning, memorize at the decision point, and the Dream-RSI observation and replay cycle. Recall gives the agent what earlier sessions found, so it does not rediscover a fact. Memorize stores a witnessed fact with memorize-fire when a later task would otherwise re-derive it (gm-config/prose/lean-p1.md). Dream-RSI turns the record of real work into strategy proposals.

Dream-RSI records each real work dispatch automatically into .gm/dream-rsi/<session>/observations.json. Orchestration bookkeeping and Dream-RSI's own maintenance dispatches are not recorded, so only real work counts. The current selection is held in active-strategy.json, which observe_dispatch in rs-plugkit/crates/plugkit-core/src/orchestrator/dream_rsi.rs rewrites on each observed dispatch.

A cycle trigger runs inside the agentplug-runner daemon. spawn_dream_rsi_cycle_ticker in agentplug/crates/agentplug-runner/src/daemon.rs wakes once every 60 seconds. For each known project it writes one dream-replay-cycle request, and only when at least 20 new observations have accumulated and at least 15 minutes have passed since the last cycle, as docs/dream-rsi.md states.

A replay result is planning input and never execution authority. It cannot run a tool or evaluate an outcome that no dispatch produced. Deploying an accepted strategy is a dispatch that an agent makes under the same gates as any other state change. No daemon tick or scheduled job redeploys a strategy. The metrics that drive selection are recomputed from the dispatch ledger on each replay, not supplied by the agent's own account of its progress.

15. The spool and its transports

Each verb reaches the same dispatch surface. A body is written to .gm/exec-spool/in/<verb>/<N>.txt, where <N> is <session>-<pid>-<epoch ms>-<counter>, and the reply lands in .gm/exec-spool/out/ as <verb>-<N>.json. An exec reply names its output in a .txt result_file, and a reply longer than its limit spills to the spill_file that the reply names. A missing reply file means the dispatch has not finished. While the claim in/<verb>/<N>.txt.inflight exists, the work is still running, and the agent waits on that claim rather than sending the body again. The file .gm/exec-spool/.status.json reports the watcher's heartbeat and its pid.

gm-mcp wraps the spool for MCP clients. It registers one tool, gm_codemode, whose code body calls every verb as gm.<verb>(body). It serves stdio, which is the default registration, and stateless streamable HTTP on 127.0.0.1:8787/mcp. Its transport failure modes and registration command are owned by gm-mcp/README.md. The Node launcher bin/gm forwards a verb to the same dispatch with no daemon of its own.

The native host is agentplug-runner. It loads the plugkit WASM guest, which implements orchestration, the spool verbs, memory and code search. The runner is the only supported loader. Git is a verb, not a shell command: the gate deviation.bash-git-bypass denies a Bash git call and names the matching git verb.

16. Git delivery

Every change lands on main, in the shared work tree. No branch, worktree or side checkout is opened to avoid a collision. A collision is recovered on main in the same turn. The agent reads the conflicted set with git_status, re-reads each path against the remote state, stages the resolved paths with git_add, commits without paths while .git/MERGE_HEAD is set, pushes the full sha of the tip with git_push {rev, allow_foreign_commits:true}, and finishes on main. git_push {rev:"HEAD"} is refused because the name is symbolic and would publish every unpushed commit.

git_finalize {message, paths} commits the named paths and pushes them. It refuses to push over a dirty path that a sibling lane holds, and a refused push leaves a local commit that duplicates content already published. In a shared work tree the publish path is therefore the Git API route, with blobs, a tree on the remote tip, and a commit parented on that tip, then a read of each published blob. git_remote reads the remote URLs and the upstream without fetching or changing state. A pushed change is witnessed by two separate reads: git_show {rev} for the commit, and ci-status {sha} for the CI (continuous integration) state. A status of unknown is reported as unknown, never as success.

A commit message states the reason for the change and carries one author, with no co-author or generated-by trailer, because the project's attribution is a single author.

17. Invariants and what would break them

AGENTS.md states the repository's invariants, and each one names what would falsify it. A reader can check each line with one read, the path named in it, or one live dispatch.

  • Configuration precedence. A vendored key in the project replaces the cached and compiled prose. Falsified by a vendored key whose instruction reply still carries the cached text.
  • Gate names. A gate names only a predicate generated into gm-config/fsm/predicates.md. Falsified by a gate that names a predicate outside that file.
  • Path safety. fs_read {"path":"../etc/hostname"} returns error_code: failed. Falsified by an ok: true reply for that path.
  • Remote transports. Only HTTP(S) remote transports with a non-empty authority are accepted. Falsified by a live dispatch that accepts another scheme.
  • One writer per surface. Each shared file, ref, submodule pin or spool directory has one writer. Falsified by two briefs that write the same surface.
  • Pin parity. A delivered submodule commit moves its parent gitlink in the same delivery. Falsified by a delivered submodule commit whose parent gitlink is unchanged.
  • Replay identity. git_commit_dedup_lookup answers a replay only while rev-parse HEAD equals the recorded sha_full. Falsified by a replay answered after git_reset_head moved HEAD.
  • Build identity. A self-update guard compares COMMIT and RELEASE_BUILD from build_info.rs, never the version string. Falsified by a guard whose only comparison is the version.
  • Single-writer markers. A single-writer or lock guard creates its marker by atomic create or atomic rename. Falsified by a plain write in the guard's source.
  • Text encoding. Every tracked text file is UTF-8 without a byte-order mark. Falsified by a tracked file that begins with EF BB BF.
  • Lean graph sync. scripts/sync-lean-graph.mjs emit never writes a path under rs-plugkit/. Falsified by an emit that writes there.

18. Limits

  1. The pool ceiling is not stated here. Section 8 says how the orchestrator finds it, and the paper gives no number for it.
  2. Memory goes stale. An entry is a claim written at one time, and section 13 gives the rule for removing stale ones.
  3. A walk is bounded, not proven complete. The graph is finite (section 3), the hop chain stops at its depth limit (section 7), and the orchestrator stops at its tick bound (section 5). These bounds end every walk. They do not show that a walk has found all the work a request contains.
  4. The paper measures nothing. It reports no speed, failure rate or effect size, because the repository holds no benchmark for any of them. Claims of that kind need a fixed workload and a live witness on each build.
