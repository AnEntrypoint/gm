The gm skills

what the gm skills are, and which verbs serve them
tl;dr
gm is a workflow for AI coding agents. It drives an agent through engineering work in a git project: code search, git verbs, recorded memory, and a plan of rows that each close with evidence. It is for developers who run coding agents such as Claude Code, Cursor, Codex or Gemini. The entry skill is /gm, from skills/gm/SKILL.md. It holds the standing rules and points the agent at the walk skills. The prose for the current phase and the live graph state come from the orchestrator through the instruction verb. The release ships eleven skill directories that each contain a SKILL.md: gm, four walk skills and six discipline skills.

What you can do next

Install with the commands on the distribution page, which also registers the gm MCP server. In a project, ask the agent to dispatch instruction, which returns the current phase's prose and the state it sits in. The orchestrator verbs section lists the verbs this page documents. skills/gm/docs/verbs.md is the verb inventory, with the body shape of each verb.

Terms

  • walk: one run of the gm state machine that the orchestrator drives to completion.
  • plan row: one entry in the plan, also called a PRD row. It closes only with recorded witness_evidence.
  • hop: one traversal of a graph node, performed by one gm-hop subagent.
  • gate: a named check that a graph edge lists in its gates. Each gate names a predicate or a hook. A move along that edge is refused while the check fails.
  • mutable: an open question, recorded with mutable-add until a live check answers it.
  • dispatch: one request that asks the gm runner to run a verb.

The entry skill

skills/gm/SKILL.md is the only skill an agent loads up front. It sets the autonomy rules, which say how far the agent acts without asking, and the search and git routing: code search goes through codesearch, and git goes through the git verbs.

The walk skills

These skills sit beside gm. Each one is loaded by name once a walk starts.

gm-orchestrate

runs the walk loop
doesTicks the subagent pool: it launches plan rows and graph hops, waits on them, and refills freed slots. It also owns the walk loop and its exit check.
pool termsceiling is the most subagents that can run at once. live is the number running now. floor is the live count required while plan rows are open, min(10, ceiling). shortfall is live below the floor while independent work is open and headroom is ok.

gm-hop

one step through the graph
doesApplies one principle from the graph to one surface and writes one receipt. It names the next principle to visit.

gm-prd

closes one plan row
doesCloses one plan row through nine stages in one run. Invoked with row=<id>; session=<SESSION_ID>.

gm-continue

final check when the walk is done
doesRuns when the walk reaches COMPLETE with no pending plan rows. It searches for remaining work before the walk ends.

The orchestrator verbs

An agent dispatches a verb through the gm MCP server, using the gm_codemode tool. Without MCP, it writes the request to .gm/exec-spool/in/<verb>/<SESSION_ID>-<N>.txt and reads the reply from .gm/exec-spool/out/<verb>-<SESSION_ID>-<N>.json, where <N> is <pid>-<ms>-<counter>.

VerbDoes
instructionReturns the prose for the current phase, with the plan rows and the open mutables.
phase-statusReturns the compact state only: the phase, prd_pending_count and the pending mutables, with no prose.
transitionAsks the orchestrator to move to a target node. A refused move is a gate denial, which names the recovery verb.
prd-add, prd-resolve, prd-listAdd a plan row, close a row with recorded witness_evidence, and list open rows, one file per row in the project's .gm/prd/ folder, a per-project runtime path that this repository does not hold. Resolved rows move to .gm/prd-log.jsonl, in the same runtime folder.
mutable-add, mutable-resolve, mutable-listRecord an open question, close it once a live check answers it, and list the open questions.
fsm-vendorCopies the graph and the prose into the project so that the project can override them.
codesearch, grepcodesearch is ranked search over the project. grep is an exhaustive literal or regex scan that reports each hit as path:line.
recall, memorizeSearch the project's memory files in .gm/memories/, and store a memory.
exec_jsRuns code in a subprocess. A leading timeoutMs=<ms> line sets its budget, with a default of 300000 ms.
git_finalize, git_push, git_show, ci-statusCommit and push, show a commit, and check CI for a commit.
healthReports plugin versions, the subsystem and verb tables, error codes and watcher liveness. Recall and codesearch probes run only when the body sets probes to true.
gm_resultReads a reply that is cut at the reply size limit, from its spill file.

How the skills install

Install steps and MCP registration are on the distribution page. An install from a checkout links each skill directory into each skill root, ~/.claude/skills and ~/.agents/skills, rather than copying it: a directory junction on Windows and a symlink elsewhere. So ~/.claude/skills/<name>/SKILL.md and <checkout>/skills/<name>/SKILL.md are one file, so an edit to the source reaches both skill roots without a reinstall. The installers run beside skills/ or with GM_SKILL_SOURCE_DIR set. With no local source, they copy the release archive.
