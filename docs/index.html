1. What it is

gm is a stdio MCP server that runs one long task as one worker. The agent session is the model. gm makes no model calls of its own: the session reads what the tools return and decides what to do next.

Every event of a run goes to one append-only log. Each step starts with next_context, which returns the rules, the task, the events the session has not yet seen, and the open jobs. Work is done inside run_code, and a step ends with finish and a witness.

gm needs Node 20 or later. Its one runtime dependency is acorn 8.18.0, pinned, which parses JavaScript for the callers and impact tools.

2. Install

You need git, npm and Node 20 or later. From the folder of the checkout, run the setup once after a clone:

./setup.sh

The setup checks the tools, installs acorn if it is missing, pulls origin main if the checkout has no changes to tracked files, runs the gate, and prints three add-mcp commands. They run through npx, pinned to version 2.6.1. Run them in this order. The first only lists the gm entries. The second removes every gm entry, old or new, from the global configs. Remove matches any server whose name contains gm, so read the list first. The third installs gm for Claude Code at user level, so one entry serves every project:

npx -y add-mcp@2.6.1 list -g
npx -y add-mcp@2.6.1 remove gm -g -y
npx -y add-mcp@2.6.1 "node /abs/path/to/gm-new/tools/relay.mjs" -n gm -g -a claude-code -y

The setup runs none of these commands. Other agents do not get gm from this install; add-mcp can add it to any agent it lists by changing the name after -a.

The gate checks syntax, ASCII, the docs, the sources, the wiki, the skills, and runs a smoke test. A checkout that fails the gate is not used.

3. Connect Claude Code

The server is named gm. Start the agent in a project folder, and approve the gm server when it asks. In Claude Code, that is /mcp. The relay serves the folder the session opens, so each project keeps its runs under its own runs folder, and .gitignore should list runs/.

Each start opens the run, or resumes it after a restart. A run that has ended stays closed, and the next start opens a new run beside it.

The chapter 2 remove command clears any older gm entry from the global configs. A project that has its own gm entry in its .mcp.json keeps that entry, which overrides the user-level one in that project.

The entry starts tools/relay.mjs. The relay holds Claude Code's connection, and it runs the supervisor, which runs the worker. The relay and the supervisor are what make updates and restarts possible without a reconnect.

The server serves two skills, gm and gm-continue. Each is an MCP prompt, which prompts/list answers, invoked as mcp__gm__gm (the gm skill) and mcp__gm__gm-continue (gm-continue), and each is a resource: skill://gm/SKILL.md and skill://gm-continue/SKILL.md. A host gets both from the server, so no user-level copy of either skill is needed. The gm prompt takes the run's task. A host reads a skill resource with resources/read.

4. The loop

Each step

  1. Call next_context. It returns the rules, the task, the witness requirement, the events new since the last step in full up to 20,000 characters, the rest of those events and the older events in compact form, query (the seq range of the step, and how to read any event by seq), stepsLeft, prefixSha, and the open jobs.
  2. Do the work in one run_code call. The body is JavaScript in the project. Each verb is a function on gm: await gm.read_file({ path: 'a.txt' }).
  3. Verify: run what you built and read its output.
  4. Call finish with a witness. The witness quotes the evidence: tool output, labelled with the tool that returned it.

Inside a body

  • Independent calls go together in Promise.all. A call that needs another call's result waits for it.
  • A failed verb call returns { ok: false, error } as data. It does not stop the body. gm.try(fn) wraps a step that may throw.
  • gm.verbs() returns each verb's description and input schema.
const [spec, notes] = await Promise.all([
  gm.read_file({ path: 'spec.md' }),
  gm.read_file({ path: 'notes.md' }),
]);
const todo = [spec.output, notes.output].join('\n').split('\n').filter((line) => line.startsWith('TODO'));
await gm.write_file({ path: 'todo.txt', content: todo.join('\n') + '\n' });
return { todo: todo.length };

One step is one body and one finish. The body reads its inputs together, decides in code, writes independent results together, checks in the same body, and returns a compact result.

Witnesses

A witness quotes only what a tool returned, labelled with the tool that returned it. If a search did not return the target, the witness says so. A read is never presented as a search result.

5. The tools

By default the session sees three tools: next_context, run_code and finish. Every other verb is called from inside run_code as gm.<name>(args). With --surface tools each verb is served as a tool of its own.

GroupVerbs
Filesread_file, write_file, edit_file, stat_file, list_dir
Shell and jobsrun_shell, job_start, job_status, job_stop
Logquery_log (reaches every event of the run)
Searchsearch (BM25 over tracked files), grep (literal, regex or word)
Webfetch (any URL Node fetch serves; the whole reply, no cap on redirects)
Codecallers, impact (acorn)
Gitgit_status, git_add, git_rm, git_commit, git_push, git_log, git_diff, git_show, git_fetch, git_pull, git_checkout, git_branch
CIci_status (every page of runs, from origin's host)
Rowsprd_add, prd_list, prd_resolve, prd_delete, unknown_add, unknown_list, unknown_resolve
Wikiwiki_search, wiki_write
Reviewreview_packet, review_record, review_join

File paths may point inside or outside the workspace. A relative path is taken from the workspace, and an outside path should be absolute. A .. segment or a symlink that leads outside is followed, not refused. search and grep cover the workspace's git-tracked text files, and query_log reads the run's log. The git tools and the row files stay inside the workspace. A run_code body takes the same paths, for its file verbs and for the literal require() and import() specifiers it loads.

job_stop kills a shell job's process group, and the job ends killed with reason cancelled. A cancel from the host (notifications/cancelled) ends a foreground run_shell the same way, and that call gets no answer. A foreground run_shell whose request carries a progress token reports its elapsed seconds every 5 seconds.

run_shell is not confined to the workspace. A shell command can reach files outside it, for example through a hard link. A path check does not see that. This is a known limit, recorded below.

6. Background runs and stuck jobs

  • A body gets a budget of 180 seconds by default. timeoutMs sets it, at most 300000.
  • A body that finishes within its budget returns its value in the call.
  • A body still running after its budget becomes a background run, named body-N. The call returns the id at once, with the verb results logged so far. The body keeps running in its own thread.
  • job_status with waitMs waits for a job, for up to 30 seconds per call. When the body ends, it returns the value. Nothing is polled in a loop without a limit.
  • finish is refused while a background run is running, and it names the run. finish with stopBackground: true stops each run first, and logs each stop.
  • A background run is stopped at 30 minutes, the job lifetime, with its output tail logged.
  • At most four bodies run at once in one worker. A body beyond that waits in arrival order, and its job is shown as queued.
  • A restart stops the background runs and logs each as killed.

Stuck jobs

A running job that makes no progress for 180 seconds is stuck. Progress is output written by a shell job, a verb call in flight or just finished in a body, or the start of the job. The worker logs job-stuck once when a job becomes stuck, and job-unstuck once when it progresses again.

Each next_context reports the changes since the last step as jobsStuck and jobsUnstuck. It also lists every open job in jobsOpen, with its state, how long it has run, how long since it progressed, and whether it is stuck.

7. Updates

The checkout is a clone of origin main, so an update is a fast-forward pull. The relay checks for updates once, 30 seconds after it starts, and then every minute. GMNEW_UPDATE_MS sets the interval in milliseconds. Zero turns the checks off.

A check fetches origin. When main is ahead, and no tracked file has local changes, it pulls. If package-lock.json changed, it runs npm ci. Then it runs the gate on the new code. A pull that the gate rejects is undone with git reset, to the commit the checkout had before the pull.

A pull that changes a module the worker loads restarts the worker, so the new code loads. The modules it loads are listed in src/worker-modules.json, and the gate checks that list against the import graph; a change to a module it does not load restarts nothing. A change to a reloadable leaf (src/hot-config.mjs) reloads in place. A change under skills/ is served without a restart. The run resumes from its log, and calls in flight finish first.

A checkout with local changes, or a history that has diverged from origin, is reported and left alone. A check that cannot reach origin is reported and skipped. A check never throws. To update by hand, run ./setup.sh.

8. Files and runs

PathWhat it is
runs/ID/log.jsonlThe run's log. Append-only. Every event, with its sequence number and times.
runs/ID/rules.mdThe rules, read at every step and placed first in each reply.
runs/ID/task.jsonThe task and the run's settings.
runs/ID/jobs/Job status files and shell job output.
runs/ID/code/Body files of running bodies. Each is deleted when its body ends.

runs/ is ignored by git. The log is the record: query_log reads all of it, and a restart rebuilds the worker's state from it.

9. Limits, named and recorded

These are the limits the project has named, with what would settle each one. They are recorded in DESIGN.md.

LimitStatus and trigger
Windows process-group killUnverified. There is no Windows machine. Windows support is not claimed.
Rule re-injectionDeferred. Trigger: a live run shows a rule violated after a summary.
Subagent isolationDeferred. Trigger: a long-horizon run shows a single worker's limit.
No long live run yetHeld. The owner decides whether a long live run is required. The scripted long-horizon witnesses are scripted evidence only.
run_shell is not confinedA shell command can reach outside the workspace. A path check cannot see that.
Search recallBM25 in process found 16 of 18 on the measured queries. An FTS5 index found 17 of 18. The SQLite index was rejected: it adds 13.2 MB of idle memory per worker and native code. The in-process index was kept.
Resident memoryEach body thread costs memory while it runs. Memory stays above the base after bodies stop. It is bounded by the four-body cap.

10. Troubleshooting

MessageWhat to do
node is vXX. gm needs Node 20 or later.Install Node 20 or later, then run setup again.
npm ci failedCheck the network, then run setup again.
origin could not be reachedThe worker still runs. The next check tries again.
the checkout has changes to tracked filesCommit or stash them. Nothing is pulled while they are there.
the checkout and origin main have divergedThe checkout has commits that origin does not have. Resolve it by hand. Nothing is pulled.
pulled code that the gate failed, and reset to the commit before itThe pull was undone. Read the failing check names in the message, and fix the cause upstream.
the gate failedsetup prints the failing check names. Fix the cause, then run setup again.
