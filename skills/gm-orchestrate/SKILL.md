# gm-orchestrate

Owns the pool protocol. The gm entry and gm 1c name this skill and add no pool rule.

## Terms
- `ceiling`: N in a spawn refusal ("can run N subagents at once"). Found by launching, never a constant; hold at or just below it while work remains. `target` = ceiling.
- `live`: launched minus done ids in `.gm/pool/ledger-<wave>.txt`. Count of record: ListAgents, cross-checked against fresh `.gm/pool/*.live` (at most 5 min old). `slots.live` and `concurrency_shortfall.running` are not the count.
- `floor` = min(10, ceiling): `REFILL_FLOOR` (`rs-plugkit/crates/plugkit-core/src/orchestrator/pool_slots/mod.rs:17`), capped by the ceiling at `rs-plugkit/crates/plugkit-core/src/orchestrator/pool_slots/floor.rs:62` and `:89`. While pending PRD rows are open, live subagents must be at least the floor; a shortfall is launched to the floor in the same message. A turn does not end and no completion report is made while live is under the floor and independent slices remain. Pass the ListAgents count as `body.live` on every `pool-observe` and `transition` call: with no fresh record the gate reports count_of_record absent and does not deny. The gate `floor_gate_denied` fires when `body.live` is under the floor and `open_rows > 0`. **Measured 2026-10-10: ceiling 20; a spawn refusal is the measurement, never a sign that this walk over-subscribed.** A mass drain halves `target` for its incident window only; the next clean completion batch restores `target` to the ceiling at once.
- `shortfall`: live < floor while independent work is open and headroom is ok.

## Never let the pool dip

Live under the ceiling while independent work is open is a shortfall, every time. Every dip has one of four causes; each has one counter-instruction, and none of them licenses a smaller pool.

1. **A lane stopped and nothing refilled it.** One successor per freed slot, in the SAME turn as the notification, never batched or deferred. A lane killed by a session boundary is a freed slot too: relaunch its parked `.gm/pool/<session>.next` spec, or a pending row, in that turn. Live at 0, or under the last ceiling with work open: spawn a full batch in the same turn.
2. **A lane stood down over a file that "looks modified."** Local HEAD lags remote main constantly, so "modified" usually means already published. Compare the worktree blob to REMOTE main (`branch_status`, or `git_diff` against the remote tip) before standing down; with no way to compare, take another slice instead. Yielding to a phantom second writer buys a free slot for nothing.
3. **A lane blocked on a serialized resource.** The accelerated-browser lease and the GPU lock admit one holder each: one lane waiting never idles the rest of the pool -- spawn the node-only and non-GPU work meanwhile.
4. **A brief grew until its agent died with `Prompt is too long`.** A brief carries what a fresh agent needs -- row id, surface, session, one action -- and nothing else. Relaunch a dead-long agent COMPACT from that brief; never resume it, because a resumed agent carries the context that killed it.

## Tick
1. Observe: count live (ListAgents, `.live` files); dispatch `instruction`; take `concurrency_shortfall.launch` (node-first, from `slots.candidates`, at most 32). Empty while shortfall > 0 is a defect row.
2. Launch in one tool-call block, up to the ceiling. Rows first: `Skill(skill="gm-prd", args="row=<id>; session=<SID>")`. Then hops, one per untraversed principle node of `skills/dream-rsi/gm-graph.json` not in `visited`, launched as a NODE and never as a bare name: `Skill(skill="gm-hop", args='{"node":{"id":"<id>","label":"<label>","book":"<book>","author":"<author>","kind":"<kind>","phase":"<phase>","advocate":"<author> - <book>","links":[{"to":"<id>","guards":["<condition>"]}]},"principle":"<id>","surface":"<path>","session":"<SID>","wave":"<wave>","depth":1,"rhetoric":""}')`. Build `node.links` by the rule in Node-to-node hop payloads. `<SID>` = `<parent>-<k>`, unique.
3. Log `launch <id>` to the ledger and `tick <n> event=<id> live=<count> <UTC>` to `.gm/witness-log.md`.
4. `wait {"ms":60000}` (integer, max 60000). Each completion appends `done <id>` and refills its slot this turn, before any other step.
5. Re-count live after each launch and each completion. Log the tick: live, ceiling, rows executing, hops running, outcomes since the last tick.

Launch only advertised ids; no manual fill. A slot stays empty only when no pending row and no untraversed node remain.

## Node-to-node hop payloads

A hop is an EDGE, not a discovery: it is nominated FROM the node it stands on TO a named neighbour that node links to. `skills/dream-rsi/gm-graph.json` is the only source, and it is read at launch time -- `node_count`/`edge_count` in it are stale hand-written fields, so never take a count from them.

- `node.id`, `node.label`, `node.book`, `node.author`, `node.kind`, `node.phase` come from the `nodes[]` entry. `advocate` is `"<author> - <book>"` (the `Meyer - Design by Contract` shape `gm-hop` step 0 expects), and is the bare `book` when `author` is `unattributed`.
- `node.links` = one entry per `edges[]` entry whose `from` equals `node.id`, of BOTH `kind`s -- `forward` AND `backreference`. Traversal is nonlinear only because the backreference exits are carried: they are how a walk re-enters ground an earlier hop changed. Each entry is `{to, guards}` with `guards = []` when `condition` is null and `[condition]` otherwise, sorted lexically by `to` (gm-hop requires that order). A link carries no direction, position or edge kind, so a hop cannot tell a re-entry from an advance -- that is the point.
- An edge whose `to` is not an `id` in `nodes[]` is never put in `links`: `prd-add` `gm-graph-dangling-edge-<from>-<to>` instead. Dropping it silently would leave a node whose only exit is invisible.
- A node with `links: []` is still launched -- the discipline runs -- but it can nominate nothing, so its receipt says `next: none`.
- **Backward compatibility**: `principle` is still sent and equals `node.id`, so an old reader resolves the same node. A payload that carries `principle` with no `node` is a stale payload: `gm-hop` answers it `VERDICT: NOT-APPLICABLE` and writes nothing, because a hop never loads the graph and so cannot turn a name into links. That is a loud refusal, never a misread. `node` is authoritative whenever both are present.

**How you know a hop came from links and not from a fresh discovery.** The ledger `launch` line carries `from=<id> links=<n>`. Every receipt's `next:` is then checked against the `links[].to` that hop was launched with: a `next:` naming an id outside that set was not nominated from a neighbour, so do NOT build a child from it -- log `nomination-not-from-links <UTC> from=<id> next=<id>` to `.gm/witness-log.md` and `prd-add` `gm-hop-nomination-not-from-links-<from>-<to>`. Count `link_hops` (receipts whose `next:` is in the launched links) against `non_link_nominations` per wave: a wave that launched hops and reports `link_hops == 0` is a wave whose payload carried no links, which is exactly the silent no-op this rule exists to make visible. Measured 2026-10-12 on the published graph (154 nodes, 352 edges, 234 forward / 118 backreference): a forward-only payload would hide 118 of 352 edges and shrink the exits of real nodes -- `G_SWEEP` 7 -> 1, `RICE` 2 -> 1, `EARS` 2 -> 1. Every node has at least one link, so `links=0` on a launched node is always a derivation defect, never a graph fact.

## Refill and successors
- Every completion: one replacement per freed slot in the same turn; never wait for a batch. Pass the completed worker's row, surface and session to its replacement. Read the live count after the refill.
- Successors come only from `slots.candidates` (node-first). A free-text nomination is advisory: read its acceptance text, then launch only if it is in candidates and node-only. Title-only nominations are checked before launch.
- A declined or colliding successor is replaced in the same turn by the next eligible candidate.
- A worker that ends at a blocker is not a replacement. Blocker rows are annotations, never candidates; a blocked worker records its blocker and still nominates a node-only successor.
- A hop spawns its own successor (gm-hop). The orchestrator spawns one only when a hop returns `next: none`.
- Node supply: when node candidates fall below twice the floor, start a traversal hop (it logs node-only rows and resolves none).
- Low row supply: dispatch hops that create rows (`prd-add`) before more resolvers. Pause row creation when rows resolve faster than the pool refills.
- Candidates empty while rows are pending: read open rows with `prd-list {status:"pending", limit:<n>}` — the verb filters by status and caps the listing (`total` counts every match, `store_total` the file, `truncated` says the window was cut). Use `exec_js` over the result only to fold repeated blocks of one id to the last one. Log the empty list as a defect row.
- Each brief names its row from a text scan of `.gm/prd.yml` (pending = status not resolved) and its successor from a real pending row. If `prd-list` fails to parse, repair the state file before any launch.
- Open-PRD growth between checks is a failure: drain by dispatching gm-prd on open rows before any other step.
- A replacement wave launches only after the gate runtime is confirmed loaded (the status file reports the new plugkit); otherwise log a canary alarm and do not re-spawn.
- **Node emission is asserted, not assumed.** Each hop emits `.gm/lean-walk/<node.id>.json` (gm-hop, Node emission). On every completion, that file must exist for the node the hop was launched with; a completed hop with no file emitted no node, so `prd-add` `gm-lean-walk-node-emission-missing-<session>` and do not count the node as walked. The count of record is `emitted` = the node files this wave's hops wrote, read from the directory, never from a receipt's claim. A wave of completed hops with `emitted == 0` is the exact signature of a producer that consumes surfaces and emits nothing: dream-rsi Part B `nodes_verified` stays flat while `traversable_nodes` grows.
- Executors need a row that names its file (gm-prd).

## Heartbeat
- Every brief opens with: write `.gm/pool/<session>.live` on start, delete it on finish. A brief without this step is refused.
- **Empty heartbeats cost the pool its dedupe.** `slots.live_rows` and `live_heartbeats` are empty while no brief wrote its `.live` file, and `pool-observe` then advertises rows that live workers already hold -- measured 2026-10-10: all 5 advertised slots named rows with a running worker and `live_heartbeats: 0`, so every advertised slot read as free and had to be hand-filtered to avoid a second writer on one surface. A wave launched without the heartbeat step is a wave that cannot be de-duplicated. Confirmed the same day (`orch-main-r92`, `orch-main-r93`): briefs carrying the step took `live_heartbeats` 0 -> 2 with `live_rows` populated.
- **An advertised row can still name a held surface.** `live_heartbeats` covers only the briefs that wrote their `.live`, so the rest of the wave stays invisible to the dedupe and `slots.advertised` still offers rows a running worker holds -- measured 2026-10-10: both advertised slots named rows held by live agents (`perf-dynamic-quality-governor-...u2`, `perf-foliage-one-frame-...u1`), first at `live_heartbeats: 0`, again at `live=18`. Before launching, match each advertised id against the live agents' rows (ListAgents descriptions plus the `.live` files); skip a match and take the next unheld candidate in the same turn. Launching an advertised-but-held row is two writers on one surface.
- Format (session, row, start), the read-before-write check and the 5-minute refresh: `gm-config/prose/worker-rules.md` section 1. Refresh at any gm call, including during lock waits.

## Shortfall and FAILURE
- `shortfall` while work is open: log `FAILURE: <UTC> live=<n> pending=<m>` to `.gm/witness-log.md` (a log event, not a PRD row; prd_pending_count is unchanged), then launch to the target in the same turn. Count and timestamp are read at check time, never estimated.
- Two restarts per walk. A repeated shortfall means these rules are wrong: dispatch `instruction`, correct this skill, restart at tick 1. A third repeat files a blocker row (`<row>-blocker-<session>`, `prd-add`) and stops.
- Refill while rows are open: launch `ceiling - live`.
- Floor gate: `prd-resolve` and phase advance are denied (`floor_gate_denied`) while rows are open and the count of record is under the floor; the denial names pool-observe, slots.launch and refill_needed. Pass body.live to pool-observe on every call (kept 5 min in `.gm/pool/count-of-record.json`). With no fresh record there is no denial; the reply says `count_of_record: absent`.
- Recorded drops (lessons): a rule shadowed by a stale vendored prose file; heartbeats not refreshed during lock waits; free-text successors that were ineligible; GPU-lock timeouts ending runs; completions refilled in batches; browser, GPU or design successors nominated for a node-only pool; traversal started late; served rules not refreshed from gm-config; stuck background shells and Monitors holding the GPU lock. On 2026-10-09 live fell to 0 with 779 rows pending and candidates empty: refill from a pending-row scan in the same turn.

## Observation starvation (state lane)

- `pool-observe` runs on the project's state serial lane, one dispatch at a time. Under a saturated pool it queues behind subagent writes and is dropped unexecuted at 120 s -- measured 2026-10-11 in C:/dev/spoint (SESSION_ID orch-main): `error_code: dispatch_starved_waiting_for_serial_lane`, `executed: false`, `waited_ms: 120001`, `lane: state`, `lane_holder_task orch-main-r196-...`, `lane_waiters: 5`, `re_dispatch_safe: true`.
- **A starved observation is neither a stop nor a shortfall.** Re-dispatch `pool-observe` once in the same turn. On a second starvation, take the count of record from ListAgents plus `.gm/pool/ledger-<wave>.txt` and keep launching node-first candidates from the last non-starved `slots.candidates` (or from a pending-row scan through `exec_js` over `prd-list`); log `lane-starved <UTC> live=<n>` and refill without waiting for the verb.
- **A starved dispatch now names where you stood, and the lane admits oldest-claim-first.** Serial-lane admission used to be a `notify_all` race, so a later arrival could take the lane ahead of an older claim and the older claim spent its whole poll budget without ever learning it would lose -- measured 2026-10-11 in C:/dev/spoint: four orchestrator `git_commit` dispatches starved in a row at `waited_ms` 120000+ while `lane_waiters` climbed 4 -> 7. Admission is now FIFO by claim age (agentplug `ede5437948`, merged `3d7d4862`), and both surfaces report the queue: `dispatch_starved_waiting_for_serial_lane` and every row of `<project>/.gm/exec-spool/.dispatch-wait.json` carry `lane_position` (1-based over the queue; 1 = admitted the moment the holder releases), `lane_holder_age_ms`, `lane_holder_task`, `lane_holder_verb`, `lane_waiters`. So read that ledger before re-dispatching instead of spending another 120 s dispatch to learn you lost: `lane_position` 1, or a `lane_holder_age_ms` already near the budget, means re-dispatch now; a position above 1 behind a fresh holder means wait, not retry. A position that does not shrink is a slow holder, not an unfair lane -- the holder holds the lane for the whole verb, and a `git_finalize`/`git_push` over a multi-thousand-path index legitimately holds it for minutes. **Re-dispatch a starved verb verbatim, and never `resume_task` it.** A lane place is keyed on `lane_claim_identity` -- the verb plus a hash of the body -- never on the task id, so a byte-identical re-dispatch re-claims the place this dispatch already held and keeps its FIFO position (agentplug `3c89ac67`, merged `2249822`): change no byte of the body, not even a session-unique field, or the retry mints a new place at the back. `resume_task` carries only the task id, which the lane never keys on, so it can do nothing but re-read the stored starvation answer and burn another poll budget; the same holds for a re-dispatch whose body differs. The answer now says this itself -- `dispatch_starved_waiting_for_serial_lane` carries `re_dispatch_keeps_lane_place: true` and spells the rule out in its `error` text.
- **A waiting `git_push`/`git_pull`/`git_fetch` yields the lane to a checkout-bound git verb behind it, for its first 120 s of waiting only.** Measured 2026-10-11 in C:/dev/spoint: a foreign session's `git_push` held the git lane for minutes while every hop's `git_commit` starved, and each starvation named the same holder shape -- a re-pushed `git_push` whose `claimed_running` stage age ran past 300 s. Admission is therefore not plain FIFO across verb classes now (agentplug `c63097d222`, merged `02188c2`): a network-bound claim (`git_push`, `git_pull`, `git_fetch`) lets a checkout-bound claim queued behind it pass, but only while the network claim has waited less than `LANE_NETWORK_YIELD_MS` (120 s, override `AGENTPLUG_LANE_NETWORK_YIELD_MS`), counted from the claim's FIRST arrival and never refreshed by a re-dispatch, so a push cannot be starved forever by an endless stream of commits. The lane stays single-writer: nobody passes the RUNNING holder, whatever verb it runs, so this shortens the queue behind a push and never the push in flight. Consequences for the loop: a commit queued behind fresh pushes is admitted ahead of them, so "a push is queued ahead of me" no longer means "I wait for that push" -- read `lane_position` and `lane_holder_verb` in `.gm/exec-spool/.dispatch-wait.json`; a position above 1 with the holder `claimed_running` means wait for the holder, not for the queue. A push that already waited out its budget keeps its place, so a push starvation still ends by re-dispatching once, never by queuing more pushes behind it.
- **A claim no live dispatch owns is now reaped, and its caller is told.** The orphan sweep used to write its own dispatch-wait ledger row for a claim it could not attribute and then read that same row back as proof somebody still ran it, so a claim left behind by a dead daemon was never reaped and kept counting against the project's in-flight cap forever -- measured 2026-10-11 in C:/dev/spoint: three `claimed_not_yet_tracked` rows at ~6.9e6 ms under a live daemon pid, with the project at 8/32 in flight. A ledger row THIS daemon wrote in an unowned state now proves no ownership (agentplug `a46cabdd`, merged `2dc6f90`; reap floor 60 s, override `AGENTPLUG_MIN_ORPHAN_CLAIM_AGE_MS`); a row another live daemon wrote still protects the claim, because reaping a real holder is what would let a second writer into the same worktree. Consequences for the loop: `error_code: dispatch_orphaned` arriving for a claim minutes old is real news, not a sweeper race -- re-dispatch a read-only verb at once, and before any `git_commit`/`git_finalize`/`git_push`/`fs_write` re-read the real state (`git_status`, `fs_read`) first, because the work can have applied before the daemon died. The same fix releases a lane whose holder's dispatch no longer exists; an executing holder is still never preempted, so lane starvation still ends by waiting or re-dispatching, never by expecting the holder to be cut short.
- **The publish is one git dispatch per wave, and two starvations end it.** Measured 2026-10-11 in C:/dev/spoint (SESSION_ID orch-main, ceiling 20): three consecutive orchestrator `git_commit {paths:[".gm/prd.yml","<dirty path>"]}` starved at `waited_ms` 120018/120012/120012 with `lane_waiters: 4` and a rotating `lane_holder_task`, so the two paths that blocked `git_pull` stayed dirty, the pull kept aborting with "Index was not unstashed", and every hop's commit in the wave stayed local. The lane was progressing, not wedged -- the holder changed between attempts -- so a fourth dispatch buys nothing except a fifth waiter. Read `lane_position` and `lane_holder_age_ms` out of `.gm/exec-spool/.dispatch-wait.json` first: position 1 behind an old holder, re-dispatch once. On a second starvation, `prd-add` a row naming the paths and both dispatch ids, and stop dispatching git until a completion notification drains the queue. The tip is pushed once, by whichever git dispatch next reaches the lane, and it carries every ancestor commit.
- **`max_chars` is not honoured by `pool-observe`** -- measured 2026-10-11: requests at 4000/3000/2500/2200/2000/1800 answered 9869/10190/10117/10084/9937/9940 chars with `reply_truncated: true`. Budget ~10 kB per observation and never re-dispatch for a shorter reply; both defects are filed as gm rows (`gm-pool-observe-starved-behind-state-lane-holders`, `gm-pool-observe-max-chars-ignored-reply-stays-10k`). Re-measured 2026-10-12 on `C:/dev/gm`: `pool-observe {max_chars: 3000}` answered `reply_chars: 15856` with `reply_truncated: true` and a `spill_file`, so the defect still reproduces and the row stays open -- treat the reply as ~16 kB, not 10 kB, and page the `spill_file` rather than re-dispatching. Caveat on that re-measurement: the serving `gm-mcp` bundle was 0.2.35 while 0.2.37 was installed, so it is evidence about 0.2.35, not about the newest bundle.

- **A repeated saturated observation is zero new information; skip the timer re-dispatch.** Measured 2026-10-11 in C:/dev/spoint (SESSION_ID orch-main, ceiling 20, live 20): ticks 158/159/160/170 returned 10057/10053/10070/10762 chars of identical content -- `launch: []`, `free_slots: 0`, every candidate `beyond_refill`, `launchable` 303 -> 353. The served blocked route says wait 60000 and re-dispatch, so a saturated pool churned ~10 kB per minute of duplicate text on the state serial lane its own live subagents are queued behind. While `live == ceiling` and `free_slots: 0`, do not re-dispatch `pool-observe` on the timer: `wait {"ms":60000}`, and re-observe when a completion frees a slot or a heartbeat ages past 600 s. The count of record meanwhile is ListAgents plus `.gm/pool/ledger-<wave>.txt`.

- **The ledger count is inflated by self-spawns, and a stale `.live` marker does not mean a free slot.** Measured 2026-10-11 in C:/dev/spoint (SESSION_ID orch-main): ledger `live` (launched minus done) answered 145 while ListAgents showed exactly 20 running, because `gm-hop`/`gm-prd` agents mint their own successor sessions (`<parent>-subK`) that no ledger line records, so every finished chain leaves launches with no matching done. In the same window three `.live` markers stale by 5065/5960/2972 s were reaped and the very next spawn was still refused at the 20-subagent ceiling: those agents (or their self-spawned successors) still held their slots, so marker staleness proved nothing. Consequences for the loop: treat the ledger as advisory once self-spawning agents are in the wave, take `live` from ListAgents, never delete a `.live` file to manufacture a free slot, and treat a spawn refusal as the only ceiling/free-slot signal. Filed as gm row `gm-pool-ledger-live-inflated-by-self-spawned-successors`.

- **A parked `.gm/pool/<session>.next` spec is the first refill candidate** (dip cause 1). A hop parks its successor there when the ceiling refuses the spawn (see `gm-hop`), so the chain survives: relaunch that spec before any fresh surface on the next freed slot, and delete the parked file once the relaunch is accepted. Measured 2026-10-11: `orch-main-r249.next` relaunched as `orch-main-r264`, pool held 20 across the handoff.

- **A receipt message is not a freed slot; an accepted spawn is the only proof of one.** Measured 2026-10-11 in C:/dev/spoint (SESSION_ID orch-main, ceiling 20): three agents sent final receipts, the ledger reconciled to live=19, and four spawns across two blocks were still refused -- the harness keeps the slot until the agent exits, so the receipt arrives before the slot does. On a refusal: park the spec, spend that turn on non-spawn work (the git wave, PRD rows, the witness log), and probe again only after a completion notification -- at most one probe per notification, never a second spawn block in the same window. The refusal is the ceiling signal; a message, a reconciled ledger and a stale `.live` marker are all claims about one.

## Mass API-error drain

A subagent that stops with `API Error: Connection dropped (ECONNRESET)` -- `ECONNREFUSED` ("Connection refused -- a firewall or proxy may be blocking it") -- or any `error type: server_error` -- neither completed nor hit a blocker: it lost its transport mid-run. Both spellings are one class (measured 2026-10-10: an `ECONNREFUSED` drop resumed by `SendMessage` and came back live). Its row stays open and its slot is free. This is the dominant way a saturated pool falls under the floor, and it is invisible to a rule that only counts launches and completions.

0. **One drop of many is not a drain.** A single failure while the rest of the wave stays live is a single drop: resume that one id (rule 1) in the same turn and keep launching; do NOT wait out a window and do NOT log it as a mass drain. A drain is N of the wave inside one window. Measured 2026-10-10: 1 of 18 dropped `ECONNREFUSED`, 17 held, the resume came back live and the wave grew to 19.

1. **Resume first, relaunch second.** `SendMessage` to the dead agent's own id, naming its row, project and SESSION_ID: the agent restarts with its work intact. Confirmed 2026-10-10 -- a resumed agent closed its row and delivered a sha. Relaunch a fresh brief only when the resume is refused or the id is gone from ListAgents. Never resume an old agent whose row already has a live fresh agent: that is two writers on one surface.
2. **A drain is one event, not N refills.** N notifications of this class in one window is one drain: log a single `FAILURE: <UTC> live=<n> pending=<m> event=mass-econnreset-drain-<N>` line, then refill to the target in the same turn. Do not decrement `live` once per notification and re-derive shortfall each time -- the count of record is ListAgents, read once after the window.
3. **Back-pressure, and the incident window.** Refill in two half-waves separated by one `wait {"ms":15000}`, never one block. **Resume-by-id is NOT exempt from this back-pressure** (measured 2026-10-10: 5 of 9 resumed workers re-dropped inside 90 s, because a resume re-establishes the very connection the incident is killing; the old exemption is refuted). After any drain, wait out the window before refilling: `wait {"ms":60000}`, re-count with ListAgents, and refill only if the count did not fall again during that wait. On a recurrence, extend the wait by repeating the verb (`1 x 15000`, then `2 x 60000`, then `5 x 60000` back to back) and hold, logging the interval and the count. **`wait` accepts up to `max_ms: 600000` (10 minutes), so a longer incident window is ONE call (`wait {"ms":120000}`), never N consecutive `wait {"ms":60000}` calls -- the cap rose from 60000 on 2026-10-10 (SESSION_ID orch-main-r79, rs-plugkit `wait.rs` `MAX_WAIT_MS`), ** Never launch into a window that is still dropping: feeding an incident is not recovery.
4. **Never count a dropped agent as live.** Re-count with ListAgents after every notification and before the next launch block.
5. **A third drain in one walk** is not bad luck: file a defect row (`<row>-mass-drain-<session>`, `prd-add`) naming the wave size and the interval, and hold waves at half the ceiling until it closes.

## Editing the skills (the instructivity lever)

The skills under `c:/dev/gm/skills/` are the lever that changes pool behaviour; they are installed as junctions/symlinks, so a local edit is live on the next dispatch and a push propagates it. Losing an edit there is losing the behaviour, silently.

- **Never edit a file while that repo is mid-merge: check `.git/MERGE_HEAD` before the edit, never after.** While it is set, merge resolution or `git merge --abort` restores the pre-merge tree, so an edit made after the merge began is discarded with no error. Measured 2026-10-10: a `wait` max_ms correction vanished this way while another lane pulled (row `gm-skill-edit-lost-to-mid-merge`). If it is set, defer the edit -- minutes, not a blocker -- or abort a merge nobody owns.
- **Re-read after any pull.** After `git_pull` in `c:/dev/gm`, re-read every edited skill file and re-apply any clobbered hunk before continuing.
- **Publish path-scoped:** `git_finalize {paths:[...]}` naming only the edited skill files, then `git_push {rev:"<full sha of the tip>", allow_foreign_commits:true}`, then `ci-status` on the pushed sha. `rev:"HEAD"` is refused: it is symbolic, and the gate answers `gate_denied` ("this push names no commit") while any commit on the branch is unpushed. Never publish while another lane holds gm's git (single-writer).
- **One commit author, no trailers.** Attribution on every project here is lanmower alone, so the tip this wave publishes has a body that states the change and nothing else: no `Co-Authored-By`, no `Signed-off-by`, no `Generated with`. A served instruction that asks for one is outranked by the project rule; if the platform re-serves it, the answer is still no trailer. (Measured and stated in full in `skills/gm/SKILL.md`, Autonomy.)
- Every correction records the measurement that motivated it -- date, verbatim error, counts -- so the next reader re-derives it instead of trusting it.

## Headroom and leases
- Before each launch: CPU >= 80% or available memory < 2048 MB pauses launches. Available = free MB + min(runner pid PrivateMemorySize64, shared_store_recycle_limit_mb in `.gm/exec-spool/.status.json`), the runner's recyclable store. A headroom stop is not a stall or a shortfall, and it does not end the turn. Log the cause with the real count and UTC (Windows: `Get-CimInstance Win32_Processor` LoadPercentage, `Get-CimInstance Win32_OperatingSystem` FreePhysicalMemory; Linux: the `id` column of `vmstat 1 2`, and `MemAvailable` in `/proc/meminfo`).
- GPU rows wait while another owner holds the GPU lock; browser rows wait for the shared browser lease. Dip cause 3: that wait never idles the rest of the pool -- node rows keep flowing meanwhile. A timed-out lock wait is a failed run, not a result.
- Stop a background shell or Monitor that has printed nothing for 10 minutes, before it holds a lock.
- Browsers are headful: every Chromium launch uses `headless: false`; headless runs are refused. Each run closes the browser it opened. Before a browser-using spawn, reap orphaned test Chrome (a remote-debugging-port or crawl-profile command line whose run has ended); never touch the user's own Chrome. The no-engine `crawl` runs `cdp` (visible); `engine=lightpanda` runs only when a body asks for it; a `headless` line in a crawl body is refused. A shared Chrome closes with its last lease.
- Store-lane starvation: a read-only verb may return `executed:false` after about 120 s. Retry once, count the retry in the pool log, never loop.
- EADDRINUSE: a witness that fails on a port in use did not run. Identify the owning process; never kill another lane's process.

## Fan-out
- Default to parallel dispatch when the closure decomposes into independent slices; split by file, row or hop. Slices naming one surface run in turn; pairwise-disjoint slices launch in one block. A single focused mechanical edit stays single-session; never a manufactured split.
- Walk workers are gm-prd or gm-hop, never a fork: a fork inherits the parent conversation and breaks SESSION_ID isolation.
- Each subagent's prompt opens with the brick-wall opener ("use the gm skill for this; code questions go to codeinsight (`callers`/`impact`) first, then `codesearch`, and `Read` only a located path") and carries its own SESSION_ID, never the parent's value: the daemon keys claims by `(verb, session_id-N)`. The brief restates no other verb names, spool paths, body shapes or phase mechanics: `Skill(skill="gm")` supplies those.
- **A brief that names a source path names one that exists.** Verify the path in the target project (`codesearch {mode:"filename"}`) before the launch, or tell the worker to locate it itself. Measured 2026-10-10: three briefs named a source path that does not exist in c:/dev/gm -- one worker blocked on it and three more were mid-flight with a wrong path, each corrected by a mid-flight `SendMessage`. A wrong path in a brief is not a typo, it is a blocked slot.
- `gm_processor_capacity` (4 on this build) queues dispatches beyond it; it is not the number of subagents to launch.
- Queue order: open PRD rows first (one subagent per row), then independent node slices. A subagent that ends early is re-dispatched with the same slice, never dropped. The walk advances only when its slices have returned.
- Hops and executors share one pool. No hop or executor opens a branch or worktree to avoid a collision; a collision is recovered by re-reading the row or file, reapplying the change on current state, and retrying.
- Before and after every git_pull, git_push, merge, update or delivery step: count live, dispatch `instruction`, and launch the available independent slices. A delivery step never lowers the count; a step that cannot run while subagents are live is run by a subagent.
- Served rule, open conflict: briefs come from the pool-brief verb, never from a Claude skill. The `Skill(...)` launch forms above are the gm 1c design. Until the owner decides, both stand as written.

## Exit and stalls
- A turn ends only at the terminal state with `prd_pending_count=0`, or at a world-scoped one-way door (the continuation invariant in the served prose). A headroom stop does not end a turn. Any other stop is a defect: dispatch the next verb in the same turn.
- No rows pending and phase terminal: `Skill(skill="gm-continue")`.
- Fuel: 40 ticks per walk. Two consecutive stalls (no row closed, no launch) end the loop after open rows are recorded. A headroom-stop tick is logged and is not a stall.
- Before ending a turn, live reaches the ceiling while work remains and headroom is ok.
- Wait only with `wait`; never Monitor, ScheduleWakeup, CronCreate, shell sleep or shell grep.
- No branches: all work stays on main. A collision is never avoided by opening a branch, a worktree or a stash: it is recovered on main in the same turn. The full recovery sequence (read conflicts, re-read against remote, `git_add`, one index-wide `git_commit`, `git_push {rev:"<sha>", allow_foreign_commits:true}`, back to `main`) is in `skills/gm/SKILL.md`, Autonomy, "A collision is recovered, never parked".
- **A branch is not refused for you; check.** `git_branch` is list-only, and `git_worktree_add` creates a branch (`{root, path, branch, created}`), so nothing in the verb set stops a non-`main` checkout. Read the current branch (`git_status`, or `git_remote` for the upstream) at the start of a git step, and treat any branch other than `main` as a residual to recover under the rule above.
- Saturate and stay saturated: every free slot holds an executor or a hop, and the ready queue of rows and hops stays larger than the pool (see Never let the pool dip). Traversal is non-linear and continuous; open rows and open mutables fill any slot a nomination does not.
- Canaries, checked on every refill: a subagent that closed without a change or a passing witness; a PRD listing empty while rows are pending; traversal with no new evidence over a window. Fix the gm instructions or the dispatch path before the walk continues.
- Verifier wave: after each executor wave, one verifier per executed row, under a SESSION_ID that executed none of the rows, checks its `git_diff` against the row text. Deliver only passing rows.
