NEVER test or debug gm-plugkit cli.js/bootstrap.js by running node or bun directly against the gm source-repo checkout on a machine that has other live gm watchers -- it triggers a machine-wide crash-loop storm, not a contained failure. Mechanism: ~/.gm-tools/ is a SINGLE shared install directory across ALL gm-driven projects on the machine, and every project's watcher checks the shared on-disk wrapper's sha every 10s. A direct node/bun invocation from inside the repo checkout copies the repo-local dev-tree wrapper over that shared install via ensureWrapperFresh(), so every other project on the machine simultaneously detects wrapper-sha-drift and cascade-kills plus respawns its watcher at once. Correct practice: use `bun x gm-plugkit@latest` for any live-system testing (it always fetches an isolated npm-temp copy, so it cannot clobber the shared install), reserve direct-node invocation for syntax/unit-level checks only, or run in a scratch/isolated environment. A guard now exists in gm-plugkit/bootstrap.js: ensureWrapperFresh() refuses the shared-install overwrite when invoked from a detected gm source-repo checkout unless GM_PLUGKIT_ALLOW_DEV_WRAPPER_OVERWRITE=1 is set. RECOVERY CONTEXT worth keeping: this lesson was found only because it had been stranded on disk as an orphaned .md.tmp-<epoch> file whose memorize-fire rename was interrupted mid-write -- it existed as bytes in .gm/memories/ but was absent from the recall index entirely, so no recall query could ever surface it. Seven such orphans accumulated across several days. When triaging .tmp- residue in a memory store, check whether the corresponding final .md exists before deleting: if it does not, the temp file is the ONLY copy of that memo and deleting it destroys real content -- complete the interrupted rename instead, then re-fire the substance so the index gains what the filesystem already had.
