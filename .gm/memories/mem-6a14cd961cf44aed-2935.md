gm session debugging lessons, witnessed 2026-07-28 across a full system-verification sweep.

NEVER BUILD JSON DISPATCH BODIES WITH SHELL printf. printf interprets backslash-n as a real newline byte, invalid inside a JSON string value. The body is then unparseable, and an existing unwrap_or(Value::Null) SILENTLY substituted null so every field read as absent. This convincingly mimics unrelated bugs: handlers report missing-argument errors that look like the verb ignoring input, and two equivalently-malformed bodies produce BYTE-IDENTICAL generic errors that look exactly like a response-cache collision. A cross-verb response-cache defect was filed on that evidence and was wrong. Use json.dumps or a heredoc. request_fingerprint and body_parse_error now stamp every response so this is self-diagnosing: if the fingerprint does not match your request, or body_parse_error is set, the fault is the request.

VALIDATE THE REQUEST AS STRICTLY AS THE RESPONSE. Every wrong conclusion in that session came from inspecting responses without checking the request was well-formed on disk. A json.load on the request file catches it in seconds.

CHECK WHICH DIRECTORY IS ACTUALLY LOADED BEFORE DIAGNOSING STALENESS. agentplug-host install_dir() resolves to ~/.agentplug, NOT ~/.gm-tools. The latter is the dormant legacy launcher edge, bypassed once tryDelegateToRunner succeeds; its stale version markers and absent slim wasm are expected by design. Six PRD rows were filed against the wrong directory and superseded.

GREP THE SERVED ARTIFACT BEFORE CONCLUDING A CODE REGRESSION. Grepping the actually-loaded wasm for the expected string takes seconds and twice overturned a conclusion that would have sent an agent to edit correct code.

A LIBRARY IS NOT GUILTY UNTIL ITS SOURCE SAYS SO. A 545MB wasmtime compiled-module cache was blamed for serving stale code; wasmtime source showed its cache key SHA256-hashes the full wasm bytes plus compiler settings, so it cannot serve stale content for changed bytes. Real cause was upstream: get_or_compile keyed on plugin NAME not content, and the pool per-slot fill guard never revisited a filled slot, producing mixed-version pools.

MIXED-VERSION POOLS INVALIDATE VERIFICATION ITSELF. When different dispatches are answered by differently-compiled modules, a check passes or fails depending on which slot answers. Two wrong conclusions traced to this. daemon-status.json now exposes loaded_plugin_content_sha256 and mixed_version_pools; check them before trusting any post-fix verification.

AN ALIVE PID MEANS WAIT, NEVER REBOOT. A heartbeat can go 200+ seconds stale under genuine load while the process is alive and serving. Rebooting on the timestamp alone kills a healthy daemon and discards concurrent agents in-flight dispatches.

DO NOT STASH ANOTHER SESSION IN-FLIGHT WORK. Wait for the agent to close its own loop; a scoped stash is only safe for files provably nobody else holds.
