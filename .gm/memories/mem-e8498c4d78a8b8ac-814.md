gm-method: cas_retry_write (cas.rs) has an N-writer coordination gap beyond simple TOCTOU -- its post-write confirm-read only protects the writer that ran it; a later concurrent writer can clobber an earlier writer's already-confirmed data with no one left to detect it, since the earlier writer already returned Ok. This surfaced live via 4 parallel mutable-add dispatches, one silently lost despite the daemon reporting success. Fix needs true version/hash-based CAS or file-level write-serialization across every mutable-add/mutable-resolve/prd-add/prd-resolve call site, not a local atomic-rename patch. Lesson: any multi-dispatch batch writing to the same gm state file (mutables.yml, prd.yml) should be serialized one-at-a-time by the calling agent, not parallelized, until this is fixed at the daemon level.
