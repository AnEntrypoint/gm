A diagnostic reader that acquires the same lock a worker holds inherits the worker's duration, so a heartbeat published through a blocking read of worker state goes stale exactly when the system is busiest -- which is when every client reads it as dead and starts a competing process. Publish worker state through a try_lock snapshot that reports "busy" as a real third answer instead of waiting until it is no longer true. Two corollaries found in the same pass: try_lock on a poisoned mutex returns Err forever, not just while held, so treating that Err as "busy" permanently removes the resource from its pool and one guest panic can wedge the whole pool -- recover the guard instead; and a pool of exactly one slot makes any fairness reservation arithmetically impossible, so a cheap/expensive class split needs at least two slots before it can bite. Ordering rule for contended ownership: check the cheap atomic claim before any setup work (a subprocess, a network seed, an announce), because losing the claim after that work multiplies waste by the caller's retry rate; and a claim loss should arm a doubling backoff that is honored only while the current owner process is alive, so a genuinely dead owner is still replaced at once. A fallback worker that takes over a queue must be gated on the owner being DEAD, not merely slow, or it double-claims the same requests and rewrites the shared status file out from under the real owner.
