.gm/browser-config.json full field reference (drained from skills/gm/SKILL.md as single-surface reference detail). Six tunable fields total, per-project, ALL optional, loaded by BrowserConfig::load and re-read on every browser dispatch -- a missing file or a missing individual field falls back to its default, so an unconfigured project sees zero behavior change and never needs this file to exist. Fields and defaults: session_idle_timeout_ms (default 1800000, i.e. 30 minutes -- how long a live Chrome session sits idle before the reaper kills the process; the on-disk --user-data-dir profile under .gm/browser-chrome-profile-<session_id>/ survives regardless, so a later session new under the same id still gets a warm profile). cdp_poll_timeout_ms (default 1000 -- per-attempt timeout when polling Chrome's /json/version HTTP endpoint while waiting for the CDP port to come up). cdp_poll_interval_ms (default 250 -- delay between those poll attempts). chrome_ready_deadline_ms (default 30000 -- total wall-clock budget for Chrome to become CDP-ready before the launch is abandoned; this is the timeout behind the 'chrome CDP endpoint did not become ready within 30000ms' error text). eval_timeout_grace_ms (default 6000 -- extra grace window added on top of a dispatch's own timeout= prefix before the eval is force-killed, so the effective kill deadline is timeout= plus this). headless (default FALSE -- Chrome launches headful and visible by default; only a project that genuinely wants headless, e.g. CI with no display attached, sets {"headless": true}). Practical note: when a browser dispatch fails with a CDP-readiness timeout, chrome_ready_deadline_ms is the knob, but a readiness timeout is much more often a profile-dir lock collision with an unreaped stale Chrome holding the same --user-data-dir than a genuinely slow launch -- check for an orphan process on that profile before raising the deadline.
