gm-method: agentplug-runner implementation detail (drained from AGENTS.md, single-crate: agentplug). It self-updates both the wasm it serves and its own executable autonomously via two 600s polls, swapping in a staged .new runner on the next idle tick with no restart ever required; a dispatch landing mid-handoff returns dispatch_orphaned (bare re-dispatch is the fix). The launcher-edge install path (~/.gm-tools) and the runner's own runtime state (~/.agentplug) are two different directories -- always check ~/.agentplug/plugins/gm.version for what is actually being served. Each sibling plugin carries a persisted ~/.agentplug/plugins/<name>.fiber-state.json (PluginFiberLifecycle: Inactive/Active/Unloading, advanced by advance_plugin_fiber on every load attempt) -- the same fiber-lifecycle abstraction gm's discipline mechanism uses, generalized to the plugin subsystem. main.rs's reconcile_plugin_manifest names the per-dispatch sibling-loading loop as an explicit declarative reconciliation (Cordis Section 5.2.1: diff a desired {plugin: version} roster against installed_plugin_version, drive only what differs); registry.rs's get_active_provider mirrors the paper's provider_k(gamma) (Definition 46), naming each SharedPluginPool as the service-broker entrypoint (Section 6.2) it already structurally is.
