Second Cordis-alignment wave on gm's discipline mechanism (rs-plugkit commit e8e4d95, after 1881d1e/3e900b5): (1) discipline-check-removal verb + removal_dependents() implements the paper's withdrawal-ordering guard (Theorem 63) -- names every enabled dependent still relying on a discipline's provides before disabling it, so removal can be deferred rather than silently breaking a satisfied requirement; (2) a Component struct unifies a discipline's requires/provides/policy-effect into one (d,p,e) type per Definition 43, replacing three independently-read files with one canonical read path. Known-remaining gap against the full paper: no persistent lifecycle state machine (Inactive/Reloading/Active/Unloading) exists for disciplines/plugins -- gm's architecture recomputes coeffect satisfaction fresh on every instruction call rather than tracking a stateful fiber, so the guard is advisory (surfaces dependents) rather than lifecycle-enforced (blocks removal outright). A stateful fiber model would require gm's disciplines/plugins to persist activation state across dispatches, a substantially larger architectural change than the paper's per-mechanism mapping done so far.
