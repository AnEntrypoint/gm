agentplug-runner self-update takeover can STARVE on a busy shared daemon -- a staged newer binary may wait indefinitely while every session keeps executing old code. Confirmed against real source, agentplug/crates/agentplug-runner/src/daemon.rs: the main loop accumulates `any_work` across ALL projects the daemon serves (lines ~1399-1401), and the handoff is gated behind `if !any_work` (line ~1467) before calling attempt_self_update_handoff. On a machine where one shared daemon serves many projects (43 active_projects observed live), that idle precondition may effectively never hold, so stage_runner_self_update keeps succeeding while the swap never fires. WITNESSED 2026-07-29: ~/.gm-tools/agentplug-runner.exe.new staged Jul 29 14:02 from a CI-green build, live agentplug-runner.exe still Jul 28 16:13 across a 10-minute observation window, daemon-takeover-ready.json present, both poll errors null, daemon even restarted under a fresh pid mid-window without completing the swap. THE HANDOFF PROTOCOL ITSELF IS SOUND, do not go rewriting it: attempt_self_update_handoff spawns the staged exe as `takeover <version>`, polls up to 40x250ms for a readiness marker whose version field must match, and only then calls release_ownership_for_handoff (which deletes the owner lock only if this pid still owns it); run_takeover pre-warms all four plugin modules, writes the readiness marker, then waits up to 480x250ms to claim ownership before entering the normal loop. That is a correct, bounded, crash-safe dance. The defect is ONLY the unbounded idle precondition in front of it. DIAGNOSTIC RECIPE when a fix seems not to take effect: stat ~/.gm-tools/agentplug-runner.exe and compare its mtime against when the fix was built, and check whether ~/.gm-tools/agentplug-runner.exe.new exists -- if .new is present and newer, the code you are looking for is built and downloaded but NOT running, and any log grep for its new events will return zero. Reading that empty grep as 'the defect stopped occurring' rather than 'the instrumentation is not live yet' is the trap. Note daemon-status.json exposes poll timestamps but NOT staged-update state, so starvation is invisible without manually stat-ing the .new file. NEVER force-kill the shared daemon to hurry a swap -- other projects have in-flight dispatches and a kill discards their work.
