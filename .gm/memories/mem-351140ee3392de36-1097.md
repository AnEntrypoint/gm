find/grep/rg via Bash are never sanctioned in gm, with zero exceptions -- not even for a quick operational check like counting queued spool files. codesearch is the sole surface for code/file/symbol/prose content search (cwd or any external root). Runtime-state files (spool response JSON, .status.json, .turn-summary.json) are Read directly since they're a known exact path, not a search target -- this is the sole narrow exception. A Glob call on an exact spool pattern (e.g. '.gm/exec-spool/in/**/*.txt') to answer a 'which/how many files are queued' runtime question is a sanctioned instance of that same runtime-state exception, never a general Glob/Grep fallback for code or documentation content. The reason: an agent invoking find/Glob/Grep for content search can walk an entire filesystem uncached and unbounded per call; codesearch is a purpose-built cached incremental index. This is a resource/blast-radius boundary, not a style preference -- internal tooling/scripts/the daemon itself may do filesystem walks as an implementation detail, but the agent never reaches for that directly.
