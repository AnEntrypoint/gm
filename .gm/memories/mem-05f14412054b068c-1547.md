agentplug daemon.rs write_project_heartbeat_with_queue_info's runner_update_in_progress/runner_update_waiting_ms fields get permanently stuck (identical value forever, surviving even a real version handoff) because the code only has `if let Some((staged_at_ms,_)) = cached_staged_runner() { set both fields }` with NO else/None branch to remove them -- each write reads the prior status.json as its base and the two fields are simply carried forward unchanged once cached_staged_runner() returns None (which happens on every fresh process after a takeover re-exec, since the in-memory mutex resets). Live-witnessed on runner 0.1.136/0.1.137 (2026-09-14): C:/dev/spoint and C:/dev/gm each showed a DIFFERENT frozen waiting_ms (7297 and 7244) that did not move for 30+ minutes, then a forced runner-refresh (`plugin-refresh {runner:true}`) drove a real, fast (~13s) 0.1.136->0.1.137 handoff (staged -> building engine -> readiness marker confirmed -> promoted -> re-exec -> ownership claimed, all logged) and BOTH projects' frozen values survived unchanged across the version bump -- proving dispatches were never actually blocked (the real self-update pipeline is bounded and fast), only the status field is misleading. Fix: add a None-branch that removes both keys from the payload (same shape already used for the busy_until field a few lines above). This exact fix was found already drafted, uncommitted, in agentplug's working tree by a concurrent session at the same time this was diagnosed -- verify it lands and ships before closing the row.
