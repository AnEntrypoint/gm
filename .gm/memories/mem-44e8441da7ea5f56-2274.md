agentplug-runner self-update could permanently suppress itself via a LYING version marker -- root-caused and fixed 2026-07-29. SYMPTOM: ~/.agentplug/agentplug-runner.version read 0.1.7 while the executing daemon binary reported `agentplug-runner 0.1.0` under --version, with a staged agentplug-runner.exe.new (genuinely 0.1.7) orphaned on disk and both last_plugin_update_poll_ts / last_runner_update_poll_ts gone null in daemon-status.json. MECHANISM: download.rs::stage_runner_self_update short-circuited on `installed_runner_version() == latest`; with the marker already claiming latest, the daemon concluded it was current and never re-staged -- self-sealing, so the swap that never happened could never be retried. HOW THE MARKER GOT AHEAD OF REALITY: daemon.rs run_takeover calls record_runner_version(version) at ~line 468 immediately after claim_ownership() succeeds but BEFORE run_daemon_body actually serves; a takeover process that claims the lock then dies (crash/kill/machine event) leaves the marker advanced with no swap performed, and the old binary later reclaims the lock. The daemon-takeover-ready.json left behind names the dead takeover pid, which is a useful tell. FIX SHIPPED (agentplug 859cee9cff, origin 69d0d24): marker_is_trustworthy_and_current() trusts the marker only when it ALSO equals the running build's CARGO_PKG_VERSION; on disagreement it logs both versions, rewrites the marker to the truth, and returns false so staging proceeds -- self-healing rather than merely ignoring. METHOD LESSON worth more than the bug: I first blamed the unguarded-looking bootstrap write at daemon.rs:1279-1280 and was WRONG -- reading it showed it is guarded by `if installed_runner_version().is_none()` and writes CARGO_PKG_VERSION, so a 0.1.0 binary could not produce a 0.1.7 marker there. Reading the candidate site to DISPROVE it, rather than pattern-matching on 'this write looks unguarded', is what located the real one. GENERAL RULE: when a persisted state marker and observable reality disagree, find the write that records intent rather than completion -- and prefer a marker derived from, or cross-checked against, something self-proving (the running binary's own version, a content hash) over a bare written value that nothing ever re-validates.
